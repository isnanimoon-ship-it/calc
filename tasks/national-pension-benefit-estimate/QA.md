# QA: 국민연금 예상수령액 계산기

## 검증 방법 (중요 — 먼저 읽을 것)

계산 정확성(Calculation Auditor PASS, nps.or.kr 라이브 계산기 21개 데이터포인트 대조 완료,
Optimizer 수정 후 재검증까지 완료)은 전제로 삼고 **재검증하지 않았다.** 이번 QA는 실사용
흐름·기능·모바일·브라우저·접근성·입력 검증에 집중했다.

이 QA는 코드 정독에 그치지 않고 **실제 브라우저(headless Chrome/Edge, CDP 프로토콜)로
실제 타이핑 → 제출 → 결과 렌더링까지 전체 플로우를 재현**했다. 방법:

1. Windows에 설치된 Chrome(153.0.8010.36)·Edge(152.0.4191.66, Chromium 엔진)를
   `--headless=new --remote-debugging-port`로 구동하고, Chrome DevTools Protocol을
   Node(v24, 내장 `WebSocket`/`fetch`)로 직접 제어하는 자동화 스크립트
   (스크래치패드 `automate.mjs`)를 작성해 실제 `<input>`/`<select>`에 네이티브 값 설정 +
   `input`/`change` 이벤트를 발생시키고(React가 실제로 감지하는 방식), 버튼 텍스트로 실제
   클릭(`계산하기`/`초기화`/`샘플 값 채우기`/`링크 복사`)을 수행한 뒤 DOM 텍스트·
   `role="alert"` 요소·스크린샷을 수집했다. 이는 실제 사용자의 타이핑→계산 흐름을 그대로
   재현한 것이며, 단순 코드 정독이 아니다.
2. 공유 상태 복원 기능(`useCalculatorShare`/`buildStateShareUrl`, 이 계산기가 이미 구현한
   기능)을 이용해 `?s=<base64>` 쿼리로 특정 입력 조합을 페이지 로드 시 자동 복원·자동
   계산시켜, 여러 시나리오(최댓값 스트레스, 조기/연기 등)를 빠르게 여러 뷰포트에서
   스크린샷으로 재검증했다. 이 경로도 실제 앱 코드(`validateNationalPensionBenefitInput`,
   `calculateNationalPensionBenefit`)를 그대로 통과한다 — 별도 mock이 아니다.
3. 뷰포트별 실제 렌더링은 `Emulation.setDeviceMetricsOverride`로 320/375/390/768/1440px을
   그대로 재현했고, 일부는 `getBoundingClientRect()`/`scrollWidth`/`clientWidth` 실측으로
   텍스트 잘림 여부를 픽셀 단위로 확인했다(육안 스크린샷 판단에만 의존하지 않음).
4. 회귀 테스트(`npx vitest run`, `npx tsc --noEmit`, `npm run build`)는 Bash로 직접 실행했다.
5. 코드 수정 권한이 없으므로 발견한 모든 이슈는 등급과 함께 기록만 하고 직접 고치지 않았다.

**한계**: Firefox/Safari(비-Chromium 엔진)는 이 환경에 설치돼 있지 않아 테스트하지 못했다
(Chrome·Edge 두 Chromium 계열 브라우저만 확인). 클립보드 쓰기(`navigator.clipboard.writeText`)는
headless CDP 샌드박스에서 권한 부여(`Browser.grantPermissions`) 후에도 실제 OS 클립보드
반영을 끝까지 확인하지 못했다 — 아래 "Copy / Reset" 절에 상세히 기록.

### 1. 정상 케이스 — 출생연도 1970, 총 가입기간 300개월, 평균소득 300만원
실제 입력창에 `1970`/`300`/`3000000`을 타이핑(금액 필드는 숫자만 입력했는데도 실시간으로
`3,000,000`으로 콤마 포맷 자동 적용 확인) 후 "예상 연금액 계산하기" 클릭.

- 결과: 법정 수급개시연령 **65세(2035년부터)**, 예상 노령연금 월 수령액 **832,250원**.
- 독립 검산: `factor = 1+0.05×(300-240)/12 = 1.25`(125.0% 표시와 일치),
  `raw = 1.29×(3,193,511+3,000,000)×1.25/12 = 832,253.04`, `floor(.../10)*10 = 832,250` —
  실제 화면 값과 정확히 일치.
- 계산 근거(A값·B값·비례상수·보정계수), 적용된 입력값 섹션 모두 정확히 표시됨.

## 모바일 테스트 (320 / 375 / 390 / 768 / 1440px)

실제 헤드리스 브라우저 뷰포트 렌더링(스크린샷 + `getBoundingClientRect` 실측) 기준.

- **1440px**: 정상 케이스 전체 페이지 스크린샷 확인 — 폼, 결과 카드, 계산 상세, 계산
  방법, 적용된 입력값, 사용 방법/소개, 정책 안내, FAQ 전부 레이아웃 정상. 가로 스크롤 없음.
- **768px**: `sm:` 브레이크포인트(640px) 적용으로 "계산 상세"·"적용된 입력값" `dl`이
  2열 그리드로 정상 전환됨. 레이아웃 붕괴 없음.
- **390px**: 정상 케이스 기준 레이아웃 정상(카드 폭·패딩 문제 없음).
- **375px**: 조기/연기 select 최장 라벨("5년 앞당겨 받기(조기노령연금, -30.0%)",
  "5년 늦춰 받기(연기연금, +36.0%)") **완전히 표시됨**(잘림 없음, 여유 폭 있음, 스크린샷
  확인). 조기/연기 이중 카드 레이아웃도 겹침·overflow 없음.
- **320px**: 아래 두 항목을 정밀 실측.

### [Medium, 재현 확인] select 최장 라벨이 320px에서만 잘림 (Critic Q13 실측 확정)

`getBoundingClientRect()` 기준 select 박스 실제 폭은 **238px**(320px 뷰포트, 좌우 폼 패딩
제외). 이 폭에 "5년 앞당겨 받기(조기노령연금, -30.0%)"(선택된 옵션 텍스트, `select.value`
`-60`)를 렌더링한 클로즈드 상태 스크린샷을 클리핑해 직접 확인한 결과:

> 화면에 보이는 텍스트: **"5년 앞당겨 받기(조기노령연금, -"** 까지만 보이고 **"30.0%)"
> 부분이 완전히 잘려 보이지 않는다.**

`getComputedStyle(select).textOverflow`가 `"clip"`(ellipsis 아님)이라 잘렸다는 시각적
신호(`...`)조차 없다 — 사용자는 자신이 정확히 몇 %가 감액/가산되는 옵션을 선택했는지
**닫힌 select 박스만 봐서는 알 수 없다**(라벨에서 가장 중요한 숫자 부분이 잘림). 375px부터는
동일 텍스트가 완전히 표시되어 문제가 320px 뷰포트에만 국한됨을 확인했다.

- 실제 제출/계산에는 영향이 없다(값 자체는 정상 제출·계산됨, "적용된 입력값" SectionCard와
  "계산 방법" 5단계에는 잘리지 않은 전체 라벨/조정률이 별도로 다시 표시되므로 계산 후에는
  확인 가능하다) — 따라서 Mobile Critical(기능 사용 불가)은 아니다.
- **Chrome과 Edge(둘 다 Chromium 엔진) 양쪽에서 동일하게 재현**됨(교차 브라우저 확인,
  아래 "브라우저 테스트" 참고).
- **등급: Medium** (Critic이 코드 정독+추정으로 예측한 것을 이번 QA가 실제 렌더링으로
  확정. 320px는 SPEC.md가 명시한 지원 대상 뷰포트이므로 등급을 낮추지 않는다.)
- 개선 권고(Critic 제안과 동일): 라벨을 "5년 앞당김(-30.0%)"처럼 축약하거나, 320px 한정
  `text-xs`로 축소하거나, select 대신 커스텀 콤보를 쓴다.

### [Low → 재검증 결과 "문제 재현 안 됨"] 핵심 결과 카드 최댓값 오버플로 (Critic Q14 재검증)

Critic이 우려한 "8자리 금액 320px 오버플로" 가능성을 이 사이트 현재 검증 규칙 상 **실제로
도달 가능한 최댓값**으로 재현했다: `totalContributionMonths` 상한(624개월, `validation.ts`
`MAX_TOTAL_CONTRIBUTION_MONTHS`) + 평균소득 상한 clamp(6,590,000원) + 연기 최대(+60개월)
조합 → **adjustedPensionMonthly = 3,718,900원**(7자리, "3,718,900원" 10글자).

320px에서 이 값을 표시하는 `<p class="text-4xl ...">` 요소를 실측한 결과:

| 측정값 | 결과 |
|---|---|
| 텍스트 | "3,718,900원" |
| `clientWidth` | 230px |
| `scrollWidth` | 230px (== clientWidth, 넘치는 내용 없음) |
| `offsetHeight` | 40px (= 1줄 높이, 줄바꿈도 발생하지 않음) |
| 부모 컨테이너 `clientWidth` | 278px |

**230px < 278px로 48px의 여유가 있어 320px에서도 한 줄로 완전히 표시되며, 잘리거나
줄바꿈되지 않는다.** 또한 이 `<p>`에는 `whitespace-nowrap`/`truncate`가 없어 설령 폭이
부족해도 클리핑이 아니라 자동 줄바꿈(콘텐츠 손실 없음)으로 안전하게 열화하는 구조임을
코드로도 확인했다.

- **결론: 이 계산기가 실제로 낼 수 있는 최댓값 기준으로는 재현되지 않는다.** Critic의 우려
  자체는 합리적인 사전 점검이었으나(코드만으로는 실제 렌더링을 확정할 수 없었음), 실측
  결과 문제가 없다. **등급을 Low(추적 필요)에서 "확인 완료·문제 없음"으로 하향한다.**
- 참고로 Critic이 예시로 든 "3,720,908원"(ARCHITECTURE.md 추정치)은 실제 검증 상수
  (`MAX_TOTAL_CONTRIBUTION_MONTHS=624`)를 적용한 재계산 결과(3,718,900원)와 근사하지만
  정확히는 일치하지 않는다 — 사소한 차이이며 결론(오버플로 없음)에는 영향 없음.

## Accessibility

실제 DOM(정적 코드가 아니라 렌더링된 페이지)에서 확인:

- 검증 오류 발생 시 각 오류 `<p>`가 실제로 `role="alert"`이고 `id`가
  `{formId}-{field}-error` 패턴으로 생성되며, 해당 입력의 `aria-describedby`가 오류 발생
  시 이 id를 포함하도록 전환되는 것을 실제 오류 3~7건 시나리오 전부에서 확인했다.
- 결과 영역(`aria-live="polite"`)이 실제로 결과 유무에 따라 내용이 나타나고(계산 후)
  사라지는(리셋 후) 것을 확인했다.
- select에 `id`/`htmlFor` 연결 확인, 실제 `change` 이벤트로 값 변경이 정상 반영됨을 확인
  (네이티브 select 시맨틱 그대로 사용, 커스텀 리스트박스 아님 — 스크린리더 호환성 측면에서
  유리).
- 라벨-입력 연결(`htmlFor`/`id`)은 4개 필드 모두 정상.
- 키보드만으로의 tab 순서 실사용 시뮬레이션(개별 Tab 키 이벤트 순회)까지는 이번 QA에서
  수행하지 못했다 — 코드상 `tabIndex` 오버라이드가 전혀 없어(DOM 선언 순서 = 논리적 입력
  순서) 자연스러운 순서가 보장된다는 점은 코드 검토로 확인했다.
- **문제없음**(Critic Q17과 동일 결론, 실제 렌더링으로 재확인).

  Critic 단계에서는 확정되지 않았던 사실이므로, **published 전환 최종 승인 여부는
  오케스트레이터/Product Owner가 이 QA 결과를 반영해 판단할 것을 권고한다**(QA는 등급
  판정과 기록까지가 권한이며 registry.ts를 직접 수정하지 않았다).
