# QA: 기초대사량(BMR) 계산기 (bmr-calculator)

검토 대상: `src/calculators/bmr-calculator/{logic,validation,formatting,content,types,ui}.tsx`
및 각 `*.test.ts`, `src/calculators/registry.ts`(등록 상태 `draft`, 아이콘 `chart`, 카테고리
`health`). Builder(자체 확인) → Calculation Auditor(PASS, 재검증까지 PASS 확정) →
UX/UI Critic(PASS, Medium 1건·Low 4건) 완료 후 QA 진행. Edit 권한이 코드에는 전혀 없어
소스 코드를 한 글자도 수정하지 않았다.

## 검증 방법 요약

- 사전 문서 확인: `tasks/bmr-calculator/{SPEC,FORMULA,EVALUATION}.md` 전문,
  `docs/DESIGN_SYSTEM.md`, `docs/EVALUATION.md`. 계산 정확성(Auditor PASS)은 전제로 삼고
  재검증하지 않았다 — 이번 QA는 실사용 흐름(타이핑 → 계산 → 결과)과 기능/모바일/브라우저/
  입력검증/접근성, UX/UI Critic이 남긴 Medium 1건·Low 4건의 재현·독립 등급 판정에 집중했다.
- **실제 헤드리스 Chrome/Edge(Chrome DevTools Protocol)로 진짜 타이핑→클릭→렌더 결과를
  확인했다.** 이 머신에 Playwright/Puppeteer는 없지만 `chrome.exe`/`msedge.exe`가 설치돼
  있어, Node 24 내장 `WebSocket`/`fetch`로 최소 CDP 클라이언트(`cdp.mjs`)를 직접 만들어
  사용했다. **반드시 `--user-data-dir`로 세션 전용 임시 프로필**(스크래치패드 하위,
  `qa-bmr-profile`/`qa-bmr-profile2`/`qa-bmr-edge-profile`/`qa-bmr-final`)을 지정해 브라우저를
  띄웠고, 사용자의 실제 브라우저(프로필)는 전혀 건드리지 않았다. 검증에 사용한 모든 스크립트·
  스크린샷은 `C:\Users\isnan\AppData\Local\Temp\claude\...\scratchpad\`(세션 전용, 프로젝트
  밖)에만 저장했다 — QA 시작 전/후 `ls src/calculators/bmr-calculator/` 결과가 동일함을
  확인했다(코드 한 글자도 수정하지 않음). 작업 종료 시 각 브라우저의 메인 PID를
  `taskkill /T /F`로 종료해 자식 프로세스까지 모두 정리했고(`qa-bmr*` 패턴 프로세스 최종
  0개 확인), 이미 실행 중이던 dev 서버(`localhost:3000`, 다른 세션이 띄운 것을 그대로
  재사용, 새로 띄우지 않음)는 QA 종료 후에도 200 정상 응답함을 재확인했다.
- **중요 — 테스트 하네스 자체의 함정을 발견하고 스스로 재검증한 경위를 투명하게 기록한다.**
  초기 스크립트에서 `document.querySelector('[aria-live="polite"]')`로 결과 영역을 찾았는데,
  이 셀렉터가 실제로는 `ShareActions` 컴포넌트의 피드백 문구
  (`<p aria-live="polite">...`, DOM상 결과 영역보다 앞서 렌더링되고 평소엔 빈 문자열)를
  먼저 매칭해버려 결과가 있는데도 "결과 없음"으로 오판하는 사고가 있었다. `div[aria-live=
  "polite"]`로 셀렉터를 구체화해 해결했다 — 이 과정에서 "제출 후 결과가 안 뜬다"는 여러
  차례의 잘못된 재현(Chrome 프로세스 재시작, 프로필 재생성까지 시도)이 있었으나, 모두
  애플리케이션 결함이 아니라 QA 스크립트 자체의 셀렉터 버그였음을 최종적으로 확인했다
  (수정 후 모든 시나리오가 일관되게 통과했고, 원인 규명 과정에서 MutationObserver·네이티브
  submit 이벤트 캡처 등으로 실제 폼 제출/React 상태 변경 자체는 처음부터 정상 동작하고
  있었음을 다각도로 확인했다). 이 실수와 해결 과정을 숨기지 않고 기록한다.
- 회귀 스위트: `npx vitest run`(전체), `npx tsc --noEmit`, `npm run build`.

## 모바일 테스트 (320 / 375 / 390 / 768 / 1440px)

실제 헤드리스 Chrome에서 `Emulation.setDeviceMetricsOverride`로 5개 뷰포트를 그대로
재현하고, `document.documentElement.scrollWidth`/`clientWidth`를 직접 비교해 가로 스크롤
여부를 실측했다(육안 스크린샷 판단에만 의존하지 않음). 각 뷰포트에서 **결과가 없는 상태**와
**Male 30/175/70 + 활동량"보통 활동" 계산 완료 상태** 둘 다 측정했다.

| 폭 | 결과 없음 (scrollWidth=clientWidth) | 결과 있음 (scrollWidth=clientWidth) |
|---|---|---|
| 320px | 320=320 (overflow 없음) | 320=320 (overflow 없음) |
| 375px | 375=375 | 375=375 |
| 390px | 390=390 | 390=390 |
| 768px | 753=753 | 753=753 |
| 1440px | 1425=1425 | 1425=1425 |

5개 뷰포트 × 2개 상태(결과 전/후) = 10개 조합 전부 **가로 스크롤 없음**을 실측으로 확인했다.

### UX/UI Critic Q11(Low) — "활동량 카드 6개 세로 스크롤 길이 / 폼 헤더 배지 좁은 화면 랩" 실기기 재현

- **폼 헤더 배지("필수 4개") 랩 위험 — 재현되지 않음.** `getBoundingClientRect()`로 배지의
  오른쪽 끝 좌표를 5개 뷰포트 전부에서 실측한 결과, **320px에서도 `badgeRight=279px <
  viewportWidth=320px`로 41px의 여유**가 있었다(375px: 41px 여유, 390px: 41px 여유, 768px:
  80px 여유, 1440px: 216px 여유). 배지 텍스트가 짧아("필수 4개") 어떤 뷰포트에서도 줄바꿈이
  일어나지 않는다. **Critic의 우려는 합리적인 사전 점검이었으나, 실측 결과 320px를 포함한
  전 구간에서 재현되지 않았다.**
- **활동량 카드 6개 세로 스크롤 길이 — 실측 확인(문제는 아님, 사실관계만 확정).** 활동량
  라디오 카드 6개를 담은 컨테이너(`.space-y-2`)의 실제 렌더 높이를 측정한 결과, **5개
  뷰포트 전부에서 정확히 424px로 동일**했다(카드 목록은 세로 스택 레이아웃이라 뷰포트
  폭과 무관하게 높이가 고정됨). 320px 화면(가로) 대비 424px는 화면 하나를 거의 다 채우는
  분량이라 스크롤이 필요한 것은 사실이지만, `docs/DESIGN_SYSTEM.md` "모바일" 절이 요구하는
  것은 "가로 스크롤 없음"이지 세로 스크롤 금지가 아니다 — 320px 스크린샷에서도 카드 6개가
  잘리거나 겹치지 않고 순서대로 정상 표시됨을 확인했다(아래 스크린샷 참고). **결함이 아니라
  Critic이 이미 정확히 분류한 대로 "체감상 길다"는 사실 확인에 그친다.**

### 스크린샷 확인 (320px, 375px 전체 페이지 + 결과 카드 확대)

- 320px 전체 페이지 스크린샷(`mobile-320.png`, 7107px 높이) 육안 확인 결과, 폼 → 결과 →
  계산 상세 → 계산 방법 → 활동량 비교표 → 꼭 확인하세요 → 사용법/소개 → 정책 안내 → FAQ
  순서로 전부 정상 렌더링되고, 잘리거나 겹치는 요소가 없다.
  - 활동량 비교표(`overflow-x-auto` + `min-w-[28rem]`)는 320px에서 **표 내부에서만** 가로
    스크롤 여지가 있고 페이지 전체 레이아웃은 밀리지 않음을 스크린샷과 위 표(scrollWidth=
    clientWidth)로 함께 확인 — Auditor/Critic 문서가 이미 언급한 완화 패턴이 실제로도
    작동한다.
- 375px 결과 카드(BMR/TDEE) 확대 스크린샷(`result-zoom.png`)으로 아래 "UX/UI Critic Medium
  재현" 절의 캡션 가독성을 시각적으로 직접 확인했다.

  아님을 확인했다.

  모두 Chromium 계열이라 완전히 독립적인 두 렌더링 엔진 검증은 아니다 — 이전 QA 라운드들과

## 입력 검증

모두 실제 입력창에 값을 타이핑(React 컨트롤드 인풋에 대해 네이티브 setter + `input` 이벤트
디스패치)하고 "BMR 계산하기"를 클릭해 재현했다(코드 추정이 아니라 실제 `role="alert"` DOM
요소를 읽어 확인).

- **빈 입력**: 전 필드 공란 제출 → 4개 오류 동시 표시: "성별을 선택해 주세요.", "나이를

### [Low, QA 신규 발견] 키(height) 필드 오류 메시지의 한국어 조사(은/는, 을/를) 오류

`src/calculators/bmr-calculator/validation.ts` 60~86행 `validateHeightOrWeight` 함수가
"키"/"체중" 두 라벨에 **항상 "은"/"을"만 하드코딩**해서 메시지를 조립한다:

```ts
errors.push({ field, message: `${label}을 입력해 주세요.` });      // 71행
errors.push({ field, message: `${label}은 숫자여야 합니다.` });     // 75행
errors.push({ field, message: `${label}은 ${min}~${max}${unit} 사이여야 합니다.` }); // 81행
```

한국어 조사 "은/는", "을/를"은 앞 글자의 받침(종성) 유무로 결정된다. "체중"(받침 `ㅇ` 있음)은
"체중은"/"체중을"이 맞지만, "키"(받침 없음, 모음 `ㅣ`로 끝남)는 "**키는**"/"**키를**"이
맞다. 이 함수가 두 라벨 모두에 같은 템플릿을 재사용하면서 "키"의 조사만 문법적으로 틀리게
나온다. 실제 브라우저에서 재현한 3가지 문구 전부 확인:

- "**키을** 입력해 주세요." → "키를 입력해 주세요."가 맞음(키 필드를 비운 채 제출 시 실제
  렌더링됨).
- "**키은** 숫자여야 합니다." → "키는 숫자여야 합니다."가 맞음(키에 "abc" 입력 시 실제
  렌더링됨).
- "**키은** 100~230cm 사이여야 합니다." → "키는 100~230cm 사이여야 합니다."가 맞음(키
  99.9/230.1/음수/0/9999999 등 범위 밖 값 전부에서 실제 렌더링됨).

Chrome·Edge 두 브라우저 모두에서 동일하게 재현되며, `role="alert"`로 스크린 리더에도 그대로
낭독되므로 **시각 사용자뿐 아니라 스크린 리더 사용자에게도 문법이 틀린 문장이 그대로
전달된다.** SPEC.md·FORMULA.md·이전 라운드(Builder/Auditor/Critic) 어디에서도 지적되지
않은, 이번 QA가 처음 발견한 이슈다.

- **등급: Low.** 계산 결과나 검증 로직의 정확성 자체에는 전혀 영향이 없다(키 필드는 여전히
  올바른 조건에서 정확히 막히고 정확히 통과한다) — 순수하게 `docs/EVALUATION.md` Low 정의
  ("사소한 디자인/텍스트/정렬 문제")에 해당하는 텍스트 오탈자성 문제다. 다만 한국어
  네이티브 사용자에게는 눈에 띄는 비문이라 개선 우선순위는 낮지 않게 두는 것을 권고한다.
- **개선 권고(Optimizer 참고, 본인은 수정 불가)**: `validateHeightOrWeight`가 라벨별 조사를
  파라미터로 받거나(`particle: {을: "를", 은: "는"}` 형태), 아니면 "키"에 대해서만 별도
  메시지 템플릿을 쓰도록 분리한다. 조사 자동 판별 유틸(받침 유무로 을/를, 은/는 계산)을
  만들어 향후 다른 계산기에서도 재사용할 수 있게 하는 것도 고려할 만하다.

## Accessibility

실제 렌더링된 DOM(정적 코드가 아니라 브라우저가 만든 실제 트리)에서 확인:

- **label 연결**: 나이/키/체중 3개 입력 전부 `<label for="...">`가 대응하는 `<input id=
  "...">`와 정확히 연결됨을 `document.querySelector('label[for="'+el.id+'"]')`로 실측
  확인(`hasLabel: true` × 3, 라벨 텍스트 "나이 *(만 나이, 세)" 등도 정확히 렌더링됨을 함께
  확인).
- **오류 = role="alert" + aria-describedby + aria-invalid 연결**: 키를 5cm(범위 밖)로
  입력해 오류를 발생시킨 뒤, 키 입력의 `aria-describedby`가 `"...{id}-help {id}-error"`
  두 id를 공백으로 연결한 값이고, 이 중 `-error` id를 가진 요소가 실제로 `role="alert"`이며
  텍스트가 정확히 해당 오류 메시지임을, 그리고 `aria-invalid="true"`가 동시에 설정됨을
  확인했다.
- **aria-live**: 페이지 전체에서 `[aria-live="polite"]` 요소가 정확히 **2개** 존재함을
  확인했다 — (1) `ShareActions`의 공유 피드백 `<p>`("링크를 복사했습니다." 등을 담는 용도),
  (2) 계산 결과 전체를 감싸는 `<div>`(SPEC.md Must Have "결과 갱신 영역에 aria-live 적용"
  대상). 둘 다 의도된 설계이며, 결과 div 쪽에 계산 후 실제로 BMR/TDEE/계산 근거/의료 면책
  텍스트 전체가 담겨 스크린 리더가 결과를 온전히 낭독할 수 있음을 확인했다(테스트 스크립트
  초기에 이 두 요소를 혼동해 겪었던 시행착오는 위 "검증 방법 요약"에 투명하게 기록함).
- **라디오 그룹 키보드 조작(실제 방향키 이벤트로 재현, 작업 지시 핵심 확인 대상)**:
  - 활동량 그룹: 첫 번째 라디오("선택 안 함")에 `focus()`를 준 뒤 CDP
    `Input.dispatchKeyEvent`로 실제 `ArrowDown` 키를 전송 → 포커스가 다음 라디오(레벨1)로
    이동함과 **동시에 `checked` 상태도 레벨1로 전환**됨을 확인(`activeIndex: 1,
    checkedIndex: 1`).
  - 성별 그룹: "남성" 라디오에 포커스 후 실제 `ArrowRight` 전송 → 포커스와 `checked`가
    모두 "여성"으로 동시 이동(`activeIndex: 1, checkedIndex: 1`).
  - 두 그룹 모두 네이티브 `<input type="radio">` + 공유 `name` 속성 기반의 진짜 브라우저
    라디오 그룹 시맨틱으로 동작함을 실제 키 이벤트로 증명했다(코드 구조만 보고 추정한 것이
    아니라 실제 방향키 결과로 확인). **문제없음.**
- ESLint가 보고한 "aria-required on role=radio" 경고 1건(Builder 보고, `loan-interest-
  calculator`에도 동일 패턴 존재)은 이번 QA에서 새로 발견한 문제가 아니며 기존 사이트 전역
  패턴이라 등급을 매기지 않는다(Critic과 동일 결론).
