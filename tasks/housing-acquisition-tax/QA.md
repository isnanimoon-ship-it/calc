  계산기만의 결함이 아니라 `severance-pay`의 `handleAmountChange`(금액류)와 동일한 사이트
  전역 관례(금액은 실시간 숫자만 필터링해 콤마 포맷, 소수 허용 필드는 자유 입력 후 제출 시
  검증)를 그대로 따른 것이다. 다만 이 계산기는 자릿수 오류의 대가가 크다는 특성상(SPEC.md·
  UX Critic Q7이 이미 지적) `650000000.5`처럼 소수점을 실수로 넣으면 소수점이 사라지고
  숫자가 그대로 이어 붙어 **의도치 않게 훨씬 큰 금액(6.5억 → 65억대)으로 조용히 바뀐 뒤
  통과**된다는 점은 실측으로 새로 확인한 사실이다. 계산 자체는 필터링된 값 기준으로
  정확하므로 계산 오류는 아니지만(등급을 매기지 않음), Optimizer가 이미 추가한 "한글 단위
  실시간 환산" 보조 텍스트가 바로 이런 상황에서 사용자가 "6,500,000,005원 = 약 65억원"이라는
  이상함을 스스로 알아챌 수 있게 하는 완화 장치로 실제로 작동함을 함께 확인했다(위 "Optimizer
  기능 확인 1." 참고) — 즉 이 필터링 방식 자체의 위험을 Optimizer의 다른 수정이 상당 부분
  상쇄한다.

## Accessibility

실제 렌더링된 DOM(정적 코드가 아니라 브라우저가 만든 실제 트리)에서 확인했다.

- **label 연결**: 매매가·전용면적 입력 2개는 `<label for="...">`↔`<input id="...">`가
  정확히 연결됨을 확인. 조정대상지역·보유주택수 라디오 6개는 전부 `<label>`이 `<input
  type="radio">`를 감싸는 암묵적 연결(`wrappedInLabel: true`) 구조로, 별도 `id`/`for` 없이도
  유효한 라벨 연결임을 확인했다.
- **오류 = `role=alert` + `aria-describedby` + `aria-invalid` 연결**: 매매가에 `-100`을
  입력(실제로는 `100`으로 필터링됨)해 하한 미달 오류를 유발한 뒤, 입력의 `aria-describedby`가
  `"{id}-help {id}-korean-unit {id}-error"` 세 id를 공백으로 연결한 값이고, `aria-invalid=
  "true"`가 동시에 설정되며, `-error` id 요소의 텍스트가 실제 오류 메시지("매매가(취득가액)가
  너무 작습니다. 1,000,000원 이상인지 확인해 주세요.")와 정확히 일치함을 확인했다. 오류가 없는
  상태에서는 `-error` id가 `aria-describedby`에서 빠지고 `aria-invalid`도 `null`임을 함께
  확인했다.
- **aria-live**: 페이지에 `[aria-live="polite"]` 요소가 정확히 **2개** 존재함을 확인했다 —
  (1) `ShareActions` 공유 피드백 `<p>`(평소 빈 문자열), (2) 계산 결과 전체를 감싸는 `<div>`
  (SPEC.md Must Have 대상). 계산 완료 시 (2)번 영역 안에 총 납부액·세목별 내역·계산
  근거·정책 고지 전체가 담겨 스크린 리더가 결과를 온전히 낭독할 수 있음을 확인했다.
- **FAQ 아코디언**: 첫 번째 FAQ 버튼을 실제로 클릭한 뒤(React 리렌더를 기다린 후 재조회)
  `aria-expanded`가 `"false"`→`"true"`로 바뀌고, `aria-controls`가 가리키는 패널 요소가
  실제로 `role="region"` + `aria-labelledby="{버튼 id}"`를 갖고 있으며 패널 안에 해당 FAQ의
  실제 답변 텍스트가 렌더링됨을 확인했다(7개 버튼 전부 `aria-expanded`/`aria-controls`
  속성을 갖고 있음을 우선 확인 후, 그중 1개를 실제 클릭으로 검증).
- **키보드 전용 조작 — 부분적으로만 실기기 수준으로 확인됨(도구 한계, 아래 참고)**: CDP
  `Input.dispatchKeyEvent`로 Tab/화살표 키를 합성 전송하는 시도는 `Input.insertText`(텍스트
  삽입)는 정상 동작했으나 **Tab 키에 의한 포커스 이동만은 이 headful Chrome 세션에서
  재현되지 않았다**(OS 레벨 창 포커스와 무관하게 CDP가 렌더러에 전달하는 저수준 키 이벤트가
  브라우저 크롬의 기본 탭 순회 동작까지는 트리거하지 못한 것으로 보인다 — 애플리케이션
  결함이 아니라 이번 세션의 CDP 도구 한계로 판단한다, 아래 "도구 한계" 참고). 대신 **정적
  구조 검증으로 키보드 접근성의 전제조건을 확인**했다: `ui.tsx` 전체에서 `onKeyDown`/
  `tabIndex`/키보드 기본 동작을 가로채는 커스텀 핸들러가 **전혀 없음**을 Grep으로 확인했고,
