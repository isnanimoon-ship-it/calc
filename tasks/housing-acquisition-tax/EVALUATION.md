### 판단이 필요했던 애매한 지점 (다음 역할이 참고할 것)

- **"raw 재사용 금지" 불변식이 이 계산기의 구체적인 상수 조합에서는 수치로 관찰되지 않는다는
  발견.** ARCHITECTURE.md "6."은 "지방교육세 표준세율 분기가 절사 후 `acquisitionTax`를
  재사용하면 예제 17류의 비정형 금액에서 결과가 미세하게 달라진다"고 명시했다. 이를 실제로
  화이트박스 테스트로 검증하려 하는 과정에서, **표준세율 지방교육세 계수가 정확히 0.1(=1/10)
  이고 절사 단위가 정확히 10원이기 때문에, `truncateTo10Won(truncateTo10Won(raw) × 0.1) ==
  truncateTo10Won(raw × 0.1)`가 항상 성립한다는 수학적 항등식(`floor(floor(x/10)/10) ==
  floor(x/100)`)을 발견했다** — 즉 이 계산기의 현재 상수로는 "절사 후 값을 재사용하는 버그"를
  넣어도 최종 화면에 보이는 지방교육세 숫자가 달라지지 않는다(직접 코드로 대입해 여러
  값에서 확인, `logic.test.ts`에 근거와 함께 기록). Builder는 그럼에도 FORMULA.md/
  ARCHITECTURE.md의 명시적 지시(절사 전 `acquisitionTaxRaw` 참조)를 그대로 구현했다 —
  (1) 이것이 명시적으로 요구된 계약이고, (2) 계수가 나중에 바뀌면 이 수학적 우연이 깨질 수
  있어 방어적으로 옳은 구현이기 때문이다. **Calculation Auditor에게 요청**: 이 지점은 Golden
  Test 통과 여부만으로 "계약 준수"를 판정할 수 없으므로, `logic.ts` 소스에서
  `acquisitionTaxRaw`(절사 전 변수)를 실제로 참조하는지 코드를 직접 읽어 확인해야 한다.
- **"계산 근거" 화면의 raw 노출 방식** — `types.ts`(Architect 확정)는
  `HousingAcquisitionTaxResult`에 raw 필드를 노출하지 않기로 이미 결정했지만,
  ARCHITECTURE.md "9.1"은 UI에 "세목별 raw→절사 과정(실제 대입값)"을 보여줄 것을 요구한다.
  이 모순을 해소하기 위해 `formatting.ts`의 `buildTaxCalculationBreakdown`이
  `input.acquisitionPrice`(입력값)와 `result.appliedRate`(결과값, 둘 다 이미 공개된 필드)를
  다시 곱해 raw를 재현하는 방식을 택했다 — 이는 세율 판정을 재구현하는 게 아니라 이미
  logic.ts가 사용한 것과 동일한 두 값의 단순 곱셈이라 안전하다고 판단했지만, Calculation
  Auditor/Architect가 이 설계 판단 자체에 동의하는지 재검토를 요청한다.
- **취득가액 하한(100만원)** — SPEC.md가 "비정상적으로 작은 값"을 걸러내라고 했지만 정확한
  하한을 위임했다. 실제 주택 매매 시나리오라면 이보다 훨씬 클 것이므로 100만원을 순수
  타이핑 실수 방어용 넉넉한 하한으로 정했다 — QA/UX Critic이 이 값이 너무 낮거나(오류 감지
  안 됨) 너무 높은지(정상 입력 오탐) 재검토할 여지가 있다.
- **조정대상지역 참고 스냅샷의 UI 배치** — ARCHITECTURE.md "3.3"은 "helpText·샘플 값 구성에
  참고"라고만 정하고 정확한 화면 위치는 정하지 않았다. Builder는 입력 폼 자체를 복잡하게
  만들지 않기 위해 이 스냅샷 전문을 FAQ 첫 항목("조정대상지역인지 어떻게 확인하나요?")에
  배치했다 — 입력 옆 helpText에는 방법 안내와 자가 확인 책임 문구만 남기고, 3차 출처 신뢰도
  고지가 포함된 상세 목록은 FAQ로 옮겼다. UX/UI Critic이 이 배치가 "확인 시점 기준 직접
  확인" 책임을 흐리지 않는지 재검토할 것을 권고한다.

### Calculation Auditor 인수인계 — 최우선 체크리스트(ARCHITECTURE.md "14." 그대로)

1. **6~9억 구간 세율의 소수 4자리 반올림이 fraction 값 자체에 적용됐는지** — 6.5억(0.0133)·
   8억(0.0233) 회귀 테스트로 확인됨(`logic.test.ts`). 위택스 등 1차 출처로 추가 재검증 권고.
2. **10원 미만 절사(내림) 규칙을 wetax.go.kr 등 실제 계산기와 최소 1건 이상 대조** —
   `policy.ts` `rounding`이 "확인 필요"로 명시한 잠정 정책. 아직 대조하지 않았다.
3. **농특세 중과세율(0.6%/1.0%) 산정 방식의 "부분 확인" 재검증** — 법 조문이 제13조의2를
   명시적으로 규정하지 않아 정황·수치 일치로만 교차검증된 상태. 가능하면 위택스 대조로 격상
   권고.
4. **4구간 heavyRate 8행 전체가 실제로 8%/12%/표준세율을 정확히 분기하는지** — 예제 13
   (비조정 4채 이상, 12%)과 예제 11(비조정 3채, 8%)의 22,000,000원 차이가
   `logic.test.ts`에서 실제로 재현됨을 확인했다(위 "Golden Test" 참고). 8행 전체 스윕
   테스트도 통과했다.

위 4개 항목은 Builder 테스트 통과로 "해결됨"이 아니라 **Calculation Auditor가 독립적으로
재검증해야 할 최우선 대상**이다.

### 1. [최우선] 6~9억 구간 세율의 소수 4자리 반올림 대상 검증 — **Architect 해석(fraction
   자체 반올림)이 옳다. 코드도 그 해석대로 구현됐다.**

- **코드 확인**: `policy.ts` `standardRate.midTier` 주석과 `logic.ts`
  `determineStandardRate`를 라인 단위로 읽었다.
  ```ts
  const rawFraction =
    ((acquisitionPrice / midTier.divisor) * midTier.multiplier - midTier.subtract) /
    midTier.percentDivisor;               // 예: 700,000,000원 → 0.016666667(소수/fraction)
  const scale = 10 ** midTier.roundDecimalPlaces;   // 10^4 = 10000
  const standardRate = Math.round(rawFraction * scale) / scale;   // 0.0167
  ```
  `percentDivisor`(=100)로 나눠 **먼저 fraction으로 만든 뒤** 그 값을 4자리로 반올림한다 —
  프로즈("1.6667%")가 아니라 검증 예제(0.0133/0.0233) 방식 그대로 구현됨을 코드로 직접
  확인했다.
- **독립 재계산**: 별도 Python 스크립트로 6.5억원(0.0133346...→0.0133 아님, 실제
  0.01333333→0.0133), 8억원(0.02333333→0.0233), 7억원(0.01666667→0.0167)을 처음부터
  다시 계산해 모두 코드/테스트 값과 일치함을 확인했다.
- **외부 1차 출처 원문 직접 대조**: casenote.kr의 지방세법 제11조 원문을 직접 열람해
  "소수점이하 다섯째자리에서 반올림하여 소수점 넷째자리까지 계산한다"는 반올림 규정
  문구 자체를 확인했다(이 문구만으로는 반올림 대상이 fraction인지 percent인지 완전히
  명시하지 않지만, 아래 실제 계산 사례가 이를 결정적으로 해소한다).
- **외부 실제 계산 사례로 결정적 확인(신규 발견, Architect가 하지 못했던 부분)**: 위
  `jptcalc.kr`와 `jiptax.com`에서 실제로 존재하는 계산 예시를 직접 열람해 다음을 확인했다.
  - 7.5억원, 85㎡ 이하, 1주택: 세율 2%, 총 납부액 1,650만원 — 우리 코드/FORMULA로 재계산한
    16,500,000원과 **원 단위까지 정확히 일치**.
  - 7억원, 85㎡ 이하 가정 취득세+지방교육세: 12,859,000원 — 코드로 재계산하면
    `acquisitionTax=700,000,000×0.0167=11,690,000`, `localEducationTax=1,169,000`,
    합계 12,859,000원으로 **원 단위까지 정확히 일치**. (percent를 먼저 반올림하는 대안
    해석 — 0.016667 그대로 사용 — 으로 계산하면 취득세 11,666,900원, 합계 12,833,590원이
    되어 이 실제 사례와 **어긋난다**. 즉 이 외부 사례가 fraction-반올림 해석이 맞고
    percent-반올림 해석이 틀렸다는 것을 실제 숫자로 반증한다.)
  - 8억원, 85㎡ 이하 취득세+지방교육세: 20,504,000원 — 코드로 재계산(18,640,000+
    1,864,000=20,504,000원)과 **정확히 일치**.
  - 8억원, 1주택 표준세율 취득세 본세: 18,640,000원 — `800,000,000×0.0233`과 **정확히
    일치**.
- **결론**: Architect의 해석과 Builder 구현 모두 옳다. 단순히 "검증 예제와 자기 정합적"이라는
  수준을 넘어, 이 세션에서 실제로 존재를 확인한 제3자 세금 계산 자료(1차 출처인 위택스는
  아니지만 원 단위로 정확히 일치하는 구체적 계산 사례)로 fraction-반올림 해석을 결정적으로
  뒷받침했다. **이견 없음.**

  수식을 전개해, `standardRateFactor = 0.1`이고 절사 단위가 정확히 10원인 한,
  `floor(floor(x/10)/10) == floor(x/100)`이 **임의의 음이 아닌 실수 x에 대해 항상
  성립하는 일반 항등식**임을 증명했다(핵심: `y = floor(x/10)*10`이라 하면 `y ≤ x < y+10`이고,
  `y`가 100의 배수 경계를 막 지난 값(예: `y mod 100 = 90`)이어도 다음 100의 배수는 `y+10`
  이므로 `x < y+10`인 한 그 경계를 절대 넘지 못한다 — 따라서 `floor(x/100)`과 `floor(y/100)`은

  고르더라도 raw-재사용 버그를 출력값만으로는 절대 구분할 수 없다"**는 더 강한(그리고
  Optimizer에게 더 중요한) 사실이다.

- **Optimizer를 위한 권고(코드/테스트를 직접 고치지 않고 기록만 남김)**: 이 불변식은

`ui.tsx`의 4개 라벨을 직접 확인했다: "매매가(취득가액)", "전용면적", "이 지역은 정부가
지정한 규제지역인가요?", "이 집을 포함해서 총 몇 채를 갖게 되나요?". 뒤의 두 라벨은
SPEC.md가 요구한 대로 "조정대상지역"·"다주택자"·"세대 합산" 같은 법령 용어를 라벨에서
완전히 제외하고 helpText로만 옮겼다 — 이 부분은 모범적으로 잘 지켰다. 다만 "매매가(취득가액)"
라벨은 `docs/DESIGN_SYSTEM.md` "라벨 표현" 원칙("정확한 법령 용어가 필요하면 라벨이 아니라
helpText에 넣는다")과 엄밀히는 어긋난다 — "취득가액"은 FORMULA.md·SPEC.md가 쓰는 지방세법
용어이자 실제 취득세 신고서에 등장하는 용어라, `severance-pay`의 FIELDS(라벨에 법령 용어를
전혀 남기지 않음, "이직일" 대신 순수히 "퇴사일"만 사용)와 비교하면 이 계산기는 법령 용어를
괄호로 남겼다는 점에서 기준이 살짝 낮다. 다만 (a) 주 용어(매매가)를 앞에 두고 법령 용어는
보조로만 병기했고, (b) "취득가액"은 실제 계약·신고서에서 사용자가 마주칠 가능성이 있는
용어라 위험도가 낮아 **Low**로 판정한다.

**Q2 (필수). 입력 순서 — 등급: 문제없음.**
`ui.tsx` 213~353행을 확인한 결과 매매가 → 전용면적 → 조정대상지역 → 보유 주택 수 순서로,
SPEC.md "핵심 사용자 흐름" 1~4단계와 정확히 일치한다. 이 계산기는 "기간을 이루는 두 날짜"

**Q3 (필수). 용어 통일 — 등급: Medium.**
라벨은 "매매가(취득가액)"로 "매매가"를 앞세우고, `h1` 아래 요약문·helpText("실제 계약서상
매매가를...")도 전부 "매매가"를 1순위 용어로 쓴다. 그런데 `validation.ts`의 오류 메시지 5개 중
4개("취득가액은 숫자로 입력해 주세요.", "취득가액은 0보다 커야 합니다.", "취득가액이 너무
작습니다...", "취득가액이 너무 큽니다...")는 "매매가" 없이 "취득가액"만 단독으로 쓴다(필수값
누락 메시지 1개만 "취득가액(매매가)을 입력해 주세요."로 둘 다 병기). 라벨이 애써 "매매가"를
1순위로 세워놨는데 실제로 사용자가 실수를 저질러 마주칠 확률이 가장 높은 순간(오류 메시지)에
정작 "매매가"라는 단어가 사라지고 "취득가액"만 남는 것은 `docs/DESIGN_SYSTEM.md` "같은 개념은
폼·결과·오류 메시지 전체에서 한 용어로 통일한다" 원칙과 어긋난다. 계산 자체에는 영향이 없고
문맥상 이해 못 할 정도는 아니지만(라벨 옆에 이미 "취득가액"이 괄호로 병기돼 있어 완전히 낯선
단어는 아니다), 일관성 원칙을 명시적으로 위반한 구체적 사례라 **Medium**으로 판정한다.
(Optimizer 권고: `validation.ts`의 4개 메시지도 "매매가"를 주 용어로 통일하거나 최소한
"매매가(취득가액)"으로 병기한다.)

**Q4 (필수). 입력 최소화 — 등급: 문제없음.**

**Q5. 조정대상지역 자가 판단 안내 — 등급: Medium.**
`ADJUSTMENT_AREA_HELP_TEXT`는 "국토교통부 규제지역 지정 현황(molit.go.kr) 등 공식 안내에서
확인 시점 기준으로 직접 확인한 뒤 선택해 주세요"라고 안내하지만, `ui.tsx`를 확인한 결과 이
문구는 순수 텍스트(`<p>`)로만 렌더링되고 실제 `<a href="https://...">` 클릭 가능한 링크가
전혀 없다(`ui.tsx` 전체에서 `<a`/`href=`로 검색한 결과 카테고리 이동용 `<Link>` 1개뿐, 외부
URL 링크는 0개 — `wetax.go.kr`도 마찬가지). SPEC.md 자신이 "조정대상지역 여부를 잘못
판단하면 완전히 틀린 세율로 계산"된다고 경고한 항목치고는, 사용자가 "molit.go.kr"이라는
문자열을 직접 타이핑해 브라우저에 입력해야 하는 수준의 마찰이 있다. `housing-subscription-
score` 등 기존 계산기도 외부 링크를 텍스트로만 제공하는 동일한 관례가 있어 이 계산기만의
새로운 결함은 아니지만, 이 계산기는 오판정의 대가(SPEC.md 표현으로 "실제보다 낮거나 높은
세율을 자동으로 제시하는 사고")가 다른 계산기보다 훨씬 크므로 사이트 공통 관례를 그대로
따르는 것만으로는 충분하지 않다고 판단해 **Medium**으로 올린다. (Optimizer 권고: 최소한
molit.go.kr/wetax.go.kr을 실제 `<a target="_blank" rel="noopener">` 링크로 바꾼다.)

**Q6. 4구간 중 자기 위치 판단, 일시적 2주택·상속주택 안내 — 등급: Medium.**
`HOUSE_COUNT_CARD_HINTS`는 각 카드에 적용 세율을 짧게 보여줘 "몇 채인지" 자체를 고르는 데는
도움이 된다. 그러나 "일시적 2주택"(종전 주택 처분 예정)이나 "상속받은 주택도 채수에
포함되는지" 같은, SPEC.md 스스로 예상한 헷갈리는 케이스에 대한 안내는 `HOUSE_COUNT_HELP_TEXT`
(세대 합산 기준만 설명)에는 없고, 계산 완료 후에만 `NOT_REFLECTED_NOTICES`("일시적 2주택
특례... 이 계산기는 이 특례를 판정하지 않으므로 실제 세액이 낮을 수 있습니다")로 뒤늦게
드러난다. 실제 일시적 2주택자가 "지금 2채가 되니 2채를 선택"하고 결과를 받은 뒤 안내문을
읽지 않으면, 자신에게 유리한 특례가 있다는 사실 자체를 모르고 지나칠 수 있다. FAQ에도 관련
질문이 없다(FAQ 2번은 "왜 4단계인지"만 다루고 "일시적 2주택이면 어떻게 하나요"는 다루지
않는다). 계산 결과 자체는 SPEC.md가 허용한 범위(Should Have 미반영을 사후 고지)를 지켰으므로
Critical/High는 아니지만, 입력 시점에 힌트가 없어 실제로 놓치기 쉬운 시나리오라 **Medium**으로
판정한다. (Optimizer 권고: `HOUSE_COUNT_HELP_TEXT` 또는 2채 카드 힌트에 "종전 주택을 곧
처분할 예정이면 다른 특례가 적용될 수 있습니다 — 결과 하단 안내를 확인하세요" 한 줄을 추가.)

**Q7. 취득가액 단위 명확성 — 등급: Medium.**
입력은 원 단위 숫자만 받고(`inputMode="numeric"`, 콤마 실시간 표시), placeholder는
"예: 650,000,000"으로 자릿수 예시를 보여준다. 이는 `severance-pay`/`loan-interest-calculator`
등 이 사이트 전반의 기존 관례와 동일하며 이 계산기만의 새로운 결함은 아니다. 다만 이
계산기는 가격 구간(6억/9억)과 중과 배수(최대 12배)가 맞물려 있어, 자릿수 하나(0 하나)를
빠뜨리거나 더 입력하면 결과가 "그럴듯하지만 완전히 틀린" 금액으로 나올 위험이 다른
계산기보다 크다(예: 6억5천만원을 "65,000,000"으로 잘못 입력하면 자동으로 "low" 구간
표준세율 1%가 적용돼 에러 없이 정상적으로 보이는 결과가 나온다 — 사용자가 스스로 자릿수를
세어보지 않는 한 실수를 알아챌 방법이 없다). 콤마 표시 자체는 도움이 되지만, "약 6.5억원"
같은 한글 단위 실시간 환산 미리보기나 별도 확인 문구는 없다. 사이트 공통 패턴을 따랐다는
점에서 Critical한 새 결함은 아니되, 이 계산기의 구조적 특성(자릿수 오류의 대가가 큼)을
고려해 **Medium**으로 판정한다. (Optimizer 권고: 입력값 옆에 "약 6억 5,000만원"처럼 한글
단위로 환산한 실시간 보조 텍스트를 추가하면 사이트 공통 컴포넌트 신설 없이도 개선 가능.)

**Q8. 부가세(지방교육세·농특세) 설명 이해 가능성 — 등급: 문제없음.**
결과 화면에 "예상 총 납부액(취득세 + 지방교육세 + 농어촌특별세)"로 구성 세목을 제목에서부터
명시하고, "세목별 내역" 카드에서 3개 세목을 각각 금액과 함께 보여준다. FAQ 3번("농어촌특별세가
왜 0원으로 나오나요?")이 국민주택규모 비과세 기준을 설명하고, "계산 근거" SectionCard가
세목별 산식(취득세×10% 등)을 근거 법령과 함께 보여줘 "왜 세 가지가 합산되는지"를 층위별로
설명한다. 다만 "지방교육세·농어촌특별세가 애초에 왜 별도로 존재하는 세금인지"(제도 취지)에
대한 한 줄 설명은 소개 문단에도 FAQ에도 명시적으로 없다 — 사소한 개선 여지는 있으나 계산
결과를 이해하는 데는 지장이 없어 **문제없음**으로 판정한다.

**Q9. Should Have 미구현(생애최초 감면) 고지 — 등급: 문제없음.**
FORMULA.md "Should Have 승격 여부 판단"에서 생애최초 감면은 요건까지 확정됐지만 v1 Must
Have로 승격하지 않기로 명시적으로 결정됐다. FAQ 5번("생애최초 주택 구입 감면이
반영되나요?")이 "아니요, 이번 버전에는 반영되지 않습니다"라고 명확히 답하고, 결과 화면의
"이 결과가 반영하지 않는 것" 섹션에도 "생애최초 주택 구입... 각종 취득세 감면 — 이 결과는
어떤 감면도 반영하지 않은 금액입니다"라고 반복 고지한다. 있지도 않은 기능을 있는 것처럼
암시하는 문구는 없다. **문제없음.**

**Q10. "확인 필요" 항목 고지의 이해 용이성 — 등급: High.**
`policy.ts`의 `HOUSING_ACQUISITION_TAX_OPEN_QUESTIONS` 4개 문자열이 `content.ts`를 거쳐
`ui.tsx`의 "꼭 확인하세요" SectionCard 하위 목록에 **가공 없이 그대로** 렌더링된다. 실제
소스(`policy.ts` 173~176행)를 확인한 결과 다음과 같은 **내부 개발 프로세스 전용 용어가
최종 사용자 화면에 그대로 노출된다**:
- "...이번 세션에서 대화형으로 대조하지 못했습니다(**Calculation Auditor** 최우선 검증
  권고)." — "이번 세션", "대화형으로", "Calculation Auditor"는 이 프로젝트의 역할극/개발
  프로세스 용어(`.claude/agents/*.md`)이지 일반 사용자가 이해할 수 있는 세무 용어가 아니다.
  일반 사용자는 "이번 세션"이 무엇을 가리키는지 전혀 알 수 없고, "Calculation Auditor"라는
  생소한 영문 role 명이 세금 계산기 화면에 뜨는 것은 매우 부자연스럽다.
- "...1차 출처로 재확인하지 못해 **v1**에 반영하지 않았습니다." / "...**v1** 입력(취득가액·
  전용면적·조정대상지역·보유 주택 수)만으로는 판정할 수 없어 반영하지 않았습니다." — "v1"은
  이 사이트에 버전 개념 자체가 사용자에게 노출된 적이 없는 순수 내부 개발 버전 표기다.
  사용자는 "v1이 무엇의 몇 번째 버전인지" 알 방법이 없고, 애초에 이 계산기에 "v2"가 있다는
  인상을 주는 것도 부적절하다.
  이 3개 문구는 `ui.tsx` 483~498행(`LEGAL_DISCLAIMER_NOTICES` 아래 "아직 위택스 등과 직접
  대조해 확정하지 못한 사항" 하위 목록)에서 **계산이 성공할 때마다 항상** 렌더링되므로, 이
  계산기를 쓰는 사실상 모든 사용자가 이 문구를 보게 된다. 계산 자체는 틀리지 않았지만(Calculation
  Auditor PASS), 공개 소비자용 계산기 화면에 내부 워크플로 전문 용어("세션", "Calculation
  Auditor", "v1")가 그대로 노출되는 것은 (a) 사용자가 문장을 이해할 수 없게 만들고("오류
  메시지의 이해 용이성" 항목 정면 위반), (b) 계산기의 전문성·신뢰도를 해치며(이런 문구를 보면
  "이 사이트가 내부 테스트 중인 미완성 도구를 실수로 공개한 것 아닌가" 하는 인상을 줄 수
  있다), (c) 이 계산기에만 국한된 새로운 결함이다(다른 published 계산기의 고지 문구에는 이런
  내부 용어가 없음을 `severance-pay`/`loan-interest-calculator` 대조로 확인했다). 계산
  정확성 자체의 문제는 아니라 Critical은 아니지만, **모든 사용자가 매번 보게 되는 화면
  텍스트에 프로덕션 부적합한 내부 전문용어가 노출**되는 것은 UX 관점에서 **High**로 판정한다.
  (Optimizer 필수 수정: `policy.ts`의 `HOUSING_ACQUISITION_TAX_OPEN_QUESTIONS` 3개 문구에서
  "이번 세션", "대화형으로", "Calculation Auditor", "v1" 표현을 전부 제거하고 순수 사용자
  관점 문장으로 재작성한다 — 예: "세목별 10원 미만 절사(내림) 규칙은 위택스(wetax.go.kr)
  실제 계산 결과와 아직 직접 대조하지 못했습니다. 정확한 금액은 위택스 또는 관할 시·군·구청에서
  확인하세요." / "...이 계산기의 나머지 입력값만으로는 판정할 수 없어 반영하지 않았습니다."처럼
  "v1" 대신 "이 계산기"로 순화.)

**Q11. 모바일 카드 레이아웃 — 등급: 문제없음(레이아웃 관점, 실브라우저 테스트는 QA 영역).**
조정대상지역 2택 카드는 `grid-cols-2 max-w-xs`로 좁은 폭에서도 2열이 자연스럽고, 보유 주택
수 4택 카드는 `grid-cols-2 gap-2 sm:grid-cols-4`로 320px~390px 구간에서는 2열×2행으로
배치돼 카드 폭이 충분히 확보된다(예: 375px 폭 기준 카드 하나당 약 170px). 각 카드는
`py-3`(세로 12px 패딩)로 터치 영역도 여유 있다. 코드 리딩만으로는 실제 렌더링 시 줄바꿈이나
글자 잘림까지 확정할 수 없으므로 이 판단은 레이아웃 설계 수준에 한정하며, 실제 기기 확인은
QA 영역으로 넘긴다.

**Q12. 계산 근거 난이도 — 등급: 문제없음(다른 계산기 대비 일관된 수준).**
`formatting.ts`의 `buildTaxCalculationBreakdown`이 만드는 문장(예: "650,000,000원 ×
1.33% = 8,645,000원(절사 전) → 10원 미만 절사 → 8,645,000원")은 `severance-pay`의
`FormulaStep`(예: "기준임금 × 30일 × (재직일수 ÷ 365) = ...")과 동일한 수준의 상세도이며,
법령 조항을 "근거:" 레이블로 별도 표기해 본문 설명과 시각적으로 분리한 점도 동일한 패턴이다.
이 계산기가 특별히 더 어렵게 서술돼 있지는 않다 — 오히려 "적용 세율 근거" 문장

8%가 적용됩니다")을 breakdown 앞에 별도로 배치해 raw 수식을 보기 전에 먼저 일상어 요약을
읽게 한 것은 오히려 다른 계산기보다 친절한 배치다.

**Q13. 경계값 오류 메시지 — 등급: 문제없음.**

치환한다. `content.ts`의 문구 자체(도메인 표기 포함)는 전혀 바꾸지 않고, 렌더링 로직만 추가한

HELP_TEXT`), "이 결과가 반영하지 않는 것"(`NOT_REFLECTED_NOTICES`), "꼭 확인하세요"

지역 지정 현황 상세 URL)는 이번 세션에서 실제로 열람해 확인한 적이 없어, 검증되지 않은 딥링크를
새로 지어내는 대신 안전하게 각 기관의 공식 최상위 도메인으로 연결했다. FAQ 답변

보고서도 이 부분은 지적하지 않았다) — 공용 컴포넌트를 바꾸는 것은 이번 보고서 범위를 벗어나는
임의 기능 추가라고 판단해 보류했다.

### 4. [권고, Medium] 일시적 2주택·상속주택 안내를 입력 시점에도 배치 — 수정 완료

`content.ts`의 `HOUSE_COUNT_HELP_TEXT`(보유 주택 수 입력 바로 아래 helpText)에 두 문장을

2주택) 다른 세율이 적용될 수 있으니 결과 하단 안내를 확인하라"는 점. 계산 결과 이후에만 있던

### 5. [권고, Medium] 취득가액 자릿수 한글 단위 실시간 환산 — 수정 완료

사이트 내 다른 계산기를 먼저 확인했으나(`Grep`으로 "억"·"만원"·한글 단위 변환 함수 검색)
이런 패턴을 가진 기존 계산기가 없어 새 로컬 함수를 만들었다. `formatting.ts`에
`formatWonInKoreanUnits(value: number): string`을 추가했다 — 취득가액을 "6억 5,000만원"·
