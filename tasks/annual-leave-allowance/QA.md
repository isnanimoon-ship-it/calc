## 3. Optimizer 수정 사항 — 실제 화면 동작 확인

- **usedDays helpText 신규 문구**: "발생일수는 가장 최근 발생한 연차만 기준으로
  계산합니다(과거 발생분은 1년 내 미사용 시 소멸한 것으로 간주). 사용일수도 입사 후 누적
  총 사용일수가 아니라 이 최근 발생분 중 사용한 일수를 입력하세요..." — DOM에 실제로
  렌더링되어 있고 `aria-describedby`로 입력 필드와 연결됨을 확인.
- **새 정책 고지 문구("누적 총량 아님")**: 정책 고지 섹션 2번째 항목으로 실제 노출 확인(예제 7
  결과 화면 전체 텍스트로 캡처).
- **보조 정보 카드 `max-w-md`**: 1440px/768px 스크린샷에서 실제로 카드 폭이 제한되어 있음을
  시각적으로 확인(이전 라운드의 "불필요하게 넓게 늘어남" 문제 해소).
- **입사일 helpText(말일/윤년 안내)**: "말일(29~31일)이나 2월 29일에 입사한 경우에도 매달/매년
  마지막 날을 기준으로 자동 계산됩니다."가 입사일 입력 아래 실제 노출, `aria-describedby`로
  연결됨을 DOM에서 확인.
- **발생일수 중복 표시 안내**: `ordinaryDailyWage` 미입력 케이스(예제 15)에서 보조 정보의
  "연차 발생일수" 카드 아래에 "위 핵심 결과와 같은 값입니다." 문구가 실제로 노출되고,
  임금을 입력한 케이스(예제 5, 7, 16 등)에서는 이 문구가 나타나지 않음을 확인(조건부 렌더링
  정상 동작).
- **26→15 전환 강조 박스**: 예제 7(정확히 2년, `completedYears=2 <= 3`)에서 "1~2년차의
  26일에서 2년 이상 구간의 15일로 발생일수가 줄어든 것은 오류가 아닙니다 — ..."가 파란색
  강조 박스(`bg-primary-soft`/`text-primary`)로 "발생일수 산출" 단계 바로 아래에 실제
  노출됨을 확인. 4년차(completedYears=4, yearlyGrant=16) 이상에서는 이 강조 박스가 사라지는
  것도 별도로 확인해, "근속 2~3년차에만 좁게 타겟팅"이라는 설계 의도가 실제 코드와 일치함을
  검증했다.

## 6. 모바일/반응형 테스트 (320/375/390/768/1440px)

CDP `Emulation.setDeviceMetricsOverride`로 5개 뷰포트 전부에서 샘플 계산(예제 8, 최저임금
경고 포함) 결과 화면을 전구간 스크롤 캡처했다.

- **가로 스크롤**: 5개 뷰포트 전부 `scrollWidth === clientWidth`(320/375/390/768/1425 — 1440은
  스크롤바 폭 반영으로 1425 보고, 브라우저 정상 동작)로 가로 스크롤 없음 확인.
- **320px(최소 폭)**: 입력 필드 2×2 그룹이 1열로 자연스럽게 쌓이고, helpText 긴 문장(usedDays
  4문장)도 줄바꿈만 될 뿐 잘림(overflow)이나 겹침 없음. 최저임금 경고 카드, 26→15 강조 박스,
  정책 고지 문구 전부 폭에 맞게 줄바꿈되어 읽기 가능. 버튼 3개(계산하기/초기화/샘플)도 겹치지
  않고 줄바꿈됨. FAQ 아코디언 6개 항목 텍스트 잘림 없음.
- **375px/390px**: 320px와 동일한 안전한 레이아웃, 추가 문제 없음.
- **768px(태블릿)**: 입력 폼이 2열 그리드로 전환, 보조 정보 카드(발생일수/미사용일수)가
  `max-w-md` 제약으로 적절한 폭을 유지(Optimizer 수정 확인).
- **1440px(데스크톱)**: 전체 `max-w-6xl` 컨테이너 안에 입력 폼 2열, 보조 정보 카드가 폭
  제한으로 불필요하게 늘어나지 않음(1차 UX Critic이 지적한 문제가 실제로 해소됨을 스크린샷
  으로 재확인).
- **Mobile Critical Issue: 0건.**

## 7. 브라우저 테스트

- Chrome(Chromium 153, 최신 stable 계열) 단일 엔진으로 CDP 기반 테스트를 진행했다(지시받은
  안전 정책에 따라 Edge는 시도하지 않음). 사이트 전체가 Tailwind 표준 유틸리티와 표준 DOM
  API(`<input type="date">`, `Intl.NumberFormat`, `localStorage`)만 사용하므로 Chromium
  계열에서의 PASS가 이 사이트의 다른 계산기들과 동일한 신뢰 수준을 제공한다고 판단했다.
- 다크모드 토글(`aria-label="라이트/다크 모드 전환"`) 클릭 시 `<html>`에 `dark` 클래스가

## 9. 접근성

- **`aria-describedby`**: 4개 입력 필드 전부 helpText id와 항상 연결되고, 오류 발생 시 error id가
  뒤에 추가로 붙는 구조(`{help-id} {error-id}`)를 DOM에서 직접 확인.
- **`aria-invalid`**: 오류가 있는 필드에만 정확히 `"true"`로 설정되고, 정상 필드에는
  속성 자체가 없음(빈 문자열이 아님)을 확인.
- **`aria-live="polite"`**: 결과 영역이 이 속성으로 감싸여 있어 계산 완료 시 스크린리더에
  갱신이 전달됨을 구조로 확인(같은 페이지에 헤더의 빈 `aria-live` 영역이 하나 더 있어, 초기
  자동화 스크립트 작성 시 `querySelector`가 잘못된 요소를 먼저 찾는 함정이 있었다 — 실사용자
  스크린리더 경험에는 영향 없음. 아래 "발견 사항 Low"에 기록).
- **FAQ 아코디언**: 6개 버튼 전부 `aria-expanded`(초기 `"false"`)/`aria-controls`가 정상
  연결되고, 클릭 시 대상 패널이 `role="region"` + `aria-labelledby`(버튼 id 참조)로 정확히
  연결됨을 확인.
- **폼 라벨**: 4개 입력 전부 `<label htmlFor>`↔`id`가 정상 연결(별도 스크린리더 없이도
  `getElementById(label.getAttribute('for'))`로 매번 성공적으로 필드를 찾을 수 있었다는 것 자체가
  연결이 정확하다는 증거).
- **포커스 스타일**: `globals.css` 전역 `:focus-visible` 규칙을 이 계산기가 별도로 덮어쓰지
  않음(코드 확인, `ui.tsx`에 `outline` 관련 커스텀 스타일 없음).
