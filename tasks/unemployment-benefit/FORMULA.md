# FORMULA: 실업급여(구직급여) 계산기

## 재검토 이력 (Calculation Auditor Medium "공식 재검토 요청" 대응, 2026-09-02)
Calculation Auditor가 work24.go.kr(고용24) 라이브 모의계산 서버를 쿠키 세션 유지 curl로 직접 대조한 결과를 근거로, 이 문서가 "확인 필요"로 남겼던 두 항목의 재검토를 요청했다(tasks/unemployment-benefit/EVALUATION.md "Calculation Auditor" 2-a·2-c 참고). Builder는 이 문서(v1 잠정 정책, 구직급여일액 절사 후 곱셈)를 정확히 그대로 구현했으므로 **Builder 결함이 아니다** — docs/EVALUATION.md "역할 간 이견 조정" 규칙에 따라 Formula Analyst(본인)가 최종 권위로 재검토했다. 핵심 변경 사항:
1. **work24.go.kr(고용24) 공식 모의계산기와 직접 대조 성공.** Auditor가 세션 쿠키(HPSESSIONID)를 유지하는 curl로 실제 계산 엔드포인트(`retrieveNewMainCalcAjax.do`)를 호출해, 이 문서의 검증 예제 1·2·3·5·6에 대응하는 입력을 넣어 전부 Expected 값과 정확히 일치함을 확인했다. "공식 계산기 대조 미확보"였던 이 문서 최대의 약점이 해소됐다 — 아래 "이 문서의 신뢰도에 관한 중요한 사전 고지", "검증 예제", "여전히 남아있는 확인 필요 항목" 갱신 내용 참고.
2. **구직급여일액(`benefitDailyAmount`)의 원 단위 처리 정책을 "clamp 후 절사, 그 절사값으로 총액 계산"에서 "clamp까지만 적용한 완전정밀도 값을 그대로 총액 계산에 사용"으로 전환**했다(구 정책 폐기). `ave_sal=112001`(×0.6=67,200.6원, 소수 있음)을 실제 계산기에 두 차례(240일·210일 구간) 넣은 결과(`tot=16,128,144`, `14,112,126`)가 "절사 후 곱셈" 가설의 예측값(각각 `16,128,000`, `14,112,000`)을 반증하고 "완전정밀도 유지" 가설과 정확히 일치했다(EVALUATION.md 2-c). 아래 "정밀도/반올림 정책"에서 근거와 새 정책을 상세히 다룬다.
3. 기존 검증 예제 1~6은 `benefitDailyAmount`가 우연히 항상 정수였으므로(clamp 적중 또는 임금이 나누어떨어지도록 설계) 정책 변경에도 **기대값(Expected)은 전부 불변**이다. 정책 차이가 실제로 드러나는 신규 예제 7을 추가했다(Auditor의 라이브 대조 사례를 이 계산기의 입력 모델로 재구성, work24.go.kr 실제 대조로 확인됨).
4. `totalExpectedBenefit` 최종 단계의 원 단위 처리 방향(절사/올림/반올림)은 이번에도 라이브 서버로 직접 확인하지 못했다(두 실증 사례가 우연히 둘 다 정수로 떨어져 이 지점을 가려냈다) — "확인 필요"로 신규 등재하고, 잠정 정책(원 단위 절사)과 그 근거를 명시한다.
5. 2026년 상한액(68,100원) 출처를 korea.kr(대한민국 정책브리핑) 1차에 준하는 정부 출처로 격상했다(EVALUATION.md 2-d).

## 목적
고용보험법에 근거해, "비자발적 이직(또는 정당한 사유 있는 자진퇴사)으로 수급자격이 인정된다고 가정했을 때"의 소정급여일수, 구직급여일액(1일 지급액), 총 예상 지급액을 계산한다. SPEC.md의 설계상 핵심 결정(수급자격의 법적 판정은 하지 않고, "자격이 있다면 얼마인가"만 계산)을 그대로 따른다. **(v2 갱신, 추적성 메모)** SPEC.md v2는 이 전제를 사용자에게 알리는 방식을 "체크박스 게이팅(계산 전 확인 필수)"에서 "결과 화면에 항상 노출하는 고지 문구"로 바꾸고, 이직사유 유형 선택 입력도 함께 제거했다 — 둘 다 애초에 이 문서가 정의하는 계산 로직의 입력이 아니었던 UI 전용/참고용 필드였으므로, 이 변경은 아래 "공식"·"계산 순서"·소정급여일수 표·반올림 정책 등 실제 계산 공식에는 아무런 영향을 주지 않는다(무영향 확인됨). 세금 계산은 하지 않는다(구직급여는 비과세, 고용보험법 제38조의2).

## 이 문서의 신뢰도에 관한 중요한 사전 고지
severance-pay(퇴직금) FORMULA.md는 고용노동부(moel.go.kr)가 실제로 로드하는 클라이언트 계산 스크립트(`retire_cal.js`)를 curl로 직접 다운로드해 알고리즘 원문을 확인할 수 있었다. 이번 조사에서도 동일한 방법을 시도했다:
- **고용보험 모바일웹(eiac.ei.go.kr, 고용보험심사위원회 운영)**의 실업급여 모의계산 페이지(`https://eiac.ei.go.kr/ei/m/pf/MOW-PF-00-180-C.html`)를 curl로 직접 다운로드해 클라이언트 JS(`chk1()`, `calc1()`, `res1()` 등)를 읽었다. 이 페이지 자체는 **1차 출처(정부 기관 페이지의 실제 클라이언트 코드)**이며, 상한/하한액 등 정책 수치와 판정 로직의 큰 그림을 확인하는 데 유효하다(아래 각주에서 구체적으로 인용).
- 다만 이 페이지가 표시하는 **실제 최종 지급액 계산은 서버 API(`/ei/pf/calcResult.do`, `/ei/pf/calcAgeInfo.do`)가 담당**하며, 그 서버 로직 자체는 클라이언트 JS에 노출되지 않는다(moel.go.kr의 퇴직금 계산기와 구조가 다르다 — 퇴직금 계산기는 계산 자체가 클라이언트 JS 안에서 완결됐지만, 이 실업급여 모의계산기는 서버 호출형이다).
- 이 API를 curl로 직접 호출해 실제 계산 결과를 얻으려 시도했으나, `/ei/pf/*` 엔드포인트가 `https://www.work24.go.kr`로 302 리다이렉트되고 있어(2026-09-02 확인) **더 이상 살아있는 API가 아니다** — eiac.ei.go.kr는 work24.go.kr(고용24)로 기능이 통합/이전된 것으로 보이며, 남아있는 정적 페이지는 구버전 콘텐츠(상한액 66,000원·하한액 60,120원 등 2019~2025년 수치)를 그대로 보여주고 있어 **캐시된 구(舊) 페이지**로 판단된다.
- 후속으로 work24.go.kr의 실제 모의계산 페이지(`https://www.work24.go.kr/cm/c/f/1200/selecSimulateCalc.do`)도 확인했으나, 계산 로직이 전적으로 서버 사이드(폼 POST → 서버 렌더링)이고 다단계 페이지 네비게이션이 필요해, 이번 조사에서 허용된 시간 안에 실제 계산 결과 하나를 재현하지 못했다.
- **결론(최초 작성 시점)**: 법 조문·시행령·정부 기관 페이지에서 확인한 산정 "공식"과 2026년 수치(상한/하한액 등)의 신뢰도는 높지만(아래 "기준/출처" 참고, 대부분 2개 이상 독립 출처로 교차확인), **"공식 계산기가 실제로 출력한 최종 금액"과 1:1로 대조된 Golden Test 예제는 이 조사 시점에는 확보하지 못했다.** 당시에는 docs/CALCULATOR_RULES.md가 요구하는 "공식 계산기 예시값과 대조한 케이스 최소 2개"를 미충족 상태로 남겼다.
- **2026-09-02 갱신(해소됨)**: 위 한계는 Calculation Auditor가 후속 검증에서 해소했다. 쿠키 세션(HPSESSIONID)을 유지하는 curl로 실제 사용자 흐름(`selecSimulateCalc.do` → `selecSimulatePost.do` → `retrieveNewMainCalcAjax.do`)을 그대로 재현해, work24.go.kr 라이브 계산 서버 응답을 얻는 데 성공했다. 이 문서의 검증 예제 1·2·3·5·6에 대응하는 입력을 그 서버에 직접 넣어 Expected 값과 정확히 일치함을 확인했고(아래 "검증 예제" 참고), 소정급여일수 표의 모든 연도 경계(12/36/60/120개월)도 실제 서버 응답으로 스캔해 일치를 확인했다(EVALUATION.md 2-a·2-b). **docs/CALCULATOR_RULES.md "공식 계산기 예시값과 대조한 케이스 최소 2개" 요건은 5개 케이스로 충족됐다.** 이 대조 과정에서 "구직급여일액 원 단위 반올림" 정책 자체가 이 문서의 잠정 채택과 상충한다는 새 증거도 발견됐다 — 아래 "정밀도/반올림 정책" 참고. (다만 이 엔드포인트는 "간편모의계산·상용직" 탭으로 근로기간(개월)·월평균임금÷30을 입력받는 단순화된 추정 도구라, "3개월 임금총액÷baseDays" 그 자체의 정확성까지 확인해주지는 않는다 — EVALUATION.md 2-a 괄호 한계 고지 참고.)

## 입력값
| 변수명 | 설명 | 단위 | 허용 범위 |
|---|---|---|---|
| `birthDate` 또는 `ageAtLeave` (연령) | 이직일 현재 만 나이. 만 나이 기준(2023.6.28 시행 "만 나이 통일법" 및 eiac.ei.go.kr 공식 페이지의 "연령은 퇴사 당시의 만 나이입니다" 안내와 일치) | 세 (정수) | 필수. 15~100 정도의 상식적 범위(정확한 상한은 Architect/Builder 재량) |
| `leaveDate` (이직일) | 근로관계 종료일 | date | 필수 |
| `insuredPeriodDays` (고용보험 가입기간, 피보험기간) | 이직일 기준 누적 고용보험 가입기간. **이 계산기는 "가입 시작일~이직일" 또는 "총 가입기간 직접 입력" 중 하나로 받되, 최종적으로 이 하나의 값이 아래 두 곳(① 180일 요건 판정, ② 소정급여일수 표 조회)에 함께 쓰인다 — 아래 "예외 > 피보험기간과 피보험단위기간의 개념 차이" 절 필독** | 일 (내부 계산은 일 단위, UI는 년/개월 등으로 보여줘도 됨) | 필수. 0 이상 |
| `isUltraShortTimeWorker` (초단시간근로자 여부) | 이직 당시 4주 평균 주 소정근로시간이 15시간 미만이었는지. `true`면 180일 요건의 기준기간이 18개월이 아니라 24개월로 늘어난다(이 계산기는 기준기간 계산 자체를 요구하지 않으므로 참고용 안내 문구에만 사용 — 아래 "예외" 참고) | boolean | 선택, 기본값 `false` |
| `isDisabled` (장애인 여부) | 「장애인고용촉진 및 직업재활법」 제2조에 따른 장애인으로 등록되어 있는지. 소정급여일수 표에서 "50세 이상" 그룹과 동일하게 취급됨 | boolean | 선택, 기본값 `false` |
| `wage3m` (이직 전 3개월 임금총액) | 근로기준법 제2조제1항제6호 평균임금 산정용 임금총액. severance-pay와 동일하게 "3개월 임금총액 직접 입력"의 간편 입력을 우선한다 | 원 | 필수. 0 이상 정수 |

v1은 severance-pay와 마찬가지로 평균임금 산정 제외기간(수습·휴업·출산휴가 등) 입력을 받지 않는다. 따라서 "평균임금 산정기간 총일수"는 `leaveDate` 이전 3개월의 순수 달력일수(89~92일)이며, severance-pay FORMULA.md의 `baseDays` 산출 로직(3개월 전 날짜 계산 + 월말 clamp 규칙)을 그대로 재사용할 것을 권고한다(같은 근로기준법 제2조제1항제6호 정의를 쓰므로 로직을 공유해도 무방하다 — 단, Architect가 실제 코드를 공유할지 별도 구현할지는 이 문서의 권한 밖).

## 출력값
| 변수명 | 설명 | 단위 |
|---|---|---|
| `eligibleByInsuredPeriod` | 피보험기간 180일 이상 요건 충족 여부(근사치 판정 — 아래 "예외" 참고) | boolean |
| `ageBandForTable` | 소정급여일수 표 조회에 쓰인 연령 구간("50세 미만" 또는 "50세 이상 및 장애인") | string |
| `insuredPeriodBand` | 소정급여일수 표 조회에 쓰인 가입기간 구간(1년 미만/1~3년/3~5년/5~10년/10년 이상) | string |
| `prescribedBenefitDays` (소정급여일수) | 별표1 조회 결과 | 일 |
| `averageDailyWage` (1일 평균임금) | `wage3m ÷ baseDays` | 원/일 |
| `baseBenefitDailyAmount` (상한/하한 적용 전 구직급여일액) | `averageDailyWage × 60%` | 원/일 |
| `minBenefitDailyAmount` (최저구직급여일액, 연도별 데이터) | 해당 연도 최저임금 × 8시간 × 80% | 원/일 |
| `maxBenefitDailyAmount` (구직급여일액 상한액, 연도별 데이터) | 해당 연도 기초일액 상한 × 60% | 원/일 |
| `benefitDailyAmount` (구직급여일액, 최종) | `clamp(baseBenefitDailyAmount, minBenefitDailyAmount, maxBenefitDailyAmount)`. **계산에는 완전정밀도로 사용, 화면 표시 시에만 별도로 원 단위 정리(절사, 확인 필요)** — 아래 "정밀도/반올림 정책" 참고 | 원/일 |
| `totalExpectedBenefit` (총 예상 지급액) | `benefitDailyAmount(완전정밀도) × prescribedBenefitDays`, **최종적으로만** 원 단위 정리(절사, 확인 필요) | 원 |
| `waitingPeriodDays` (대기기간, 안내용 상수) | 7 | 일 |

## 공식

```
1. baseDays              = calendarDays(leaveDate - 3개월, leaveDate)         (일, 89~92 — severance-pay와 동일 규칙, 월말 clamp 적용)
2. averageDailyWage      = wage3m / baseDays                                  (원/일, 반올림 없이 유지)
3. baseBenefitDailyAmount= averageDailyWage × 0.6                             (원/일, 고용보험법 제46조제1항제1호)
4. minBenefitDailyAmount = minWageHourly(해당연도) × 8 × 0.8                  (원/일, 고용보험법 제46조제1항제2호·제2항 — "최저구직급여일액". 1일 소정근로시간은 8시간으로 가정 — 아래 "예외" 참고)
5. maxBenefitDailyAmount = baseWageDailyCap(해당연도) × 0.6                   (원/일, 고용보험법 제45조제5항·시행령 제68조 — "기초일액의 상한액"에 60%를 곱한 값. 연도별 데이터에는 이미 곱해진 값을 그대로 저장해도 되고, 상한 기초일액을 저장하고 계산 시점에 ×0.6 해도 됨 — 아래 "연도별 데이터 파일 스키마" 참고)
6. benefitDailyAmount    = min(max(baseBenefitDailyAmount, minBenefitDailyAmount), maxBenefitDailyAmount)   (원 단위로 절사하지 않음 — 완전정밀도 유지, work24.go.kr 실증 확인. "정밀도/반올림 정책" 참고)
7. ageBandForTable       = isDisabled OR (age >= 50) ? "50세 이상 및 장애인" : "50세 미만"
8. insuredPeriodBand     = lookupBand(insuredPeriodDays)   (아래 "소정급여일수 표" 참고, 5개 구간)
9. prescribedBenefitDays = table[ageBandForTable][insuredPeriodBand]          (고용보험법 제50조제1항, 별표1)
10. totalExpectedBenefit = benefitDailyAmount(6단계의 완전정밀도 값) × prescribedBenefitDays, 최종적으로만 원 단위 절사(확인 필요, "정밀도/반올림 정책" 참고)
```

**주의(Builder용)**: 6단계 `benefitDailyAmount`는 화면에 "1일 구직급여일액"으로 표시할 때만 별도로 원 단위 절사한 값을 만들고, 그 절사값을 10단계 계산에 재사용해서는 안 된다 — `roundBenefitDailyAmount()`처럼 곱셈 이전에 절사를 끼워 넣는 구조는 이제 공식과 상충한다(work24.go.kr 실증으로 반증됨). 절사는 10단계 결과(`totalExpectedBenefit`) 자체에 대해서만, 그리고 표시용 `benefitDailyAmount`에 대해서만 각각 독립적으로 적용한다.

지급요건 미충족(`insuredPeriodDays < 180`)이면 1~10단계를 수행하지 않고 "수급자격 요건 미충족" 안내만 반환한다.

## 계산 순서
1. **비자발적 이직 전제(고지 전용, v2 갱신)** — v1에 있던 체크박스 게이팅 입력은 SPEC.md v2에서 제거됐다. 이 단계는 더 이상 계산을 막는 조건이 아니며, 항상 2단계로 진행한다. "비자발적 이직으로 인정된다고 가정한 금액"이라는 전제는 결과 화면의 고지 문구로만 안내한다(SPEC.md "설계상 핵심 결정" v2 참고). 아래 2~12단계 계산 로직 자체는 이 변경으로 달라지지 않는다.
2. **피보험기간 180일 요건 판정** — `insuredPeriodDays >= 180`이 아니면 "수급자격 요건(피보험단위기간 180일 이상) 미충족" 안내만 반환하고 중단한다. 이 판정이 근사치임을 결과 화면에 안내할 것을 권고한다(아래 "예외" 참고).
3. **평균임금 산정기간 총일수 산출** — severance-pay FORMULA.md의 `baseDays` 로직과 동일(3개월 전 날짜 + 월말 clamp).
4. **1일 평균임금 산출** — `wage3m / baseDays`.
5. **상한/하한 적용 전 구직급여일액 산출** — `averageDailyWage × 0.6`.
6. **해당 연도 상한액·하한액 조회** — `/src/data/rates-{year}.json`(연도는 `leaveDate`의 연도)에서 `baseWageDailyCap`, `minWageHourly` 등을 읽어 `maxBenefitDailyAmount`, `minBenefitDailyAmount`를 계산(또는 미리 계산된 값을 그대로 읽음).
7. **구직급여일액 확정** — 5단계 값을 6단계의 하한~상한 범위로 clamp. **이 값을 원 단위로 절사하지 않고 완전정밀도로 유지한다**(work24.go.kr 실증 확인, "정밀도/반올림 정책" 참고) — 이후 11단계 계산에는 이 완전정밀도 값을 그대로 쓴다.
8. **연령 구간 판정** — `isDisabled`가 `true`이거나 이직일 현재 만 나이가 50세 이상이면 "50세 이상 및 장애인" 구간, 아니면 "50세 미만" 구간.
9. **가입기간 구간 판정** — `insuredPeriodDays`를 년 단위로 환산해(365일 = 1년 기준 또는 정확한 달력 anniversary 기준 — Architect/Builder가 일관되게 선택) 5개 구간 중 하나에 배정.
10. **소정급여일수 조회** — 8·9단계 결과로 표에서 값을 가져온다.
11. **총 예상 지급액 산출** — `benefitDailyAmount(완전정밀도) × prescribedBenefitDays`를 계산한 뒤, **이 결과에 대해서만** 원 단위 절사를 적용해 확정한다(확인 필요, "정밀도/반올림 정책" 참고).
12. **결과 화면 breakdown 구성** — SPEC.md Must Have "결과 화면 breakdown"에 따라 4~11단계의 중간값을 모두 노출한다. 단, "1일 구직급여일액"으로 화면에 보여주는 값은 7단계의 완전정밀도 값이 아니라 **별도로 원 단위 절사한 표시용 값**을 쓴다(확인 필요, "정밀도/반올림 정책" 참고) — 이 표시용 절사값은 11단계 계산에 재사용하지 않는다.

## 단위
- 날짜: `date`(YYYY-MM-DD), severance-pay와 동일하게 UTC 자정 고정 등으로 timezone 이동 문제 방지.
- 금액: 원 단위. 근로기준법상 평균임금 자체는 원 미만("전") 단위까지 정밀도가 요구될 수 있으나(severance-pay 참고), 이 계산기의 최종 출력(구직급여일액, 총 지급액)은 정부 공식 발표(상한 68,100원, 하한 66,048원 등)가 모두 원 단위 정수로 고시되므로, **아래 "정밀도/반올림 정책"에서 정한 지점을 제외하고는 원 미만 정밀도를 유지할 실익이 크지 않다.**
- 가입기간: 일(day) 단위로 내부 보관, 표시는 년/개월 등으로 변환 가능.
- 비율(60%, 80%): 무차원 소수(0.6, 0.8)로 저장하되, 표시는 %.

## 정밀도 / 반올림 정책

**2026-09-02 갱신**: 아래 항목 중 "구직급여일액 원 단위 처리"는 Calculation Auditor가 work24.go.kr 라이브 계산 서버를 실제로 대조해 **확인됨(구 정책 반증·폐기)**으로 갱신됐다(EVALUATION.md 2-c, Medium "공식 재검토 요청" 대응). 나머지 항목(1일 평균임금 반올림 방향, 최종 총액의 원 단위 처리 방향, "1년" 경계)은 이번에도 직접 확인하지 못해 "확인 필요"로 유지한다 — **절대 추정하지 않는다.**

- **1일 평균임금(`averageDailyWage`, 3~4단계)**: severance-pay와 동일한 근로기준법 제2조제1항제6호 정의를 쓰므로, severance-pay FORMULA.md가 채택한 정책(중간에 반올림하지 않고 다음 단계로 넘김, 필요시 moel.go.kr 방식처럼 표시 시점에만 전 단위 올림)을 참고할 수 있다. 다만 moel.go.kr 퇴직금 계산기의 반올림 정책(전 단위 올림 후 재사용)이 **구직급여에도 그대로 적용된다는 증거는 이번 조사에서 찾지 못했다** — 서로 다른 법 조항(근로자퇴직급여 보장법 vs 고용보험법)이고 계산 주체(moel.go.kr vs work24.go.kr/고용24)도 다르다. **확인 필요.**

- **구직급여일액(`benefitDailyAmount`, 5~7단계) 원 단위 처리 — work24.go.kr 실제 계산기 대조로 확인됨(구 정책 폐기)**:
  Calculation Auditor가 work24.go.kr 라이브 계산 서버(`retrieveNewMainCalcAjax.do`)에 소수점이 남는 입력(`ave_sal=112001` → `baseBenefitDailyAmount=112,001×0.6=67,200.6원`, 상한·하한 clamp 범위 내)을 두 차례(소정급여일수 240일·210일 구간) 넣어 확인한 결과, 서버는 **`benefitDailyAmount`를 원 단위로 절사(또는 어떤 방식으로든 중간 반올림)하지 않고, clamp까지만 적용한 완전정밀도 값을 그대로 `prescribedBenefitDays`와 곱하는 최종 총액 계산까지 이어간다**(EVALUATION.md 2-c):
  - `67,200.6 × 240 = 16,128,144원` — 실제 응답과 정확히 일치. "절사 후 곱셈"이었다면 `67,200 × 240 = 16,128,000원`이어야 했다(144원 차이).
  - 같은 `ave_sal`로 `prd=61`(210일 구간)도 재확인: `67,200.6 × 210 = 14,112,126원` — 실제 응답과 정확히 일치. 절사였다면 `14,112,000원`(126원 차이). 두 케이스 모두 "절사 후 곱셈" 가설을 반증한다.

  **v1 확정 정책(구 정책 폐기)**: 이전 문서가 "확인 전까지의 잠정 정책"으로 채택했던 "clamp 후 원 단위 절사, 그 절사값으로 총액 계산"(`Math.floor` 후 곱셈)은 **실증 근거로 반증됐으므로 폐기한다.** 대신:
  1. **계산용 `benefitDailyAmount`** = `clamp(baseBenefitDailyAmount, minBenefitDailyAmount, maxBenefitDailyAmount)`를 **원 단위로 절사하지 않고 완전정밀도(부동소수점 또는 유리수)로 유지**한 채, 10단계(`totalExpectedBenefit` 계산)에 그대로 사용한다. `minBenefitDailyAmount`·`maxBenefitDailyAmount` 자체는 정수이므로, clamp가 적중한 경우(예제 1·2·5)는 이 구분이 결과에 영향을 주지 않는다 — 영향은 clamp가 적중하지 않는 좁은 구간에서만 발생한다(EVALUATION.md 2-c "영향 범위·심각도" 참고, 최대 약 269원).
  2. **표시용 `benefitDailyAmount`**(결과 화면에 "1일 구직급여일액"으로 보여주는 값)는 계산용과 분리한다 — 화면에는 원 단위로 정리한 값을 보여주되, 그 정리된 값을 다시 총액 계산에 재사용하지 않는다. severance-pay가 moel.go.kr 방식으로 "표시용=계산용"을 통일한 것과는 **정반대의 결정**이다 — 두 계산기의 실제 라이브 서버 동작이 서로 다르다는 것이 각각 확인됐으므로, "모든 계산기를 동일한 방식으로 통일해야 한다"는 원칙은 이 문서가 채택한 적이 없다. 각자 확인된 증거를 따른 결과일 뿐이다.
  3. **표시용 반올림의 구체적 방향(버림/올림/반올림)은 여전히 확인하지 못했다.** work24.go.kr 응답 필드는 `day`(소정급여일수)·`tot`(총액)뿐이고 "1일 지급액" 필드 자체가 노출되지 않는다(EVALUATION.md 2-a). 참고 정황(간접, 종전과 동일): eiac.ei.go.kr 자영업자 계산 로직의 `Math.floor` 사용 사례. **v1 잠정 정책(표시용에 한함)**: 사용자에게 불리하지 않은 방향(정부가 실제 지급할 금액보다 화면에 더 크게 보여주지 않는 방향)을 택해 **원 단위 절사(버림)**를 유지한다 — 단, 이 표시값은 이제 총액 계산에 전혀 쓰이지 않으므로, 화면에 절사된 값이 보이더라도 `totalExpectedBenefit`은 항상 완전정밀도 `benefitDailyAmount` 기반으로 정확히 계산된다는 점이 구 정책과의 핵심 차이다. **확인 필요(표시용 방향만).**

- **총 예상 지급액(`totalExpectedBenefit`, 10~11단계) 최종 원 단위 처리 — 신규 확인 필요 항목**:
  구직급여일액이 이제 완전정밀도로 유지되므로, `totalExpectedBenefit = benefitDailyAmount × prescribedBenefitDays`도 일반적으로 정수가 아닐 수 있다(`averageDailyWage`가 나누어떨어지지 않고 clamp도 적용되지 않는 경우 — 실사용자 다수가 겪을 수 있는 흔한 경우다). Auditor가 확보한 두 실증 사례(`16,128,144원`, `14,112,126원`)는 **우연히 둘 다 정수**로 떨어졌다(`prescribedBenefitDays`가 모두 30의 배수이고 `benefitRate=0.6=3/5`이므로, `ave_sal`이 정수일 때 `baseBenefitDailyAmount`의 소수부가 정확히 0.6인 경우는 배수 관계상 정수가 되는 우연이다 — 반면 실사용자의 `averageDailyWage=wage3m/baseDays`는 나누어떨어지지 않는 반복소수인 경우가 훨씬 흔하다). 즉 **이번 실증은 "중간에 절사하지 않는다"는 사실만 확정했을 뿐, "최종 총액 자체를 원 단위로 어떻게 정리하는지"는 여전히 직접 확인하지 못했다.**
  **v1 잠정 정책(확인 전까지)**: 구직급여일액 표시용 정책과 동일한 원칙(사용자에게 불리하지 않은 방향 = 정부가 실제 지급할 금액보다 화면에 더 크게 보여주지 않는 방향)을 적용해 **`totalExpectedBenefit`도 최종적으로 원 단위 절사(버림)**를 잠정 채택한다. Builder는 이 최종 절사를 `benefitDailyAmount`(완전정밀도) × `prescribedBenefitDays`를 계산한 직후, 화면에 표시하기 직전 단 한 번만 적용해야 하며, 그 사이 어떤 중간 단계에서도 반올림해서는 안 된다(`roundBenefitDailyAmount`처럼 곱셈 이전에 적용되는 함수를 만들지 말 것 — 곱셈 이후 총액에만 적용하는 함수로 재설계해야 한다). **확인 필요.**

- **가입기간 → 구간 판정 시 "1년" 경계**: 정확히 365일(또는 윤년 포함 실제 만 1년 anniversary)에 도달하는 시점을 "1년"으로 볼지, 365일 고정으로 볼지 확인되지 않았다. severance-pay가 나이·근속연수 판정에 쓴 "달력상 실제 경과일" 방식(생일/기념일 도래 여부로 판정)을 일관되게 적용할 것을 권고한다. **확인 필요(실무상 영향은 경계값 근처 극소수 사용자에게만 미미하게 발생).**

## 예외

### 피보험기간과 피보험단위기간의 개념 차이 — 이 계산기의 핵심 단순화 지점
고용보험법은 서로 다른 목적에 쓰이는 **두 가지 "기간" 개념**을 구분한다:
1. **피보험단위기간**(제41조): 이직일 이전 18개월(초단시간근로자는 24개월) 동안 **"보수 지급의 기초가 된 날"만 합산**한 값. 소정근로일 + 유급휴일(주휴일 등)만 포함되고, 무급 휴무일은 빠진다. **180일 이상 요건(제40조)의 판정 기준이 되는 값이 바로 이것이다.**
2. **피보험기간**(제50조제3항): 수급자격과 관련된 **적용 사업에 고용된 기간**(대체로 달력상 재직 기간에 가깝고, 3년 이내 재취업 시 종전 사업장 기간을 합산할 수 있음 — 단, 그 종전 기간으로 이미 구직급여를 받았으면 제외). **소정급여일수 표(별표1) 조회 기준이 되는 값이 바로 이것이다.**

즉 법적으로는 "180일 요건 판정"과 "표 조회"에 **서로 다른 두 숫자**를 써야 한다. 주 5일 근무 + 주휴일 유급인 일반적인 근로자라면 피보험단위기간은 달력일수의 약 6/7 수준에 그치므로(무급 토요일 등이 빠짐), **달력상 재직기간을 그대로 180일 요건에 대입하면 실제보다 자격을 관대하게(즉 "된다"고) 오판할 위험**이 있다(달력일수는 항상 피보험단위기간보다 크거나 같으므로).

**v1 결정(단순화)**: SPEC.md가 "정확한 입력 필드 설계는 이 단계에서 확정하지 않는다"고 위임했고, 이 계산기는 애초에 "참고용 추정 도구"임을 전제로 설계됐다(SPEC.md "목적"). 이에 따라 v1은 **단일한 `insuredPeriodDays`(달력 기준 가입기간)를 입력받아 ① 180일 요건 판정과 ② 표 조회에 동일하게 사용**한다. 이 단순화가 **근거 없는 임의 결정이 아님을 아래 증거로 뒷받침한다**: 정부 기관(고용보험심사위원회)이 실제로 운영했던 실업급여 모의계산기 자체도 동일한 단순화를 쓴다 — `https://eiac.ei.go.kr/ei/m/pf/MOW-PF-00-180-C.html`의 클라이언트 코드(`chk1()` 함수, 확인일 2026-09-02)를 보면, 근무 시작일·종료일의 **달력일수 차이**(`diff = (t_date - f_date)/86400000 + 1`)가 180 미만이면 곧바로 `"근무한 기간(피보험단위기간)이 180일 미만이므로 수급자격이 없습니다"`라는 경고를 띄운다 — 즉 정부 공식 모의계산기 스스로 "달력일수"를 "피보험단위기간"의 근사치로 취급하고 있다. 다만 이 계산기가 여전히 "모의계산"(참고용)이라는 한계는 이 계산기와 동일하다.

**결과 화면에 반드시 반영해야 할 안내**: "가입기간은 실제 근무일·유급휴일만 계산되는 '피보험단위기간'과 다를 수 있으며, 무급 결근·휴직 기간이 많았다면 실제 요건 충족 여부가 이 계산과 달라질 수 있습니다. 정확한 판정은 고용센터에서 확인하세요." — SPEC.md의 기존 정책 고지 문구와 자연스럽게 결합 가능.

### 피보험단위기간 요건 미충족
`insuredPeriodDays < 180` → 금액 계산 없이 "수급자격 요건(피보험단위기간 180일 이상) 미충족" 안내만 반환(SPEC.md Must Have "입력 오류/극단값 방어"에 이미 명시된 요구사항과 일치). 근거: 고용보험법 제40조제1항제1호.

### 초단시간근로자의 기준기간 연장(v1은 계산에 반영하지 않음, 안내만)
`isUltraShortTimeWorker=true`인 경우 180일 요건을 판정하는 "기준기간" 자체가 18개월이 아니라 24개월로 늘어난다(제40조제2항). 이 계산기는 기준기간(18/24개월) 자체를 계산하지 않고 `insuredPeriodDays`(총 가입기간)만 받으므로, 이 필드는 **결과 화면에 "귀하는 초단시간근로자에 해당하여 피보험단위기간 산정 기준기간이 18개월이 아닌 24개월로 연장됩니다"라는 안내 문구를 띄우는 용도로만** 쓰고, 계산 로직 자체(180일 임계값)는 바꾸지 않는다.

### 대기기간(7일)
금액 계산에 영향을 주지 않는 안내용 상수. 고용보험법 제49조. 최종 이직 당시 건설일용근로자였던 경우는 대기기간 없이 신고일부터 지급되는 예외가 있으나(제49조 단서), SPEC.md Should Have "대기기간 안내"는 텍스트 안내 수준이므로 v1은 이 예외를 별도로 계산하지 않고 "일반적으로 7일"이라고만 안내한다(건설일용근로자 예외는 "확인 필요" 겸 v2 후보로 남긴다).

### 입력 오류
`insuredPeriodDays < 0`, `wage3m < 0`, 필수값 미입력, `age`가 상식 범위 밖(예: 음수, 200세) → 계산 진행하지 않고 오류 안내.

### 구직급여일액이 상한·하한 사이에 정확히 걸치는 경계값
`baseBenefitDailyAmount == minBenefitDailyAmount` 또는 `== maxBenefitDailyAmount`인 경우는 clamp 연산상 자연스럽게 처리되며 별도 분기가 필요 없다(`min(max(x, lo), hi)`는 `x == lo` 또는 `x == hi`에서도 안전).

### 예제 1 — 상한액 적용 (50세 이상, 10년 이상 가입, 고액 연봉)

- `averageDailyWage = 30,000,000 / 92 = 326,086.9565...원`
- `baseBenefitDailyAmount = 326,086.9565... × 0.6 = 195,652.17...원` → 2026년 상한액(68,100원)을 크게 초과 → **상한 적용**
