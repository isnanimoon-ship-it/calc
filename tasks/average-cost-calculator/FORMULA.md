# FORMULA: 평단가(물타기) 계산기

## 목적
보유 수량·보유 평균 매입단가(평단가)와 추가 매수 수량·추가 매수 단가를 입력받아, 매수 후
새 평단가·총 보유수량·총 투자원금을 계산한다. SPEC.md가 명시한 대로 이 계산기는 **정책형
계산기가 아니다** — 산식은 순수 가중평균(weighted average)이며 법령·고시·정부 발표 수치를
전혀 참조하지 않는다. 따라서 이 문서의 초점은 "기준 연도가 맞는가"가 아니라 **표준 산식(가중
평균)이 정확히 서술·유도되었는가, 그리고 코인 대응 소수 정밀도가 반올림 오차 없이
안전한가**이다(`tasks/loan-interest-calculator/FORMULA.md`와 동일한 초점 전환 — 그 문서가
채택한 "공식 검증 결과 요약" 형식을 그대로 따른다).

이 계산기가 다른 금융 계산기(대출 이자, 4대보험 등)와 근본적으로 다른 지점은 **수량 자체가
소수**인 입력이 흔하다는 점이다(코인). 대부분의 금융 계산기는 "금액(원)만 소수 위험이
있고 수량(주, 개월, 회차 등)은 항상 정수"였지만, 이 계산기는 수량·단가 양쪽 모두 소수를
허용해야 하고, 그 둘을 곱한 뒤(비용) 다시 합을 수량으로 나누는(평균) 연산 체인 전체에서
부동소수점 오차가 발생할 수 있다. 이 문서의 "정밀도 / 반올림 정책" 절이 이 문제를 정면으로
다룬다.

## 공식 검증 결과 요약 (Formula Gate)
- **핵심 산식(가중평균) = SPEC.md가 제시한 식과 정확히 일치: PASS.** 2개의 독립 도메인(서로
  다른 사이트) 출처(brainc.me, Plus27/makeit27.com)가 제시한 구체적 숫자 예시 3건 모두
  이 계산기의 산식으로 정확히 재현됨(아래 "검증 예제" 1~3, 확인일 2026-09-12).
- **가중평균의 기본 성질(결과값이 두 입력 단가 사이에 위치, 극한에서 한쪽 값에 수렴)**:
  **PASS** — 대수적 증명으로 자기완결적(아래 "공식" 절 "가중평균의 범위 증명" 참고)이며,
  검증 예제 8·9로 극한 성질까지 구체적 숫자로 재확인.
  - 이 성질의 응용 확인: omnicalculator.com의 6회 분할매수(AMD) 실제 예시를 "기존 보유
    5건 + 신규 매수 1건" 2그룹으로 재구성해도 전체 6건을 한 번에 평균낸 결과와 정확히
    일치함을 확인(확인일 2026-09-12, 아래 "2그룹 축약이 다회차 평균과 동일함" 참고) —
    이는 SPEC.md가 "여러 회차 매수 이력"을 Could Have로 미루면서도 "기존 보유를 이미 여러
    번 매수해 형성된 평단가로 보고 그 위에 1건을 더하는 구조로 확장 가능하다"고 주장한
    근거를 외부 자료로 뒷받침한다.
- **목표 평단가 역산 공식(Should Have)과 유효성 조건 `Pc < Pt < P1`**: **PASS** — 정방향
  공식에서 대수적으로 직접 유도해 SPEC.md 제시 식과 정확히 일치함을 확인, 유효성 조건도
  부호 분석으로 재확인(아래 "공식 ②" 참고). 별도 외부 출처 대조는 불필요(교과서적 대수
  유도이므로 자기완결적 — loan-interest-calculator의 연금현재가치식 유도와 동일한 성격).
- **코인 대응 수량·단가 소수 자릿수 상한 8자리**: **근거 확보(정책적 사실 확인, 법령 아님)**
  — 국내 거래소 빗썸이 2024-02 "주문 수량 소수 자릿수를 4자리 → 8자리로 확대"한 공지를
  확인(확인일 2026-09-12, 아래 "기준/출처" 참고), 업비트도 BTC를 8자리까지 거래 지원.
  다만 이는 "거래소가 매매 주문에 쓰는 자릿수"이지 "이 계산기가 반드시 이 자릿수를 써야
  한다는 법적 근거"는 아니다 — 엔지니어링/제품 판단으로 채택했음을 명확히 한다.
- **1건 발견 — 외부 계산기 사이트의 산술 오류(참고용으로도 채택하지 않음)**: calctools.co.kr의
  "주식 평단가 계산기" 예시 표(1차 100주@60,000원, 2차 100주@50,000원, 3차 200주@45,000원,
  합계 400주 20,000,000원)가 최종 결과를 "평단 51,250원"으로 표시하고 있으나, 이 사이트
  자신의 공식(총 매수 금액 ÷ 총 보유 수량)대로 계산해도 `20,000,000 ÷ 400 = 50,000원`이며
  `51,250원`이 아니다(확인일 2026-09-12, WebFetch 2회 재확인 — 동일한 표·동일한 오답을
  재현해 일회성 스크래핑 오류가 아님을 확인). **이 사이트의 최종 결과값은 Golden Test
  참고 자료로 채택하지 않는다** — 대신 이 표의 1·2행 부분합(100주+100주 → 55,000원)은
  자체 재계산으로 검산 가능하고 다른 독립 출처와도 산식 구조가 일치해 "산식 자체가
  가중평균이라는 사실"을 보강하는 정황 자료로만 인용한다(Golden Test로는 채택하지 않음).
  `docs/CALCULATOR_RULES.md` "정확성 원칙"에 따라 확인되지 않은/틀린 수치를 그대로 베끼지
  않기 위한 조치다.

## 입력값
| 변수명 | 설명 | 단위 | 허용 범위 |
|---|---|---|---|
| `holdingQty` (보유 수량) | 현재 보유 중인 주식/코인 수량 | 주 또는 개(무차원) | 필수. 0 초과, 소수 8자리까지(초과분은 반올림하지 않고 입력 단계에서 검증 오류), 상한 1,000,000,000,000,000(10^15) |
| `holdingPrice` (보유 평단가) | 현재 평균 매입단가 | 원 | 필수. 0 초과, 소수 8자리까지, 상한 10,000,000,000원(100억원) |
| `additionalQty` (추가 매수 수량) | 이번에 추가로 매수하려는 수량 | 주 또는 개 | 필수. 0 초과, 소수 8자리까지, 상한 10^15 |
| `additionalPrice` (추가 매수 단가) | 매수 예정 가격(보통 현재가) | 원 | 필수. 0 초과, 소수 8자리까지, 상한 100억원 |
| (Should Have) `targetPrice` (목표 평단가) | 역산 시 도달하고자 하는 평단가 | 원 | 목표 평단가 역산 기능에서만 사용. 0 초과, `additionalPrice`와 조합해 유효성 조건 검사(아래 "공식 ②") |

### 입력 상한/하한 근거
법령·고시로 강제되는 값이 아니므로(정책형 아님), Formula Analyst가 아래 근거로 v1 기준값을
정한다 — Architect/Builder가 UX상 필요하면 조정할 수 있으나 변경 시 근거를 남길 것을
권장한다(loan-interest-calculator와 동일한 관례).

- **수량 하한(0 초과)과 최소 표현 단위(10^-8)**: 코인은 수량 자체가 소수이며, 국내 거래소
  빗썸이 2024-02 "주문 수량 소수 자릿수 4자리 → 8자리" 확대 공지를 낸 사실(확인일
  2026-09-12), 업비트가 BTC를 8자리까지 거래 지원하는 사실(WebSearch로 정황 확인, 1차
  출처 미확보 — 아래 "확인 필요" 참고)로 볼 때, 개인 사용자가 실제로 입력할 가능성이 있는
  가장 세밀한 수량 단위는 소수 8자리(1억분의 1) 수준이다. 이보다 더 세밀한 자릿수(예: 이더리움
  최소단위 wei는 18자리)까지 지원할 실익은 "계산기를 몰라도 쓸 수 있어야 한다"는 제품 목표
  대비 입력 UX 복잡도만 키운다고 판단해 8자리로 캡한다.
- **수량 상한(10^15, 1천조)**: 법정 근거가 아니라 UX 방어값이다(loan-interest-calculator의
  "100억원" 상한과 같은 성격의 판단). 주식은 발행주식총수가 아무리 많아도(국내 시가총액
  최상위 종목도 수십억 주 수준) 개인 보유수량이 조 단위를 넘는 경우가 사실상 없으나, 코인은
  일부 대형 밈코인의 총발행량이 수백조 개 수준으로 알려져 있어(예: 시바이누류 토큰) 정수
  보유량 자체가 조 단위를 넘는 사례가 실제로 존재한다. 10^15는 이런 극단적 코인 보유량까지
  넉넉히 포괄하면서, 아래 "정밀도/반올림 정책"에서 서술할 BigInt 고정소수점 연산이 안전하게
  처리 가능한 범위이기도 하다(정확한 계산이 가능함을 검증 예제 10에서 확인).
- **단가 상한(100억원)**: 전 세계에서 가장 비싼 단일 주식으로 알려진 버크셔 해서웨이 클래스A
  (BRK.A)가 2026-09-10 기준 주당 약 761,245달러(원화 환산 약 10.3억~10.7억원, 환율
  1,350~1,400원/달러 가정)에 거래된 사실을 확인했다(WebSearch, 확인일 2026-09-12).
  100억원은 이 실제 최고가 종목 대비 약 10배의 여유를 두어, 향후 환율 변동이나 이보다 비싼
  종목이 등장해도 안전하게 포괄한다. `loan-interest-calculator`의 원금 상한(100억원)과 같은
  자릿수를 채택해 이 사이트 금융 계산기 간 입력 상한 규모를 통일하는 부수적 이점도 있다.
- **단가 하한(0 초과)과 최소 표현 단위(10^-8원)**: 저가 알트코인은 1원 미만의 소수 원 단위
  가격으로 거래되는 경우가 흔하다. 수량과 동일하게 8자리까지 허용해 이런 케이스를 정상
  처리한다 — 이 자릿수 선택은 수량과 달리 특정 거래소 공지로 직접 확인한 사실은 아니며(수량
  쪽 8자리 근거를 대칭적으로 적용한 엔지니어링 판단), 이렇게 명시적으로 구분해 둔다.
- **목표 평단가(`targetPrice`, Should Have)**: 0 초과라는 형식 조건 외에 별도 상·하한을 두지
  않는다 — 유효성은 상·하한이 아니라 "공식 ②"의 부호 조건(`additionalPrice < targetPrice <
  holdingPrice`)으로 판정한다.

## 공식

### 공식 ① 정방향 — 매수 후 새 평단가(가중평균)
```
새 평단가 = (보유수량 × 보유평단가 + 추가매수수량 × 추가매수단가) ÷ (보유수량 + 추가매수수량)
총 보유수량 = 보유수량 + 추가매수수량
총 투자원금 = 보유수량 × 보유평단가 + 추가매수수량 × 추가매수단가
           (= 새 평단가 × 총 보유수량, 완전정밀도에서는 항상 정확히 성립 — 표시 단계
             반올림으로 인한 근소한 불일치 가능성은 아래 "정밀도/반올림 정책" 참고)
```
`Q1=보유수량, P1=보유평단가, Q2=추가매수수량, Pc=추가매수단가`로 표기하면
`새 평단가 = (Q1·P1 + Q2·Pc) / (Q1+Q2)` — 이는 "가중치가 각 수량인 두 값의 가중평균"의
정의 그 자체이며, 별도의 재무수학적 유도가 필요 없는 산술적 정의다(대출 이자 계산기의
연금현재가치식처럼 복잡한 유도 과정이 없다 — 이 계산기의 검증 부담은 "산식이 맞는가"가
아니라 "정의를 코드로 옮길 때 정밀도를 잃지 않는가"에 있다).

#### 가중평균의 범위 증명 (완료 기준 불변식의 수학적 근거)
`Q1, Q2 > 0`(SPEC.md가 두 수량 모두 "0보다 큰 값"을 필수로 요구하므로 항상 성립)일 때,
```
새평단가 − Pc = (Q1·P1 + Q2·Pc)/(Q1+Q2) − Pc = Q1·(P1−Pc) / (Q1+Q2)
P1 − 새평단가 = P1 − (Q1·P1 + Q2·Pc)/(Q1+Q2) = Q2·(P1−Pc) / (Q1+Q2)
```
두 식 모두 우변의 부호가 `(P1−Pc)`의 부호와 같다(계수 `Q1/(Q1+Q2)`, `Q2/(Q1+Q2)`가 항상
양수이므로). 따라서:
- `Pc < P1`(물타기)이면 두 식 모두 양수 → `Pc < 새평단가 < P1` (엄격한 하락, `Q1,Q2>0`이므로
  등호 없음).
- `Pc > P1`(불타기)이면 두 식 모두 음수 → `P1 < 새평단가 < Pc` (엄격한 상승).
- `Pc = P1`이면 두 식 모두 0 → `새평단가 = P1 = Pc` (변동없음, 정확히 성립 — 반올림과 무관한
  대수적 항등식).

이 증명은 SPEC.md "완료 기준"이 요구하는 불변식(새 평단가가 항상 `min(P1,Pc)`와 `max(P1,Pc)`
사이에 있음, 방향별 부등식 성립)을 대수적으로 100% 확정한다. 외부 출처 대조가 필요 없는
자기완결적 증명이다.

#### 극한 성질(수렴)
위 식에서 `Q2/(Q1+Q2) → 0`(추가수량이 보유수량 대비 무시할 만큼 작을 때) → `새평단가 → P1`.
`Q1/(Q1+Q2) → 0`(추가수량이 보유수량을 압도할 때) → `새평단가 → Pc`. 검증 예제 8·9에서
구체적 숫자로 재확인한다.

#### 2그룹 축약이 다회차 평균과 동일함 (외부 자료 대조)
omnicalculator.com의 Stock Average Calculator 예시(AMD 주식 6회 분할매수, 1주씩 매수단가
$85/$84/$83/$75/$77/$75.5, 결과 평균단가 $79.92, WebFetch 확인일 2026-09-12)를 이용해
"여러 회차를 2그룹(기존 보유 vs 신규 매수)으로 축약해도 결과가 같다"는 성질을 검증했다:
```
1~5회차를 "기존 보유"로 묶으면: 평균 = (85+84+83+75+77)/5 = 404/5 = 80.8, 수량 5주
6회차를 "추가 매수"로 두면: 수량 1주, 단가 75.5
2그룹 가중평균 = (5×80.8 + 1×75.5) / (5+1) = (404+75.5)/6 = 479.5/6 = 79.91666... ≈ 79.92
```
6회를 한 번에 평균낸 원래 계산(사이트가 제시한 79.92)과 정확히 일치한다. 이는 대수적으로도
당연한 결과(가중평균의 결합법칙 — 부분집합의 가중평균을 다시 그 부분집합의 총수량으로
가중평균 내도 전체 가중평균과 같다)이지만, 외부 자료의 실제 숫자로 재확인해 SPEC.md가
"여러 회차 매수 이력"을 Could Have로 미루면서 "기존 보유 + 신규 매수 1건 구조로 나중에
확장 가능하다"고 주장한 근거를 뒷받침한다.

### 공식 ② 목표 평단가 역산 (Should Have)
**유도**: 목표 평단가를 `Pt`라 하면, 추가매수수량 `x`를 구하는 문제는 다음 방정식을 `x`에
대해 푸는 것과 같다.
```
(Q1·P1 + x·Pc) / (Q1+x) = Pt
⇒ Q1·P1 + x·Pc = Pt·Q1 + Pt·x
⇒ Q1·(P1 − Pt) = x·(Pt − Pc)
⇒ x = Q1·(P1 − Pt) / (Pt − Pc)
```
SPEC.md가 제시한 식(`추가수량 = 보유수량 × (보유평단가 − 목표평단가) / (목표평단가 −
추가매수단가)`)과 정확히 일치함을 확인했다.

**유효성 조건(부호 분석)**: `Q1 > 0`이므로 `x`의 부호는 `(P1−Pt)`와 `(Pt−Pc)` 두 항의 부호
조합에 좌우된다. 사용자가 원하는 것은 "평단가를 **낮추는**" 시나리오(`Pt < P1`)이므로
`(P1−Pt) > 0`이고, 이때 `x > 0`이려면 `(Pt−Pc) > 0`, 즉 `Pc < Pt`가 필요하다. 두 조건을
합치면 SPEC.md가 제시한 유효성 조건
```
추가매수단가(Pc) < 목표평단가(Pt) < 보유평단가(P1)
```
와 정확히 일치한다. 검증 예제 11(라운드트립)에서 구체적 숫자로 재확인한다.

**대칭 branch(참고, v1 UI 범위 아님)**: 부호 분석상 `Pc > Pt > P1`(목표를 오히려 **높이는**
시나리오)도 수학적으로는 `x>0`인 유효한 해를 갖는다(불타기 목표). SPEC.md의 Should Have
설명과 유효성 조건은 "낮추기" 시나리오만 명시하므로 v1 UI는 이 대칭 케이스를 다루지 않는다 —
다만 공식 자체는 이 branch에서도 동일하게 성립하므로, 훗날 이 기능을 확장할 때 새 유도가
필요 없다는 점만 기록해 둔다.

**무효 조건**: 위 두 부등식 중 하나라도 깨지면(`Pt ≥ P1` 이면서 `Pc < Pt` 이거나, `Pt ≤ Pc`
이거나) `x ≤ 0`이 산출되어 무의미하다. 구체적 케이스는 아래 "예외" 절 참고.

## 계산 순서

### 정방향(Must Have)
1. 4개 입력값(`holdingQty`, `holdingPrice`, `additionalQty`, `additionalPrice`) 검증 —
   하나라도 누락·형식 오류·범위 초과면 계산 중단.
2. 입력 문자열을 각각 정수부·소수부로 분리하고, 소수부를 8자리로 우측 0-패딩한 뒤 BigInt
   정수로 변환한다(`qtyScaled_i = round(값 × 10^8)`를 문자열 파싱으로 직접 구성 —
   `parseFloat` 경유 없이. 아래 "정밀도/반올림 정책" 참고).
3. `costScaled_i(1e-16원 단위) = qtyScaled_i × priceScaled_i` (BigInt 곱셈, 완전정밀도).
4. `totalCostScaled = costScaled_1 + costScaled_2`, `totalQtyScaled = qtyScaled_1 +
   qtyScaled_2` (BigInt 덧셈, 완전정밀도).
5. `priceResultDecimals = clamp(max(decimalPlaces(holdingPrice), decimalPlaces
   (additionalPrice)), 0, 8)`, `qtyResultDecimals = clamp(max(decimalPlaces(holdingQty),
   decimalPlaces(additionalQty)), 0, 8)` 산출.
6. `새평단가` = `totalCostScaled / (totalQtyScaled × 10^8)`를 `priceResultDecimals` 자리로
   사사오입해 확정(BigInt 나눗셈 + 나머지 기반 반올림, 아래 "정밀도/반올림 정책" 알고리즘
   참고). `총 투자원금` = `totalCostScaled / 10^16`을 동일한 `priceResultDecimals` 자리로
   **독립적으로** 사사오입해 확정(새평단가에서 역산하지 않음).
7. `총 보유수량` = `totalQtyScaled / 10^8`을 `qtyResultDecimals` 자리로 표시(스케일이
   정수합이므로 반올림 손실 없이 정확히 표현 가능 — 반올림 아님, 자릿수 맞춤일 뿐).
8. `direction`은 **입력값 자체**(`additionalPrice` vs `holdingPrice`, 스케일된 정수로 정확히
   비교)로 판정한다 — 반올림된 `새평단가`와 `holdingPrice`를 비교하지 않는다(아래 "변동
   없음 표시 모순 방지 규칙" 참고).
9. `priceChangeAmount`(완전정밀도) = `새평단가(완전정밀도) − holdingPrice`를
   `priceResultDecimals` 자리로 반올림해 표시. 반올림 결과가 0이면서 `direction ≠
   "변동없음"`이면 "모순 방지 규칙" 적용.

### 역방향(Should Have)
1. `holdingQty`, `holdingPrice`, `additionalPrice`, `targetPrice` 검증.
2. 유효성 조건(`additionalPrice < targetPrice < holdingPrice`) 확인 — 위배 시 계산하지 않고
   구체적 사유 안내(아래 "예외" 참고).
3. `x = holdingQty × (holdingPrice − targetPrice) / (targetPrice − additionalPrice)`를
   완전정밀도로 계산한 뒤 `qtyResultDecimals` 자리로 반올림.
4. (권장) 정방향 공식에 `x`를 재대입해 결과가 `targetPrice`와 일치하는지 자체 검산 로직을
   두면 반올림 경계에서의 근소한 오차를 사용자에게 "약 목표평단가" 식으로 안내할 수 있다
   (구현 세부는 Builder 재량).

## 단위
- 수량(`holdingQty`, `additionalQty`, `totalQty`, `requiredAdditionalQty`): 무차원(주 또는
  개), 최대 소수 8자리.
- 금액(`holdingPrice`, `additionalPrice`, `newAveragePrice`, `totalCost`,
  `priceChangeAmount`, `targetPrice`): 원(KRW), 최대 소수 8자리(정수 원이 아니라 소수 원까지
  허용하는 것이 이 계산기의 특수성 — "단위" 절에서 명시적으로 강조).
- `priceChangeRate`: 무차원(%), 표시는 소수 둘째 자리 권장(Builder/Architect 재량, 계산
  자체는 완전정밀도 나눗셈 후 표시 직전 반올림).

## 정밀도 / 반올림 정책

### 핵심 위험: "수량도 소수, 단가도 소수"인 곱셈·나눗셈 체인
다른 금융 계산기(대출 이자, 4대보험 등)는 금액만 소수 위험이 있고 수량·개월수 등은 항상
정수였다. 이 계산기는 `수량(소수) × 단가(소수)`를 곱해 비용을 만들고, 그 합을
`수량(소수)`으로 나눠 평균을 낸다 — 두 단계 모두에서 이진 부동소수점(JS `number`)의 대표적
문제(`0.1 + 0.2 !== 0.3`)가 개입할 여지가 있다. 예를 들어 `holdingQty=0.1`,
`additionalQty=0.2`인 입력에서 `totalQty = holdingQty + additionalQty`를 그대로 `Number`
덧셈으로 계산하면 `0.30000000000000004`가 나온다 — 이 오차 자체는 8자리 반올림 표시에서는
가려지지만, 그 오염된 값을 **나눗셈의 분모**로 그대로 쓰면 최종 `새평단가`에 미세한 상대오차가
전파된다. SPEC.md "오류와 예외 처리" 절이 "부동소수점 오차나 반올림 오류 없이 검증·계산되어야
한다"고 명시적으로 요구하므로, 이 계산기는 아래 방식으로 이 위험을 원천 차단한다.

### 권장 방식: BigInt 고정소수점 스케일링 (Architect 참고용, 강제 아님)
`docs/ARCHITECTURE.md` "숫자 정밀도 전략"은 Number/정수 스케일링/BigInt/decimal.js·big.js 중
선택을 Architect 재량으로 위임한다. Formula Analyst로서 아래와 같이 **BigInt 고정소수점
스케일링을 1순위로 권장**하며, 그 근거와 구체적 알고리즘을 남긴다(loan-interest-calculator가
"구현 시 숫자 표현 권장(강제 아님)"으로 남긴 것과 같은 성격의 권고).

- **왜 일반 `Number`를 그대로 쓰지 않는가**: 위 "핵심 위험"에서 보였듯 수량 덧셈 단계부터
  이미 오차가 발생할 수 있고, 이 계산기는 loan-interest-calculator(정수 금액만 다룸)나
  four-major-insurance(정수 분수 연산으로 요율을 처리)와 달리 **입력값 자체가 이미 임의
  정밀도 소수**라 "정수 분수 연산"으로 우회할 수 없다.
- **왜 decimal.js/big.js 같은 임의정밀도 라이브러리가 아니라 BigInt를 권장하는가**: 이
  계산기가 다루는 소수 자릿수 상한은 (제품 결정으로) 8자리로 **고정**되어 있고, 연산 횟수도
  곱셈 2회·덧셈 2회·나눗셈 1~2회로 매우 적다(대출 이자 계산기의 480회 반복과 대조적). 고정
  자릿수·적은 연산 횟수라는 조건에서는 "정수부+소수부를 8자리로 정규화해 BigInt로 변환 →
  BigInt 산술 → 표시 직전 1회 나머지 기반 반올림"만으로 임의정밀도 라이브러리와 동일한
  안전성을 얻을 수 있어, 새 의존성을 추가하지 않는 쪽(`docs/ARCHITECTURE.md` "모든 계산기에
  무조건 무거운 decimal 라이브러리를 쓰지 않는다")이 더 낫다고 판단한다. 단, 이후 요구사항이
  바뀌어 자릿수 상한이 가변적이어야 한다면 big.js/decimal.js가 더 유연한 대안이 될 수 있다는
  점은 남겨 둔다(Architect가 최종 결정).
- **문자열 기반 스케일링(핵심)**: `parseFloat`/`Number()`로 먼저 파싱한 뒤 `× 10^8`을 하면
  그 파싱·곱셈 과정 자체에서 이미 부동소수점 오차가 재도입될 수 있다. 반드시 **입력 문자열을
  정수부/소수부로 직접 분리해 소수부를 8자리로 0-패딩한 뒤 문자열을 이어붙여 `BigInt()`로
  변환**해야 한다(예: `"0.5"` → 정수부 `"0"` + 소수부 `"5"` → 8자리 패딩 `"50000000"` →
  `BigInt("050000000")=50000000`). 이렇게 하면 파싱 단계에서부터 부동소수점이 전혀 개입하지
  않는다.
- **연산 전체를 BigInt로 수행**: 곱셈(비용 계산)·덧셈(합산)은 BigInt 연산이라 완전정밀도로
  정확하다. 유일하게 반올림이 필요한 지점은 **나눗셈(평균 계산) 단 한 곳**이며, 그마저도
  "표시 직전 1회만" 수행한다(`docs/CALCULATOR_RULES.md` "반올림 정책" — 중간 계산 단계에서
  임의로 반올림하지 않는다는 원칙과 완벽히 부합).
- **나머지 기반 사사오입 알고리즘**: BigInt 나눗셈(`/`)은 항상 내림(버림)이므로, 별도로
  나머지를 보고 반올림 여부를 결정해야 한다.
  ```
  function divRoundHalfUp(numerator: bigint, denominator: bigint): bigint {
    const quotient = numerator / denominator;
    const remainder = numerator % denominator;
    // 나머지×2 ≥ 분모이면 올림 (사사오입, 분모가 항상 양수라는 전제 — 이 계산기는
    // 수량·단가 모두 0 초과만 허용하므로 분모가 음수가 되는 경우가 없다)
    return remainder * 2n >= denominator ? quotient + 1n : quotient;
  }
  ```
  이 알고리즘으로 아래 "정확히 .5" 검증 예제(검증 예제 10)의 반올림 방향을 결정론적으로
  고정한다.

### 반올림 방법: 사사오입(반올림, round-half-up)
이 계산기는 대출 이자 계산기처럼 법적 강제나 실사례 대조가 필요한 영역이 아니라 순수 산술
도구이므로, 이 사이트의 다른 비정책형 금융 계산기(loan-interest-calculator)가 채택한 것과
동일하게 **사사오입을 기본 정책으로 채택**한다. 은행권의 "예금 이자 원단위 절사" 같은 특정
업권 관행이 이 계산기(개인 투자자용 평단가 계산)에 적용된다는 근거는 확인하지 못했다 —
확인 필요로 남기지 않고, 애초에 그런 업권 관행이 적용될 이유가 없는 순수 시뮬레이션 도구임을
명시한다.

### 반올림 시점 — 표시 단계에서 각 출력값을 독립적으로 1회만
`새평단가`·`총 투자원금`은 각각 완전정밀도 BigInt 값에서 **독립적으로** 1회만 반올림한다.
한쪽의 반올림된 값을 다른 쪽 계산에 재사용하지 않는다(예: `총 투자원금`을 `새평단가(반올림)
× 총보유수량`으로 역산하지 않는다). 이로 인해 **`새평단가(표시) × 총보유수량(표시)`이
`총투자원금(표시)`과 최소 표시 단위 미만에서 근소하게 다를 수 있다** — 이는 버그가 아니라
"각 출력이 자신의 완전정밀도 원본에 가장 가깝게 반올림된 결과"라는 정책의 자연스러운 결과다
(loan-interest-calculator가 "마지막 회차 상환액이 다른 회차와 근소하게 다를 수 있다"고 고지한
것과 같은 성격 — 화면에 "반올림으로 인해 항목 간 합계가 표시 단위에서 근소하게 다를 수
있습니다" 고지 문구를 두는 것을 권장한다, UX 문구 확정은 Architect/UX 재량).

### 표시 소수 자릿수 규칙
- `priceResultDecimals = clamp(max(decimalPlaces(holdingPrice), decimalPlaces
  (additionalPrice)), 0, 8)` — `새평단가`·`총투자원금`·`priceChangeAmount`에 공통 적용.
  두 입력 단가가 모두 정수(0자리)면 결과도 정수 원으로 표시된다(주식 시나리오의 직관과 일치).
  하나라도 소수라면(저가 코인) 결과도 그만큼의 자릿수를 유지해 "0원"으로 뭉개지는 것을
  방지한다.
- `qtyResultDecimals = clamp(max(decimalPlaces(holdingQty), decimalPlaces(additionalQty)),
  0, 8)` — `총보유수량`에 적용. 합산은 항상 정확하므로(BigInt 정수합) 반올림 손실이 없다.

### 변동 없음 표시 vs 반올림 표시값 간 모순 방지 규칙
**문제 상황**: 보유수량이 추가수량 대비 압도적으로 크면, 추가매수단가가 보유평단가와
**정확히는 다름에도** 새평단가의 반올림된 표시값이 보유평단가와 우연히 같아 보일 수 있다(검증
예제 7 참고). 이때 `direction`은 "하락"(또는 "상승")인데 화면에 표시되는 두 숫자는 동일해
보여 사용자에게 모순처럼 느껴질 수 있다.

**규칙**:
1. `direction`(하락/상승/변동없음) 판정은 **항상 반올림 이전의 정확한 입력값**
   (`additionalPrice` vs `holdingPrice`, BigInt 스케일 정수로 정확히 비교)으로만 한다 —
   반올림된 `새평단가`와 `holdingPrice`를 비교해서 판정하지 않는다. 따라서 `direction`이
   "변동없음"이 되는 경우는 오직 `additionalPrice`가 `holdingPrice`와 **정확히** 같을 때뿐이다.
2. `priceChangeAmount`(표시)를 `priceResultDecimals` 자리로 반올림한 결과가 `0`이면서
   `direction ≠ "변동없음"`인 경우(위 문제 상황), UI는 이를 "변동없음"으로 바꿔 표시하지
   않는다 — `direction`이 가리키는 "하락"/"상승" 라벨은 그대로 유지하되, "표시 자릿수
   기준으로는 변동액이 0으로 반올림될 만큼 미세합니다" 같은 보조 설명을 함께 노출해 라벨과
   숫자 "0"이 동시에 보여도 모순처럼 읽히지 않게 한다(정확한 문구는 UX Critic/Builder 재량,
   이 "라벨을 임의로 변동없음으로 바꾸지 않는다"는 규칙 자체는 필수).
3. `priceChangeRate`도 동일 원칙 — 반올림 결과가 "0.00%"로 보이더라도 `direction`이
   "변동없음"이 아니면 방향 표시를 함께 유지한다.

### `holdingQty`, `holdingPrice`의 정밀도는 그대로 신뢰한다
사용자가 입력한 "보유수량"·"보유평단가"는 이미 그 자체로 이전의 여러 매수를 종합한 결과값
(가중평균의 결과)일 수 있다. 이 계산기는 그 입력값을 완전정밀도로 신뢰하고 추가로 반올림하지
않는다(입력값을 재반올림하면 사용자가 실제로 보유한 값과 미세하게 달라져 "계산 근거" 대조
시 혼란을 줄 수 있다).

## 예외

### 정방향 계산
- **4개 필수 입력값 중 하나라도 누락/형식 오류(음수, 0 이하, 숫자가 아닌 값, 빈 값)**:
  계산하지 않고 해당 필드 오류 표시.
- **소수 자릿수 상한(8자리) 초과 입력**: 계산 전 검증 단계에서 차단하고 오류 표시(자동으로
  반올림·절사해 계산에 사용하지 않는다 — 사용자가 의도한 정밀도와 다른 값으로 조용히
  계산되는 것을 방지).
- **입력 상한 초과**(수량 10^15 초과, 단가 100억원 초과): 계산하지 않고 오류 표시.
- **매우 작은 값(예: 수량 0.00000001)**: 오류가 아니라 정상 경로 — 검증 예제 6에서 확인.
- **`additionalPrice = holdingPrice`(변동 없음)**: 오류가 아니라 정상 결과 케이스(검증
  예제 4).
- **`additionalPrice ≠ holdingPrice`이지만 반올림 표시값이 우연히 같아 보이는 경우**: 오류가
  아니라 "변동 없음 표시 모순 방지 규칙"에 따라 정상 처리(검증 예제 7).

### 역방향 계산(Should Have)
- **`targetPrice = holdingPrice`(이미 목표 달성)**: 공식상 `x=0` — 오류가 아니라 "이미 목표
  평단가에 도달해 있어 추가 매수가 필요 없습니다"로 안내(검증 예제 12).
- **`targetPrice > holdingPrice`(목표가 현재 평단보다 높음)이면서 `additionalPrice <
  holdingPrice`(낮은 가격에 사려는 입력)인 경우**: 산식상 `x<0` — "추가매수단가보다 낮은
  가격에 사지 않는 한 평단가를 목표보다 낮게 유지하면서 동시에 그 위로 올릴 수 없습니다"류의
  모순 안내(수학적으로 낮은 가격 매수는 평단가를 낮추는 방향으로만 작동하므로, 그보다 높은
  목표는 애초에 이 매수로 도달 불가능).
- **`targetPrice ≤ additionalPrice`(목표가 추가매수단가 이하)**: 산식상 `x≤0` 또는 분모 0 —
  "그 가격으로는 아무리 많이 매수해도 목표에 도달할 수 없습니다(추가매수단가에 점근할 뿐
  도달하지 못합니다)"로 안내(검증 예제 13). `targetPrice = additionalPrice`인 극한 경계는
  분모가 정확히 0이 되어 수학적으로 정의되지 않음(무한대) — 반드시 나눗셈 실행 전에 별도
  분기로 차단해야 한다(0으로 나누기 방지, `Builder`가 반드시 처리해야 할 안전장치).
- **`targetPrice`가 유효 구간(`additionalPrice < targetPrice < holdingPrice`) 밖의 형식
  오류(음수, 0 이하 등)**: 정방향과 동일하게 계산 자체를 중단하고 필드 오류 표시.

## 검증 예제 (Golden Test 후보 — 정방향 10개 + Should Have 3개)

### 예제 1 — 물타기 기본 (외부 출처 대조 ①)
- Input: `holdingQty=10, holdingPrice=10000, additionalQty=10, additionalPrice=5000`
- 계산: `(10×10,000 + 10×5,000)/(10+10) = 150,000/20 = 7,500`
- Expected: `newAveragePrice=7,500원`, `totalQty=20`, `totalCost=150,000원`, `direction=하락`.
- 출처: brainc.me "주식 평단가 계산법, 물타기 평균단가 구하기" — "매입금액은 10만원에
  5만원을 더해 15만원, 수량은 20주가 된다. 평단가는 15만원을 20주로 나눈 7500원"(WebFetch
  확인, 확인일 2026-09-12). **PASS(독립 출처와 정확히 일치)**.

### 예제 2 — 불타기 기본 (외부 출처 대조 ②, 예제 1과 동일 출처)
- Input: `holdingQty=10, holdingPrice=10000, additionalQty=10, additionalPrice=15000`
- 계산: `(10×10,000 + 10×15,000)/20 = 250,000/20 = 12,500`
- Expected: `newAveragePrice=12,500원`, `totalQty=20`, `totalCost=250,000원`, `direction=상승`.
- 출처: brainc.me, 같은 페이지의 두 번째 예시 — "매입금액은 25만원, 수량은 20주가 되어
  평단가는 1만 2500원으로 올라간다"(WebFetch 확인, 확인일 2026-09-12). **PASS**. 이 계산기의
  핵심 요구사항인 "불타기 방향도 오류로 취급하지 않고 정확히 계산"을 외부 자료로 확인.

### 예제 3 — 수량이 다른 정수 케이스 (외부 출처 대조 ③, 다른 도메인)
- Input: `holdingQty=10, holdingPrice=10000, additionalQty=15, additionalPrice=8000`
- 계산: `(10×10,000 + 15×8,000)/(10+15) = (100,000+120,000)/25 = 220,000/25 = 8,800`
- Expected: `newAveragePrice=8,800원`, `totalQty=25`, `totalCost=220,000원`, `direction=하락`.
- 출처: Plus27(plus.makeit27.com) "코인 주식 평단(평균단가) 계산기" — "(100,000원 +
  120,000원) ÷ (10주 + 15주) = 220,000원 ÷ 25주 = 8,800원"(WebFetch 확인, 확인일
  2026-09-12). **PASS**. 예제 1·2와 다른 도메인의 출처로, 수량이 서로 다른 경우까지
  독립적으로 재확인.

### 예제 4 — 변동 없음 경계값 (자체 산출, 대수적 항등식)
- Input: `holdingQty=10, holdingPrice=10000, additionalQty=5, additionalPrice=10000`
- 계산: `(10×10,000+5×10,000)/15 = 150,000/15 = 10,000`
- Expected: `newAveragePrice=10,000원`, `direction=변동없음`. `additionalPrice=holdingPrice`인
  한 수량이 얼마든 항상 정확히 성립(위 "가중평균의 범위 증명" 참고, 외부 대조 불필요한
  항등식).

### 예제 5 — 코인 소수 수량, 정확히 나누어떨어지는 케이스 (자체 산출)
- Input: `holdingQty=0.5, holdingPrice=52340000, additionalQty=0.25,
  additionalPrice=41150000` (BTC 시나리오 가정)
- 계산: `cost1=0.5×52,340,000=26,170,000`, `cost2=0.25×41,150,000=10,287,500`,
  `totalCost=36,457,500`, `totalQty=0.75`, `새평단가=36,457,500/0.75=48,610,000`(정확히
  나누어떨어짐 — `36,457,500×4/3=145,830,000/3=48,610,000`).
- Expected: `newAveragePrice=48,610,000원`, `totalQty=0.75`, `totalCost=36,457,500원`,
  `direction=하락`. `priceResultDecimals=0`(두 단가 모두 정수)이므로 정수로 표시.

### 예제 6 — 코인 소수 수량, 무한소수 → 반올림이 필요한 케이스 (자체 산출, 핵심 정밀도 검증)
- Input: `holdingQty=0.00012345, holdingPrice=90000000, additionalQty=0.00007656,
  additionalPrice=80000000`
- 계산(BigInt 스케일, 8자리): `Q1=12,345`, `Q2=7,656`(1e-8 단위), `cost1=0.00012345×
  90,000,000=11,110.5원`, `cost2=0.00007656×80,000,000=6,124.8원`, `totalCost=17,235.3원`,
  `totalQty=0.00020001`. 정확한 새평단가 = `17,235.3/0.00020001 =
  1,723,530,000,000/20,001 = 86,172,191 + 7,809/20,001 ≈ 86,172,191.39048...원`.
  `priceResultDecimals=0`(두 단가 모두 정수)이므로 사사오입 → `86,172,191원`(소수부
  `.39048`은 0.5 미만이므로 내림).
- Expected: `newAveragePrice=86,172,191원`, `totalQty=0.00020001`,
  `totalCost=17,235원`(17,235.3을 0자리로 반올림 — 위 "독립적으로 반올림" 정책에 따라
  `새평단가×총수량`으로 역산하지 않고 `totalCost`의 완전정밀도 원본에서 직접 반올림),
  `direction=하락`. **이 예제가 "코인 대응 소수 정밀도가 반올림 오차 없이 고정되는지"를
  검증하는 핵심 케이스** — Number로 단순 구현 시 `0.00012345`, `0.00007656` 같은 8자리
  소수의 덧셈·곱셈에서 이진 부동소수점 오차가 개입할 여지가 있는 반면, BigInt 고정소수점
  구현은 위 값을 오차 없이 정확히 재현해야 한다(Calculation Auditor가 Number 구현과
  BigInt/decimal 구현을 대조해 이 예제에서 값이 갈리는지 반드시 확인할 것을 권장).

### 예제 7 — "변동 없음처럼 보이지만 실제로는 미세 하락" 모순 방지 규칙 검증 (자체 산출)
- Input: `holdingQty=100000, holdingPrice=10000, additionalQty=1, additionalPrice=9000`
- 계산: `totalCost=100,000×10,000+1×9,000=1,000,000,000+9,000=1,000,009,000`,
  `totalQty=100,001`. 정확한 새평단가 = `1,000,009,000/100,001 = 9,999 + 99,001/100,001 ≈
  9,999.9900001원`. `priceResultDecimals=0`이므로 사사오입 → `10,000원`(소수부 `.99`가
  0.5 이상이므로 올림).
- Expected: **`newAveragePrice(표시)=10,000원`으로 `holdingPrice(10,000원)`와 화면상 숫자가
  동일하게 보이지만, `direction=하락`을 유지한다**(입력값 `additionalPrice(9,000) <
  holdingPrice(10,000)`로 정확히 비교했으므로). `priceChangeAmount(표시)=10,000−10,000=0원`
  이지만 "변동 없음 표시 모순 방지 규칙"에 따라 라벨은 "변동없음"으로 바뀌지 않고 "하락(표시
  자릿수 기준 미세 변동)" 형태로 노출되어야 한다. **이 예제가 SPEC.md가 요구한 "반올림 표시값과
  모순되지 않는 규칙"의 존재 이유를 정확히 보여준다.**

### 예제 8 — 수렴성 ① 추가수량이 보유수량 대비 매우 작음 (자체 산출, 정확)
- Input: `holdingQty=99, holdingPrice=10000, additionalQty=1, additionalPrice=100`
- 계산: `(99×10,000+1×100)/100 = (990,000+100)/100 = 990,100/100 = 9,901`(정확히
  나누어떨어짐)
- Expected: `newAveragePrice=9,901원`. `holdingPrice(10,000)`와 `additionalPrice(100)`의
  차이가 9,900원이나 되는데도, 추가수량이 보유수량의 1%뿐이라 새평단가는 보유평단가에서
  99원(약 1%)밖에 움직이지 않는다 — "추가수량이 보유수량 대비 작으면 새평단가는 보유평단가에
  수렴한다"는 완료 기준 불변식을 정확한 정수로 실증.

### 예제 9 — 수렴성 ② 추가수량이 보유수량 대비 매우 큼 (자체 산출, 정확, 예제 8의 대칭)
- Input: `holdingQty=1, holdingPrice=10000, additionalQty=99, additionalPrice=100`
- 계산: `(1×10,000+99×100)/100 = (10,000+9,900)/100 = 19,900/100 = 199`(정확히 나누어떨어짐)
- Expected: `newAveragePrice=199원`. 새평단가(199원)가 `holdingPrice(10,000)`가 아니라
  `additionalPrice(100)`에 훨씬 가깝다 — "추가수량이 보유수량을 압도하면 새평단가는
  추가매수단가에 수렴한다"는 불변식을 정확한 정수로 실증(예제 8과 완전히 대칭적인 구조).

### 예제 10 — 입력 상한 극단값 + 정확히 0.5 반올림 경계 (자체 산출, BigInt 필요성 실증)
- Input: `holdingQty=1000000000000000(10^15, 상한), holdingPrice=10000000000(100억원, 상한),
  additionalQty=1000000000000000(10^15, 상한), additionalPrice=1(최소 근접값)`
- 계산: `totalCost = 10^15×10^10 + 10^15×1 = 10^15×(10^10+1) = 10^15×10,000,000,001`,
  `totalQty=2×10^15`. `새평단가 = 10,000,000,001/2 = 5,000,000,000.5`(정확히 절반).
  `priceResultDecimals=0`이므로 사사오입 → **`5,000,000,001원`(0.5는 올림)**.
- Expected: `newAveragePrice=5,000,000,001원`, `direction=하락`(1<100억).
  **이 예제의 두 가지 검증 목적**:
  1. **일반 `Number` 연산의 실패 가능성 실증**: `10^15 × 10^10 = 10^25`는
    `Number.MAX_SAFE_INTEGER`(약 9.007×10^15)를 10^9배 이상 초과한다 — `Number`로 이
    곱셈을 그대로 수행하면 정밀도가 완전히 소실되어 잘못된 값이 나올 위험이 크다. 위
    "정밀도/반올림 정책"이 권장한 BigInt 방식은 이 스케일에서도 정확한 정수 연산이므로
    안전하다(이 계산기가 다른 계산기와 달리 "Number로 충분하다"는 결론에 도달하지 못하는
    핵심 이유).
  2. **사사오입(round-half-up) 정책의 결정론적 검증**: 정확히 `.5`가 나오는 입력을 의도적으로
    구성해, "반올림 방법"이 사사오입인지 은행반올림(banker's rounding, round-half-to-even)
    인지를 구분한다 — 은행반올림이었다면 `5,000,000,000`(짝수로 반올림)이 나와야 하지만, 이
    계산기는 `5,000,000,001`(항상 올림)을 정답으로 채택한다.

> **정방향 Golden Test 후보 총 10개.** 외부 독립 출처 대조 3건(예제 1·2·3, 서로 다른 2개
> 도메인), 방향 3종(하락/상승/변동없음) 모두 포함(예제 1·2·4), 코인 소수 정밀도 2건(예제
> 5·6), 반올림-라벨 모순 방지 규칙 1건(예제 7), 수렴성 불변식 2건(예제 8·9), 입력 극단값 +
> 반올림 경계 1건(예제 10) — SPEC.md "완료 기준"이 요구한 모든 불변식과 방향을 커버한다.

### 예제 11 — 목표 평단가 역산, 라운드트립 검증 (Should Have, 자체 산출)
- Input: `holdingQty=100, holdingPrice=10000, additionalPrice=8000, targetPrice=9000`
  (유효성 조건 `8,000 < 9,000 < 10,000` 충족)
- 계산: `x = 100×(10,000−9,000)/(9,000−8,000) = 100×1,000/1,000 = 100`.
- 검산(정방향 재대입): `(100×10,000+100×8,000)/(100+100) = 1,800,000/200 = 9,000` —
  `targetPrice`와 정확히 일치.
- Expected: `requiredAdditionalQty=100`. 공식 유도와 정방향 공식이 서로 모순 없이 맞아떨어짐을
  확인하는 핵심 예제.

### 예제 12 — 목표 평단가 역산, 이미 목표 달성(무효 케이스 ①, 자체 산출)
- Input: `holdingQty=100, holdingPrice=10000, additionalPrice=8000, targetPrice=10000`
  (`targetPrice = holdingPrice`)
- 계산: `x = 100×(10,000−10,000)/(10,000−8,000) = 100×0/2,000 = 0`.
- Expected: 오류가 아니라 "이미 목표 평단가(10,000원)에 도달해 있어 추가 매수가 필요
  없습니다" 안내. `x=0`을 그대로 결과로 노출하기보다 명시적 안내 문구로 처리할 것을 권장.

### 예제 13 — 목표 평단가 역산, 도달 불가능(무효 케이스 ②, 자체 산출)
- Input: `holdingQty=100, holdingPrice=10000, additionalPrice=8000, targetPrice=7000`
  (`targetPrice ≤ additionalPrice`)
- 계산: `x = 100×(10,000−7,000)/(7,000−8,000) = 100×3,000/(−1,000) = −300`(음수, 무효).
- Expected: "8,000원에 매수해서는 평단가를 7,000원까지 낮출 수 없습니다(매수단가보다 낮은
  목표는 수학적으로 도달 불가능합니다)" 같은 안내. 음수 결과를 그대로 노출하지 않는다.

> Should Have 검증 예제 3개 — 유효 케이스 1건(라운드트립), 무효 케이스 2건(이미 달성/도달
> 불가능). SPEC.md가 명시한 유효성 조건(`Pc<Pt<P1`)의 경계를 모두 검증했다.
