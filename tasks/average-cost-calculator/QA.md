# QA: 평단가(물타기) 계산기 (average-cost-calculator)

검토 대상: `src/calculators/average-cost-calculator/`(`decimal-scale.ts`, `logic.ts`,
`validation.ts`, `formatting.ts`, `content.ts`, `types.ts`, `ui.tsx` 및 각 `*.test.ts(s)`),
`src/calculators/registry.ts`(등록 상태, 아이콘 `trend`). Calculation Auditor(PASS, 독립 Python
재계산 + Number/BigInt 대조 + 20,000회 fuzz 포함) · UX/UI Critic(PASS, Medium 2건) 완료 후 QA
진행. Edit 권한이 없어 코드를 전혀 수정하지 않았다.

- 사전 문서 확인: `tasks/average-cost-calculator/{SPEC,FORMULA,ARCHITECTURE,EVALUATION}.md` 전문,
  `docs/DESIGN_SYSTEM.md`, `docs/EVALUATION.md`. 계산 정확성(Auditor PASS)은 전제로 삼고 재검증
  하지 않았다 — 이번 QA는 UX Critic이 남긴 Medium 2건의 재현 여부·독립 등급 판정과, 실사용
  흐름(타이핑→계산→결과) 관점의 기능/입력검증/접근성/모바일 검증에 집중했다.
- 회귀 스위트: `npx vitest run`(전체), `npx tsc --noEmit`, `npm run build`.
- 이 환경에는 Playwright/Puppeteer 등 브라우저 자동화 도구가 없다(`node_modules/.bin` 확인 결과
  미설치, 임의 설치는 진행하지 않음 — `bill-split-calculator`/`loan-interest-calculator` QA
  선례와 동일). 대신 다음 방법으로 보완했다.

     기동해 둔 상태를 그대로 재사용 — 직접 새로 띄우려 하자 "Another next dev server is already

     `src/calculators/average-cost-calculator/`에 `zzz-qa-probe.test.tsx`로 잠시 복사해 실행(15개

     문구·입력 검증(0/음수/상한초과/잘못된 문자)·ShareActions 왕복·초기화/샘플·`console.error`/

## 기능 테스트

- **정방향 계산 흐름(입력 4개 → 계산 → 결과 → 계산 근거)**: 샘플 값(FORMULA 예제 1)으로
  타이핑 → 계산 → 핵심 결과 카드에 "7,500원"·"평단가 하락" 정상 표시, "보유 현황 변화"·
  "계산 방법"·"적용된 입력값" 섹션 모두 렌더링됨을 프로브로 재확인(기존 `ui.test.tsx`와 동일
  결론, 독립 재실행).
- **코인 소수 시나리오(FORMULA 예제 6, 실사용 타이핑 흐름으로 재현 — 작업 지시 핵심 확인
  대상)**: `holdingQty="0.00012345"`, `holdingPrice="90000000"`, `additionalQty="0.00007656"`,
  `additionalPrice="80000000"`을 각 입력 필드에 `fireEvent.change`로 직접 타이핑 → 계산 버튼
  클릭까지 실제 폼 흐름으로 재현한 결과, 새 평단가 **"86,172,191원"**, 총 보유수량
  **"0.00020001"**, 총 투자원금 **"17,235원"**, 방향 "평단가 하락"이 화면에 정확히 표시됨을
  확인했다(FORMULA.md/Auditor의 계산값과 정확히 일치). 이 과정에서 `console.error`/
  `console.warn` 호출 0회. **문제없음.**
- **극단값(FORMULA 예제 10, 상한 근접 + 정확히 .5 반올림, 작업 지시 핵심 확인 대상)**:
  `holdingQty`/`additionalQty`=`10^15`(수량 상한), `holdingPrice`=`10,000,000,000`(단가 상한),
  `additionalPrice`=`1`을 실제 입력 필드에 타이핑 → 계산까지 재현한 결과, 새 평단가
  **"5,000,000,001원"**(사사오입 — 은행반올림이었다면 나왔을 "5,000,000,000원"이 아님을 직접
  확인), 총 투자원금 **"10,000,000,001,000,000,000,000,000원"**(26자리 정수 + 콤마 8개 + "원",
  총 35자)이 손실 없이 정확하게 렌더링됨을 확인했다. `console.error`/`console.warn` 호출 0회,
  화면 크래시·`NaN`/`Infinity` 노출 없음. **계산 자체는 문제없음** — 다만 이 값의 화면 표시
  폭에 대해서는 아래 "모바일 테스트"에 별도 이슈로 기록한다.
- **방향 뱃지 3종 실제 렌더(하락/상승/변동없음, 작업 지시 핵심 확인 대상)**: 세 케이스(예제
  1: 하락, 예제 2: 상승, 예제 4: 변동없음)를 순서대로 입력→계산해 SSR·클라이언트 렌더 모두
  확인한 결과, 세 경우 모두 `role="alert"`가 전혀 나타나지 않았다(즉 "상승"이 오류 상태로
  취급되지 않음) — `ui.tsx` 코드 대조 결과 `DirectionBadge`가 `direction` 값과 무관하게 항상
  동일한 중립 톤 클래스(`border-border-strong bg-surface-subtle text-foreground` 또는
  `onPrimary` variant)만 쓰고 `text-danger`/`red-` 계열 클래스가 방향 표시에 전혀 쓰이지
  않음을 재확인했다(UX Critic Q5와 동일 결론, QA 레벨에서 실제 렌더로 재검증). **문제없음.**
- **"변동 없음처럼 보이지만 실제로는 하락"(FORMULA 예제 7, 작업 지시 핵심 확인 대상)**:
  `holdingQty=100000, holdingPrice=10000, additionalQty=1, additionalPrice=9000`을 실제로
  입력→계산한 결과, 핵심 결과 카드에 새 평단가 **"10,000원"**(= `holdingPrice`와 표시상 동일)과
  **"평단가 하락"** 뱃지가 동시에 표시되고, 보조 설명 "표시 자릿수 기준으로는 변동액이 0으로
  보일 만큼 미세하지만, 실제로는 위 방향대로 변동했습니다(추가 매수 수량이 보유 수량보다 매우
  작을 때 발생할 수 있습니다)."가 핵심 결과 카드와 "보유 현황 변화" 카드 **두 곳 모두**에
  노출됨을 확인했다. `direction` 라벨이 "변동없음"으로 바뀌지 않았음(`screen.queryByText("변동
  없음")`이 `null`)을 프로브로 직접 확인했다 — FORMULA.md "모순 방지 규칙"이 화면까지 정확히
  이어짐. **문제없음.**
- **ShareActions 왕복(계산 후 공유 URL → 그 URL로 재진입, 작업 지시 핵심 확인 대상)**: 코인
  소수값(FORMULA 예제 5: `holdingQty=0.5, holdingPrice=52340000, additionalQty=0.25,
  additionalPrice=41150000`)을 `buildStateShareUrl`로 인코딩한 URL로 새로 마운트한 결과, 4개
  입력 필드(`0.5`/`52,340,000`/`0.25`/`41,150,000`)와 결과("48,610,000원")가 정확히 복원됐다.
  복원 후 계산 버튼을 다시 눌러 재계산해도 **완전히 동일한 "48,610,000원"**이 나옴을 확인해
  이 계산기가 RNG 없이 항상 결정적임을 실측으로 재확인했다(Auditor의 코드 분석과 별개로 UI
  엔드투엔드 경로에서 재확인). 손상된 공유 상태(`?s=broken-not-base64!!`)로 진입해도 오류 없이
  기본 빈 화면으로 처리됨도 확인했다. **문제없음.**
- **초기화**: 계산 후 "초기화" 클릭 시 4개 입력·오류·결과 모두 초기 상태로 복귀. **문제없음.**
- **샘플 값 채우기**: 클릭 시 FORMULA 예제 1 값이 채워지지만 **자동으로 계산되지는 않음**
  (사용자가 "계산하기"를 눌러야 결과가 나타남 — 실수로 이전 입력의 결과가 남아있는 것처럼
  보이는 상황을 방지하는 설계). `docs/DESIGN_SYSTEM.md` "Reset/Sample" 권장(FORMULA 검증
  예제 값을 그대로 사용)과 일치. **문제없음.**
- **입력 변경 시 이전 결과 숨김**: 계산 후 아무 입력이나 바꾸면 결과 영역이 즉시 사라져
  오래된 결과와 새 입력값이 불일치한 채로 남지 않음. **문제없음.**

## 모바일 테스트 (320 / 375 / 390 / 768 / 1440px)

실기기/브라우저 뷰포트 자동화 도구가 이 환경에 없어 **코드 정적 분석(Tailwind 클래스 기반
픽셀 재계산)**으로 판단했다 — 이 한계는 아래 "발견된 이슈"에도 별도로 남긴다.

- **폼 영역**: 페이지 컨테이너 `mx-auto max-w-6xl px-5 sm:px-8`(320px 기준 좌우 20px) + 폼
  컨테이너 `p-5 sm:p-8`(좌우 20px) → 실사용 폭 240px. 입력(`FIELD_CLASS`)은 `w-full`에
  `px-3.5`(좌우 14px) 패딩만 있어 텍스트 표시 폭 약 212px 확보 — 입력 필드 잘림 없음.
  `inputMode="decimal"`이 4개 필드 모두에 설정돼 있어 모바일에서 숫자 키패드(소수점 포함)가
  뜬다. **문제없음.**
- **버튼 3개(계산하기/초기화/샘플 값 채우기)**: `flex flex-wrap gap-3` — 320px에서 세 버튼이
  한 줄에 다 들어가지 않으면 자동으로 다음 줄로 줄바꿈되므로 가로 스크롤을 유발하지 않는다.
  **문제없음.**
- **결과 카드 숫자(정상 범위 입력, 예: 예제 1~9 수준)**: 핵심 결과 `text-4xl`(320px 기준 폭
  약 296px 컨테이너, "7,500원" 등 일반적 자릿수)과 보조 결과 `text-lg` 모두 여유 있게 들어감.
  **문제없음.**
- **극단값 입력 시 320px 가로 스크롤 위험(UX Critic Q11 Low 재현 + 추가 발견, 작업 지시 핵심
  확인 대상) — 재현됨, 독립 등급 재평가**: 위 "기능 테스트"에서 재현한 예제 10 극단값
  (`totalCost="10,000,000,001,000,000,000,000,000원"`, 총 35자)을 기준으로 직접 재계산했다.
  - `app/globals.css`에 `overflow-wrap`/`word-break`/`break-words` 전역 규칙이 없고, `ui.tsx`의
    결과 숫자 표시 요소(`dd`, breakdown `p`)에도 이런 줄바꿈 방어 클래스가 전혀 없음을 코드
    직독 + 프로브 테스트(`totalCostDd.className`에 `break-words|break-all|overflow-wrap` 미포함)
    로 재확인했다.
  - 320px 기준 "보유 현황 변화" `SectionCard`(`p-6`, 아이콘 `h-9 w-9`+`gap-3`) 내부 실사용
    폭은 `280(페이지) - 48(카드 패딩) - 48(아이콘+간격)` ≈ **184px**인데, 35자 숫자 문자열은
    `text-lg`(18px) `tabular-nums` 기준 약 **350px** 폭이 필요해(문자당 약 10px) 컨테이너 폭을
    크게 초과한다. 이 문자열은 콤마만 있고 공백이 없어 브라우저 기본 줄바꿈 규칙
    (`overflow-wrap: normal`)으로는 줄바꿈되지 않으므로, `dd`가 부모 폭을 넘어 시각적으로
    삐져나오고 조상 요소 어디에도 `overflow-x: hidden`이 없어(코드 확인) 페이지 전체의 가로
    스크롤로 이어질 가능성이 높다.
  - **UX Critic이 발견하지 못한 추가 지점**: 같은 결함이 "적용된 입력값" 섹션에서도 재현된다
    — 이 섹션은 `<div className="flex justify-between gap-2 sm:block">`로 `dt`/`dd`를 **한
    줄에 나란히** 배치하는데(640px 미만), 극단값 수량(`holdingQty=1,000,000,000,000,000`, 21자)
    만으로도 `dt`("보유 수량", 한글 4음절 약 70px) + `gap-2`(8px) + `dd`(21자 숫자 약 168px)
    ≈ 246px가 되어 같은 카드의 실사용 폭(약 184px)을 초과한다 — **이 섹션은 "총 투자원금"
    수준의 초극단값이 아니라 수량 상한(10^15)만 넣어도 재현되므로, "보유 현황 변화" 섹션보다
    더 낮은 입력값에서도 트리거된다.** `flex` 컨테이너는 `min-w-0`이 없어 `dd`가 줄어들지
    못하고(기본 `min-width: auto`) 그대로 넘친다.
  - **768px에서도 재현 가능성 있음**: `SectionCard`의 `sm:grid-cols-2`(640px 이상)가 적용돼도
    768px 기준 2열 폭은 대략 `(768 - 64(페이지) - 48(카드) - 48(아이콘) - 16(gap)) / 2 ≈ 296px`
    수준이라, 예제 10 수준의 35자 문자열(약 350px)은 여전히 이 폭을 넘는다. 다만 320~390px
    구간보다는 여유가 있다.
  - **1440px에서는 문제되지 않음**: `max-w-6xl` 컨테이너 안에서 2열 폭이 600px 이상 확보되어
    350px 문자열이 충분히 들어간다.
  - **독립 등급 재평가(Critic의 Low를 그대로 따르지 않고 QA 자체 판단)**: UX/UI Critic은 이
    현상을 "실제 극단값 입력이 흔치 않은 edge case"로 보고 **Low**로 분류했다. QA는 다음
    이유로 **Medium**으로 재평가한다 — (1) SPEC.md "공통 제품 요건"이 "320px···1440px 화면에서
    가로 스크롤 없이 사용할 수 있어야 한다"를, 그리고 FORMULA.md/ARCHITECTURE.md가 수량
    상한 `10^15`·단가 상한 `100억원`을 **둘 다 명시적 Must Have로 승인**했으므로, 이 결함은
    "일어날 것 같지 않은 우발적 edge case"가 아니라 **이 계산기 스스로 승인한 두 Must Have
    요건이 동시에 위반되는 조합**이다. (2) Critic은 "보유 현황 변화"의 `totalCost` 한 곳만
    확인했지만, QA 재현 결과 "적용된 입력값" 섹션은 **수량 상한만 넣어도(단가는 평범해도)**
    재현되어 발생 조건의 문턱이 Critic이 파악한 것보다 낮다. (3) 다만 실사용자(개인 투자자,
    SPEC.md "주요 사용자")가 실제로 보유 수량 1천조 개나 주당 100억원짜리 종목을 입력할
    가능성은 극히 낮으므로 계산 오류나 핵심 기능 마비는 아니다 — Critical/High("잘못된 계산
    결과"/"핵심 모바일 기능 사용 불가")에는 해당하지 않고, Issue 등급 정의의 "특정 Edge Case
    불편"(Medium) 구간에 해당한다고 판단한다.
- **768px/1440px 그리드 전환**: "보유 현황 변화" `dl`은 `sm:grid-cols-2`(640px↑ 2열), "적용된
  입력값"은 `sm:block`(640px↑ dt/dd 세로 배치로 전환돼 위 flex 가로 배치 문제가 해소됨),
  "사용 방법"/"평단가·물타기·불타기란?"은 `lg:grid-cols-2`(1024px↑ 2열, 그 미만은 1열
  스택) — 코드상 640/1024 각 breakpoint에서 정상적으로 열 수가 바뀌는 구조를 확인했다(정상
  범위 입력에서는 문제없음).

## 입력 검증

실사용 경로(직접 타이핑)로 4개 필드 모두를 프로브 테스트로 재현했다 — 이 계산기는 검증·계산
어디에도 `Number(raw)` 변환이 없다는 ARCHITECTURE.md 불변식이 실제 UI 이벤트 경로에서도
지켜짐을 확인했다.

- **빈 입력**: 아무것도 입력하지 않고 계산 → 4개 필드에 각각 "OO을/를 입력해 주세요." 오류가
  동시에 표시됨(기존 `ui.test.tsx` + 본 QA 재확인). **문제없음.**
- **음수**: `holdingQty`에 `"-5"`를 입력하면 `normalizeDecimalDisplay`가 `-`를 실시간으로
  걸러내 필드 값이 즉시 `"5"`로 바뀐다 — **음수를 입력 필드에 남길 방법 자체가 없다**(직접
  타이핑 기준). 프로브로 실측 확인. **문제없음.**
- **0**: `holdingQty="0"`으로 계산 → "보유 수량은 0보다 큰 값을 입력해 주세요."(빈 값 오류
  "보유 수량을 입력해 주세요."와 **다른 문구**)가 정확히 표시됨을 확인 — 형식 검증과 "0 이하"
  검증이 서로 다른 단계(ARCHITECTURE.md 4단계 검증)로 분리돼 있어 사용자에게 더 정확한 원인이
  전달된다. **문제없음.**
- **매우 큰 값(상한 초과)**: 수량에 `"1000000000000001"`(10^15+1) 입력 → "보유 수량은
  1,000,000,000,000,000(1천조) 이하로 입력해 주세요." 정확히 표시. 단가에 `"10000000001"`
  (100억원+1원) 입력 → "보유 평단가는 10,000,000,000원(100억원) 이하로 입력해 주세요." 정확히
  표시. 두 경우 모두 계산이 실행되지 않음. **문제없음.**
- **소수(자릿수 경계)**: 정확히 8자리(`"0.12345678"`)는 오류 없이 계산이 정상 실행됨(경계값
  통과, 본 QA에서 신규로 재현), 9자리(`"0.123456789"`)는 "소수점 8자리까지 입력할 수
  있습니다." 오류로 정확히 차단됨(기존 `ui.test.tsx` + 본 QA 재확인). **경계값 양쪽 모두
  문제없음.**
- **잘못된 문자**: `"1a2b3"` → 타이핑 즉시 `"123"`으로 정규화(문자 제거), `"1.2.3"`(다중
  소수점) → `"1.23"`으로 정규화(두 번째 이후 소수점 제거), `"한글입력10"` → `"10"`으로
  정규화(한글·비숫자 제거) — 세 경우 모두 `Number()`를 거치지 않는 순수 문자열 필터
  (`normalizeDecimalDisplay`)로 처리됨을 실제 입력 이벤트로 확인했다. 오류 메시지 없이
  조용히 정규화되므로 "왜 내가 입력한 문자가 사라졌는지" 사용자가 명시적으로 안내받지는
  못하지만, 크래시나 `NaN` 노출 없이 항상 유효한 부분 문자열로 수렴한다. **기능적으로
  문제없음**(안내 부재는 Low 수준 UX 여지로만 기록).

## Copy / Reset

- **Reset(초기화)**: 위 "기능 테스트"에서 확인 — 계산 후에도 4개 입력·오류·결과가 모두 초기
  상태로 정확히 복귀. **문제없음.**
- **Copy(링크 복사)**: `ShareActions`는 공용 컴포넌트이며 이번 계산기가 수정하지 않았다
  (`copyText` — `navigator.clipboard.writeText` 우선, `execCommand('copy')` 폴백 — 다른
  계산기 QA에서 이미 검증된 경로). 이 계산기 쪽에서 QA로 확인해야 할 부분은 "복사되는 URL이
  실제로 올바른 결과를 재현하는가"이며, 이는 위 "ShareActions 왕복" 절에서 `buildStateShareUrl`
  결과를 직접 디코딩·재마운트해 정확히 재현됨을 이미 확인했다. **문제없음.**

## Accessibility

- **label 연결**: SSR HTML에서 4개 입력 모두 `<label for="{id}">`와 `<input id="{id}">`가
  정확히 매칭됨을 `curl` 응답으로 직접 확인(`_R_..._-holdingQty` 등 4쌍).
- **필수 표시**: 4개 입력 모두 `aria-required="true"`가 SSR HTML에 포함됨(라벨의 시각적 `*`도
  `aria-hidden="true"`로 장식 처리돼 스크린리더가 중복으로 읽지 않음). 이 계산기는
  `bill-split-calculator`/`loan-interest-calculator` QA가 지적했던 "일부 입력에
  `aria-required` 누락" 문제가 **없다** — 4개 필드 모두 일관되게 적용돼 있음을 확인했다.
  **문제없음.**
- **오류 = role="alert" + aria-describedby + aria-invalid**: `ui.tsx` 코드 대조 결과 오류가
  있을 때만 `role="alert"`(`ERROR_CLASS`), `aria-describedby="{id}-error"`, `aria-invalid="true"`
  가 함께 설정됨을 확인. 프로브 테스트에서 "상승"(정상 결과) 렌더 시 `role="alert"`가 전혀
  없음을 재확인(오류가 아닌 정상 결과를 오류로 오인시키지 않음). **문제없음.**
- **aria-live**: 결과 영역(`<div aria-live="polite">`, 초기엔 빈 상태)과 `ShareActions` 피드백
  문구(`<p aria-live="polite">`) — SSR HTML에서 `aria-live="polite"` 2건 확인. 계산 완료 시
  결과가 이 영역 안에 삽입되므로 스크린리더에 자동 전달된다. **문제없음.**
- **FAQ 아코디언**: SSR HTML에서 6개 질문 각각 `aria-expanded="false"` + `aria-controls="{id}"`
  버튼으로 렌더링됨을 확인(공용 `FaqAccordion`, 이번 계산기가 수정하지 않음 — 기존에 이미
  검증된 패턴).
- **`ShareActions`의 `<section aria-label="...">`**: 프로브 테스트에서
  `screen.getByRole("region", { name: "계산기 공유" })`/`"계산 결과 공유"`가 정상적으로
  요소를 찾음을 확인(암묵적 `region` 역할이 접근 가능한 이름과 함께 정상 노출됨).
- **키보드 포커스**: 4개 입력·3개 버튼(계산하기/초기화/샘플 값 채우기) 모두 네이티브
  `<input>`/`<button>`이라 Tab/Enter/Space로 조작 가능. 전역 `:focus-visible` 스타일을
  개별적으로 제거하는 코드 없음(코드 대조).
- **방향 뱃지 아이콘**: `DirectionIcon`은 `aria-hidden="true"`(장식 요소)이고, 실제 정보는
  옆의 한글 텍스트("평단가 하락"/"평단가 상승"/"변동 없음")로 전달되므로 아이콘 크기(14px)와
  무관하게 스크린리더 접근성에는 영향이 없다(시각적 스캔 용이성은 별개 문제 — UX Critic Q5가
  이미 Low로 기록).

`docs/DESIGN_SYSTEM.md` "모바일" 절 요건(입력 필드 잘림 없음, 숫자 키패드, 결과 한눈에 보임,
가로 스크롤 없음)을 위 "모바일 테스트" 절에서 코드 치수 계산으로 확인했다. 정상 범위 입력

### 3) 화면 구성 순서 이탈 — **재확인, QA 독립 판단으로 Medium → "위반 아님"으로 해제**

- **독립 판단(Optimizer 판단에 자동 동의하지 않고 재검토)**: 다만 이 계산기 고유의

  계산기가 되어 오히려 "사이트 전체의 시각적 일관성"이라는, 이 프로젝트가 이미 한 번(2026-09-07)
