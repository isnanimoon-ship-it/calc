### 3. 이 계산기 특유의 중점 검증 항목 결과

- **예제 6(코인 무한소수)**: 독립 계산·실제 구현·Golden Test 3자 모두 `86172191`/
  `0.00020001`/`17235`/`-3827809`로 일치. **PASS**.
- **예제 7(반올림 모순 방지)**: 실제 구현 재호출 결과 `newAveragePrice="10000"`(holdingPrice와
  표시상 동일)이지만 `direction="하락"`, `priceChangeAmount="0"`,
  `isRoundedToZeroButChanged=true`로 정확히 FORMULA.md 규칙대로 동작함을 확인. **PASS**.
- **예제 10(극단값 + 정확히 .5)**: `newAveragePrice="5000000001"`(사사오입, 은행반올림
  아님), `totalCost="10000000001000000000000000"`(26자리 정수, 정확) 확인. **PASS**.
- **Number vs BigInt 대조 실험(FORMULA.md·ARCHITECTURE.md가 명시적으로 요청)**: 프로젝트
  코드를 참조하지 않는 순진한 Number 구현을 별도로 작성해 실측했다.
  - `totalCost`는 예제 10과 같은 규모(`10^15 × 10^10 = 10^25`)에서 **실제로 깨진다** —
    `additionalPrice=1`일 때는 JS의 "가장 짧은 왕복 가능 십진 표현" 알고리즘 덕에 우연히
    올바른 문자열(`10000000001000000000000000`)이 출력되지만, `toPrecision(30)`으로 저장된
    실제 이진값을 보면 이미 `10000000001000000288980992`로 오염되어 있었다(참값과
    288,980,992 차이). `additionalPrice`를 2, 3, 9, 13, 17, 100 등으로 살짝만 바꾸면 이
    오염이 출력 문자열에도 그대로 드러나 **명백히 틀린 `totalCost`가 나온다**(예:
    `additionalPrice=2`일 때 Number는 `...002000002000000000`, 정답은
    `...002000000000000000`). ARCHITECTURE.md "2.2"/"2.4"의 "Number로는 이 계산기가 승인한
    입력 범위 안에서 이미 실패한다"는 주장이 실측으로 확인됨.
  - `newAveragePrice`는 위와 같은 극단 조합에서도 (이 계산기 예제 10의 구체적 수치 및
    인접값들에서는) 우연히 정답과 같게 나왔다 — 이유는 최종 몫의 크기가 항상
    `[min(P1,Pc), max(P1,Pc)] ⊆ [0, 10^10]`로 Number 안전 정수 범위 안에 있고, 분자
    `totalCost`(최대 10^25)의 절대오차(ULP 수준, 약 10^9)를 분모 `totalQty`(최대 2×10^15)로
    나누면 상대오차가 약 10^-6 수준까지 줄어들어 정수 반올림 단위(1원)보다 훨씬 작아지기
    때문이다. **이는 코드 결함이 아니라 우연한 상쇄이며, `totalCost`(SPEC.md Must Have 출력
    필드)가 Number로는 검증 범위 안에서 명확히 틀린다는 사실만으로 BigInt 채택의 정당성은
    충분히 입증된다.** (참고 사항 — Low, "발견된 이슈" 참고)
  - `decimal-scale.ts`에는 위 실험과 무관하게 애초에 `Number()`/`parseFloat` 경유 코드가
    없음을 코드 직독으로 재확인(위 "1." 참고).
- **`direction` 판정 로직**: 반올림 이전 정확한 입력값(BigInt) 비교임을 코드 직독 + 예제 7
  실행 결과로 확인. **PASS**.
- **가중평균의 범위 불변식**: FORMULA.md의 대수적 증명을 그대로 신뢰하지 않고, 실제 구현에
  대해 **20,000회 랜덤 fuzz 테스트**(수량 1~15자리 정수부 + 0~8자리 소수부, 단가 1~10자리
  정수부 + 0~8자리 소수부, 상한 근접값 포함)를 수행했다. 결과: `min(P1,Pc) ≤ newAveragePrice
  ≤ max(P1,Pc)`(비엄격) 위반 0건, `direction`이 입력값 비교와 불일치 0건, `totalQty`가
  독립적으로 재계산한 BigInt 합과 불일치 0건, `totalCost`가 독립적으로 재계산한 BigInt
  가중합의 사사오입 결과와 불일치 0건, 예외 발생 0건. (참고: fuzz 스크립트 1차 버전에서
  "반올림된 표시값이 엄격 부등식을 만족하는지"까지 검사했다가 극단적으로 수량이 치우친
  입력에서 표시 자릿수 반올림으로 인해 정상적으로 경계값과 같아지는 경우가 다수 발견됐는데,
  이는 FORMULA.md가 "완전정밀도(반올림 전) 값"에만 엄격 부등식을 증명했을 뿐 "반올림된 표시값"
  에는 그런 약속을 하지 않았으므로 구현 결함이 아니라 검증 스크립트 자체의 과도한 가정이었다
  — 예제 7의 "모순 방지 규칙"과 같은 성격.) **PASS**.
- **입력 검증**(`validation.ts`): FORMULA.md 상한(10^15/100억원)·소수 8자리 상한을 정확히
  반영, `Number(raw)` 없음, 상한 경계값 정확히 포함(≤) 확인. **PASS**.

#### Q8. (평가 항목: 계산 과정 이해) 계산 근거(breakdown)가 숫자만 나열되어 있어 여전히 이해하기 어렵지는 않은가?

- **등급**: 문제없음.

#### Q10. (평가 항목: 입력 라벨 순서·그룹핑 / 불필요한 UI 요소) 실제 화면 구성 순서가 SPEC.md "화면 구성" 및 `docs/DESIGN_SYSTEM.md` "공통 화면 순서"(소개→사용방법→입력→결과→계산근거→정책안내→FAQ)와 일치하는가?
- **근거**: `ui.tsx`를 렌더 순서대로 추적한 결과 다음과 같다: (1) `<header>` — h1 + 인라인
  한 문단 소개(전체 `IntroSection` 컴포넌트 아님) → (2) `<form>`(입력, 보유→추가매수) →
  (3) `ShareActions` → (4) 결과(핵심 결과 카드 + 보조 결과 + 계산 방법(breakdown) + 적용된
  입력값) → (5) **`UsageGuide` + `IntroSection`**(줄 485-491, "사용 방법"과 "평단가·물타기·
  불타기란?") → (6) 계산 전 확인(전제 고지) → (7) 서버 미전송 안내 → (8) `FaqAccordion`.
  SPEC.md "화면 구성"은 "1.소개 2.사용 방법 3~4.입력 5.공유 6.결과 7.계산 근거 8.전제고지+
  FAQ" 순서를 명시했고, `docs/DESIGN_SYSTEM.md` "공통 화면 순서"도 "소개 → 사용 방법 →
  입력 → 결과 → 계산 근거 → 정책 안내 → FAQ"를 명문화했다. 그런데 실제 구현은
  `UsageGuide`/`IntroSection`(온전한 소개·사용법 섹션)을 **입력보다 앞이 아니라 결과·
  계산근거보다도 뒤**에 배치했다. header의 짧은 한 문단이 최소한의 맥락을 주긴 하지만,
  이는 SPEC.md가 명시적으로 요구한 화면 순서 및 이 프로젝트의 공통 디자인 시스템 규칙에서
  벗어난 것이다. 첫 방문자가 "평단가"·"물타기"·"불타기" 개념을 아직 모른 채 곧바로 입력
  폼을 마주하게 되는데(header 문단이 있어 완전히 맥락 없음은 아니지만, 전체
  `IntroSection`이 주는 상세 설명은 결과 이후에야 나온다), 이는 "계산법을 몰라도 쓸 수
  있어야 한다"는 제품 목표와 이 사이트가 스스로 정한 화면 순서 표준에 부분적으로 어긋난다.
- **등급**: **Medium** — 계산 정확성이나 기능 자체에는 영향이 없고 header의 요약 문단이
  최소한의 맥락을 제공하지만, SPEC.md와 DESIGN_SYSTEM.md 양쪽이 명시한 화면 순서 규칙을
  구조적으로 벗어난 것은 사소한 디자인 취향 차이가 아니라 이 사이트의 공통 규칙 위반이다.

#### Q11. (평가 항목: 모바일 사용성, 레이아웃 관점) 극단적으로 큰 입력값(상한 근접)에서도 좁은 화면(320px)에서 가로 스크롤 없이 결과가 표시되는가?
- **근거**: `app/globals.css`에 `overflow-wrap`/`word-break`/`break-words` 관련 전역 규칙이
  없음을 확인했고, `ui.tsx`의 결과 숫자 표시 요소들(`text-4xl`/`text-lg font-semibold
  tabular-nums` 등)에도 `break-words`/`overflow-wrap` 클래스가 없다. FORMULA.md 예제 10처럼
  입력 상한(수량 10^15, 단가 100억원)에 가까운 값을 넣으면 `totalCost`는 최대 26자리
  정수(`formatWon` 결과 기준 "원" 포함 약 30자 이상, 천 단위 콤마 포함)까지 늘어날 수
  있다(Auditor 절 "예제 10" 참고, 실제로 `totalCost="10000000001000000000000000"` 같은
  값이 관측됨). 쉼표가 포함된 순수 숫자 문자열은 브라우저에 따라 줄바꿈 지점으로 인식되지
  않을 수 있어(공백이 없는 연속 문자열), 320px 뷰포트에서 이런 극단값이 카드 폭을
  초과하며 가로 스크롤을 유발할 가능성을 코드상 배제할 수 없다. 다만 이 계산기의 실제
  주 사용 시나리오(개인 투자자의 실제 보유 수량·단가)에서는 이런 극단값이 나올 가능성이
  매우 낮고, 일반적인 값(예: FORMULA.md 예제 1~9 수준)에서는 이 문제가 발생하지 않는다.
- **등급**: Low — 실제 극단값 입력이 흔치 않은 edge case이고 실제 브라우저 렌더링(줄바꿈
  동작)은 QA의 실기기 검증이 필요한 영역이나, 레이아웃 코드상 방어 장치(`break-words`
  등)가 없다는 사실 자체는 기록해 QA가 320px에서 상한값 입력으로 재현 테스트할 것을
  권장한다.

#### Q12. (평가 항목: 오류 메시지의 이해 용이성) 오류 메시지가 계산법을 모르는 사용자도 이해할 수 있는 문구인가?

  `DECIMAL_PLACES_MESSAGES`/`ZERO_OR_LESS_MESSAGES`/`UPPER_BOUND_MESSAGES`)를 모두 확인한
  결과, 전문 용어 없이 "보유 수량을 입력해 주세요.", "보유 수량에는 0보다 큰 숫자만 입력할
  수 있습니다.", "보유 수량은 소수점 8자리까지 입력할 수 있습니다.", "보유 수량은
  1,000,000,000,000,000(1천조) 이하로 입력해 주세요." 등 구체적인 필드명과 조건을 평이한

  설계되어 있다 — 오류가 나더라도 "무엇을, 왜 고쳐야 하는지"가 각 메시지에 분명하다.

### 3. 극단값 입력 시 가로 스크롤(Critic Q11 Low / QA 재평가 Medium) — **수정함**

`src/calculators/average-cost-calculator/ui.tsx`에서 결과 숫자를 표시하는 요소들에
`break-words`(Tailwind `overflow-wrap: break-word`)를 추가하고, "적용된 입력값" 섹션의
`dd`에는 `min-w-0`도 함께 추가했다.

- 핵심 결과 카드 새 평단가 `<p>`(수정 전 줄 405): `text-4xl font-bold …` →

- 핵심 결과 카드 변동액 `<p>`(수정 전 줄 410): `text-sm opacity-90 …` →
  `break-words text-sm opacity-90 …` 추가.
- "보유 현황 변화" 총 보유수량 `<dd>`(수정 전 줄 426), 총 투자원금 `<dd>`(수정 전 줄 430):
  각각 `mt-0.5 text-lg font-semibold tabular-nums` → `mt-0.5 break-words text-lg font-semibold
  tabular-nums` 추가.
- "보유 현황 변화" 평단가 변동 값 `<span>`(수정 전 줄 436): `tabular-nums` →
  `break-words tabular-nums` 추가.
- "계산 방법"(breakdown) 각 줄의 `<p>`(수정 전 줄 454): `mt-1 tabular-nums …` →
  `mt-1 break-words tabular-nums …` 추가.
- "적용된 입력값" 섹션의 `<dd>` 4개(수정 전 줄 464/468/472/476, `보유 수량`/`보유 평단가`/
  `추가 매수 수량`/`추가 매수 단가`): 클래스가 없던 자리에 `min-w-0 break-words` 추가. 이
  섹션의 부모(`<div className="flex justify-between gap-2 sm:block">`)는 640px 미만에서 `dt`/
  `dd`를 한 줄에 나란히 배치하는 flex 컨테이너인데, flex item의 기본 `min-width: auto`
  때문에 `dd`가 자기 콘텐츠 폭 밑으로 줄어들지 못해 부모 폭을 초과했다 — `min-w-0`으로 이
  기본값을 없애 `dd`가 남은 공간까지 줄어들 수 있게 하고, `break-words`로 줄어든 폭 안에서
  숫자 문자열이 줄바꿈되게 했다.

**치수 계산으로 확인한 결과(QA.md가 산출한 수치를 그대로 사용)**: QA.md "모바일 테스트" 절이
계산한 대로, 320px 뷰포트에서 "보유 현황 변화" `SectionCard` 내부 실사용 폭은 약 184px인데
FORMULA.md 예제 10 수준(`totalCost` 26자리, 콤마 포함 35자)의 문자열은 줄바꿈 방어가 없으면
약 350px가 필요해 폭을 초과했다. `break-words`(`overflow-wrap: break-word`)를 추가하면 공백이
없는 숫자 문자열이라도 컨테이너 폭에 맞춰 줄 단위로 강제 개행되므로(브라우저가 한 줄에 담을
수 없는 지점에서 문자 단위로 줄을 바꿈), 텍스트가 세로로 여러 줄에 걸쳐 표시될 뿐 가로로는
더 이상 부모 폭(184px)을 넘지 않는다 — 즉 텍스트 박스의 가로 폭은 항상 부모 컨테이너 폭
이하로 유지되고, 넘치는 길이는 줄 수 증가로만 흡수된다.
"적용된 입력값" 섹션도 동일 논리다. `holdingQty=10^15`(21자)만으로도 `dt`(약 70px) +
`gap-2`(8px) + `dd`(줄바꿈 방어 없이 약 168px) ≈ 246px > 184px였는데, `dd`에 `min-w-0`을
추가하면 `dd`의 최소 폭 제약이 사라져 flex 컨테이너가 남은 공간(약 184-70-8=106px)만큼만
`dd`에 배분하고, `break-words`가 그 106px 안에서 168px 분량의 숫자를 2줄 이상으로 접어
표시하게 만든다 — 가로로는 106px(＝부모가 배분한 폭)를 넘지 않으므로 가로 스크롤을 유발하지
않는다. 640px 이상에서는 부모가 `sm:block`으로 전환돼 `dt`/`dd`가 세로로 쌓이므로 이 문제
자체가 발생하지 않는다(QA.md 확인 사항, 변경 없음).
이 환경에는 브라우저 자동화 도구가 없어(QA.md와 동일한 제약) 실제 렌더링 픽셀을 관찰하지는
못했다 — 위 계산은 Tailwind `break-words`/`min-w-0`의 표준 동작(MDN
`overflow-wrap: break-word`, CSS flexbox `min-width: auto` 기본값)에 근거한 코드/치수 수준
검증이며, 다음 QA 재검증 라운드에서 가능하면 재확인을 권장한다.
