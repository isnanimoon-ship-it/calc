# FORMULA: 디데이 계산기

## 목적

특정 두 날짜 사이의 순수 달력일(calendar day) 차이를 `D-Day`/`D-N`/`D+N`으로 표시하는
모드 A(디데이 계산)와, 기준일에 일수를 더하거나 빼서 결과 날짜(+요일)를 구하는 모드 B(날짜
계산)를 계산한다. 법령·고시·연도별 요율에 의존하지 않는 순수 그레고리력 산술 계산기이며,
이 문서의 "공식 출처"는 법 조항이 아니라 그레고리력 계산 규칙 자체(윤년 규칙, 날짜 직렬 번호
변환, 요일 계산 알고리즘)와 이를 검증한 방법이다.

## 기준

- 기준일 / 마지막 검토: 2026-09-12
- 날짜 해석: 시간대 없는 그레고리력 `YYYY-MM-DD` 문자열. 계산은 항상 UTC 자정 기준 정수
  연산으로 고정하고 로컬 timezone·DST를 계산에 관여시키지 않는다.
- 지원 범위: **1900-01-01 ~ 2200-12-31** — 모드 A의 시작일·목표일, 모드 B의 기준일 모두
  동일하게 적용한다(근거는 아래 "지원 범위 확정 근거" 참고).
- 다음 재검토: 정책·법령에 의존하지 않으므로 정기 재검토 대상이 아니다(SPEC.md "정책
  재검토: 해당 없음"과 동일). 그레고리력 계산 로직 자체의 오류가 발견되거나 지원 날짜 범위
  확장이 필요할 때만 재검토한다.

## 공식 출처 (그레고리력 계산 규칙 검증)

법령 조항 대신 아래 표준 규칙과 두 개의 독립적인 알고리즘으로 이 문서의 모든 수치를
교차 검증했다.

1. **그레고리력 윤년 규칙**(ISO 8601이 채택한 표준 정의): 연도가 4로 나누어떨어지면 윤년,
   단 100으로 나누어떨어지면 평년, 단 400으로 나누어떨어지면 다시 윤년. (예: 1900=평년,
   2000=윤년, 2024=윤년, 2028=윤년, 2025=평년.)
2. **날짜 → 정수 직렬 번호(day serial) 변환**: 이 프로젝트가 이미 프로덕션에서 검증한 패턴을
   그대로 재사용한다 — 새 알고리즘을 발명하지 않는다.
   - `src/calculators/age-calculator/date-utils.ts`의 `daySerial`
   - `src/calculators/military-discharge-date/logic.ts`의 `serial`/`fromSerial`
   - `src/lib/date-calc.ts`의 `parseIsoDateUtc`/`diffDaysUtc`
   - 공통 알고리즘: `daySerial(y,m,d) = floor(Date.UTC(y, m-1, d) / 86_400_000)`
     (UTC 자정 기준 Unix epoch(1970-01-01=0) 정수 일련번호).
3. **요일 계산**: `new Date(Date.UTC(y,m-1,d)).getUTCDay()`(0=일요일~6=토요일, JS `Date`
   표준, `age-calculator/date-utils.ts`의 `weekday`와 동일)를 1차 계산 방식으로 쓰고,
   독립적인 교차검증 수단으로 **Zeller's Congruence**(그레고리력 버전)를 별도로 손계산해
   모든 예제 값이 두 방식에서 100% 일치함을 확인했다(아래 "요일 계산 검증" 참고).
4. **큰 규모 날짜 이동 검증**: Howard Hinnant의 `days_from_civil`/`civil_from_civil` 공개
   그레고리력 산술 알고리즘(https://howardhinnant.github.io/date_algorithms.html, 그레고리력
   표준 산술 알고리즘으로 널리 인용됨)을 별도로 손계산해 이 문서의 모든 대규모(N≥10,000일)
   Golden Test 값을 재계산하고 일치를 확인했다.
5. 이 계산기는 법령·고시·연도별 수치에 의존하지 않으므로 "확인 필요"로 남길 미확정 수치가
   없다(docs/CALCULATOR_RULES.md 정확성 원칙).

## 입력값

| 변수 | 설명 | 단위 | 허용 범위 |
|---|---|---|---|
| startDate (모드 A) | 디데이 기산 시작일 | 날짜(`YYYY-MM-DD`) | 1900-01-01~2200-12-31 |
| targetDate (모드 A) | 목표일 | 날짜 | 1900-01-01~2200-12-31, startDate와 선후관계 제약 없음 |
| baseDate (모드 B) | 날짜 계산 기준일 | 날짜 | 1900-01-01~2200-12-31 |
| days (모드 B) | 더하거나 뺄 일수 | 일, 0 이상 정수 | 0~100,000 |
| direction (모드 B) | 방향 | enum | `add` \| `subtract`, 기본값 `add` |

## 출력값

| 변수 | 설명 | 단위 |
|---|---|---|
| dayDiff (모드 A) | `daySerial(targetDate) - daySerial(startDate)` | 일(부호 있음) |
| ddayLabel (모드 A) | `D-Day` / `D-N` / `D+N` | 문자열 |
| weeksBreakdown (모드 A, Should Have) | `{ weeks, remainderDays }` | 주/일 |
| resultDate (모드 B) | `baseDate ± days` | 날짜(`YYYY-MM-DD`) |

## 공식

### 날짜 → 정수 직렬 번호
```
daySerial(y, m, d) = floor(Date.UTC(y, m-1, d) / 86_400_000)
```
입력 문자열은 항상 정규식 `^\d{4}-\d{2}-\d{2}$`로 형식을 먼저 검증하고, `Date.UTC` 결과를
다시 `getUTCFullYear/getUTCMonth/getUTCDate`로 읽어 원래 y/m/d와 일치하는지 왕복 검증한다
(`military-discharge-date/validation.ts`의 `isValidIsoDate`와 동일 패턴). 이 왕복 검증에서
불일치가 나면(예: 2024-02-30 → 3월로 정규화됨) 존재하지 않는 날짜로 판정해 거부한다.

### 모드 A: 날짜 차이(diff, fencepost 규칙)
```
diff = daySerial(targetDate) - daySerial(startDate)

diff === 0 → "D-Day"
diff  > 0 → "D-" + diff        (N = 목표일 − 시작일, 아직 N일 남음)
diff  < 0 → "D+" + (-diff)     (N = 시작일 − 목표일, N일 지남)
```
SPEC.md "날짜 차이 계산 정의"가 정의한 fencepost 규칙(시작일=목표일 → 0)을 정수 직렬 번호
뺄셈으로 그대로 구현한 것이다. 인클루시브 카운트(+1)는 어떤 경로로도 계산하지 않는다.

### 모드 B: 날짜 이동(add)
```
signedDays  = direction === "add" ? days : -days
resultSerial = daySerial(baseDate) + signedDays
resultDate   = fromSerial(resultSerial)
```
`fromSerial(serial)`은 `new Date(serial * 86_400_000)`에서 `getUTCFullYear/getUTCMonth/
getUTCDate`를 읽어 `YYYY-MM-DD`로 조립한다(`military-discharge-date/logic.ts`의
`fromSerial`과 동일 구현).

### 요일
```
weekdayIndex = new Date(daySerial(y,m,d) * 86_400_000).getUTCDay()   // 0=일 ... 6=토
label = ["일","월","화","수","목","금","토"][weekdayIndex]
```

### 모드 A ↔ 모드 B 역함수 불변식 (완료 기준)
```
result = addDays(baseDate, N, "add")
diff(startDate = baseDate, targetDate = result) === N

result = addDays(baseDate, N, "subtract")
diff(startDate = baseDate, targetDate = result) === -N
```
두 모드는 같은 `daySerial`/`fromSerial` 순수 함수를 공유해 구현하며, 별도의 계산 경로를
만들지 않는다(SPEC.md "계산 방식(공통)" 참고).

### 주 단위 환산 (Should Have)
```
n = |diff|  (모드 A) 또는 days (모드 B 참고 표시 시)
weeks = floor(n / 7)
remainderDays = n - weeks * 7

n === 0             → 표시하지 않음 (당일이므로 의미 없음)
weeks === 0         → `${remainderDays}일`
remainderDays === 0 → `${weeks}주`
그 외               → `${weeks}주 ${remainderDays}일`
```
나눗셈은 항상 `floor`(내림)만 쓰고 반올림하지 않는다. 방향 어미는 diff 부호를 따른다
(diff>0 → "…후", diff<0 → "…전"). 예: `D-45` → `6주 3일 후`, `D+254` → `36주 2일 전`.

## 계산 순서

**모드 A**
1. `startDate`, `targetDate`의 형식(`YYYY-MM-DD`)과 실존 여부를 검증(정규식 + `Date.UTC`
   왕복 검증).
2. 두 날짜 모두 지원 범위(1900-01-01~2200-12-31) 안인지 검증. 벗어나면 계산하지 않고
   범위를 안내하는 오류를 표시.
3. `daySerial`로 변환해 `diff = daySerial(target) - daySerial(start)` 계산.
4. `diff` 부호에 따라 `D-Day`/`D-N`/`D+N` 라벨 생성.
5. (Should Have) `weeks`/`remainderDays`, 시작일·목표일 요일 계산.

**모드 B**
1. `baseDate`의 형식·실존 여부·범위를 검증.
2. `days`가 0 이상 100,000 이하의 정수인지 검증(음수·소수·비숫자·100,000 초과는 거부).
3. `direction`에 따라 `signedDays` 결정.
4. `resultSerial = daySerial(baseDate) + signedDays` 계산 후 `resultDate = fromSerial(resultSerial)`.
5. **`resultDate`도 지원 범위(1900-01-01~2200-12-31) 안인지 다시 검증한다.** `days` 상한
   (100,000)을 통과했더라도 `baseDate`의 위치에 따라 결과가 범위를 벗어날 수 있다(아래
   "N 상한 근거" 참고). 벗어나면 계산 결과를 표시하지 않고 범위 초과 오류로 처리한다.
6. `resultDate`의 요일 계산.

## 단위

- 날짜: `YYYY-MM-DD` 문자열이 입출력 표현이며, 내부 계산은 항상 UTC 자정 기준 정수 일련
  번호(`daySerial`)로 변환해 수행한다.
- 일수(`days`, `diff`): 정수. `diff`의 부호는 모드 A의 D-/D+ 접두사로만 표현하고, 모드 B의
  `days` 입력 자체는 항상 0 이상(방향은 별도 `direction` 값으로 분리).
- 요일: 정수 인덱스(0~6, JS `getUTCDay()` 규약) → 화면 표기는 한국어 1글자(`일월화수목금토`).

## 정밀도 / 반올림 정책

- 모든 날짜 연산은 정수(일련번호) 산술만 사용한다 — `Date.UTC`로 만든 밀리초를 `86_400_000`
  으로 나눈 몫만 쓰므로 부동소수점 오차, DST, 로컬 timezone 이동이 개입할 여지가 없다.
- 반올림이 필요한 값 자체가 없다(일수는 항상 정수, 요일은 정수 인덱스). 주 단위 환산의
  나눗셈은 `floor`(내림)만 사용한다 — "6.4주"처럼 애매한 값을 만들지 않기 위함이다.
- 근거: 법적으로 강제되는 절사·반올림 규정이 없는 순수 산술 계산기다.

## 예외

- **존재하지 않는 날짜**(2월 30일, 4월 31일 등): 정규식 통과 후 `Date.UTC` 왕복 검증에서
  불일치를 확인해 계산하지 않고 오류.
- **누락된 입력**: 시작일·목표일·기준일·일수 중 하나라도 비어 있으면 계산하지 않고 해당
  필드 근처에 오류.
- **지원 범위 밖 입력**(1900-01-01 미만 또는 2200-12-31 초과): 계산하지 않고 지원 범위를
  안내.
- **모드 B 결과가 범위 밖**: `baseDate`, `days`가 각각 유효해도 `resultDate`가 범위를
  벗어나면 결과를 표시하지 않고 오류(위 "계산 순서" 모드 B 5단계).
- **`days` 음수/소수/비숫자**: 방향은 별도 토글로 받으므로 `days` 필드는 항상 0 이상 정수만
  허용. 위반 시 오류.
- **`days` > 100,000**: 상한 초과로 오류(아래 "N 상한 근거").
- **시작일=목표일(모드 A)**: 오류가 아니라 정상, `D-Day`.
- **`days`=0(모드 B)**: 오류가 아니라 정상, 결과일=기준일과 동일.
- **선후관계 제약 없음**: 목표일이 시작일보다 과거여도 정상 계산(`D+N`), 영업일 계산기의
  "종료일이 시작일보다 빠를 수 없다" 제약을 적용하지 않는다.

## 지원 범위 확정 근거 (1900-01-01 ~ 2200-12-31)

`age-calculator/FORMULA.md`(지원 범위 1900-01-01~2200-12-31)와
`military-discharge-date/FORMULA.md`(날짜 해석 규칙, `referenceDate` 검증 범위
2020-01-01~2200-12-31)를 대조한 결과, 이 계산기도 동일한 상한(2200-12-31)과 하한 연도대
(1900년)를 채택한다. 근거는 다음과 같다.

- 이 계산기는 `military-discharge-date`처럼 특정 정책(복무기간)의 유효 구간이 없으므로
  하한을 정책 시작일이 아니라 `age-calculator`와 동일하게 1900-01-01로 넓게 잡는 것이
  타당하다 — "과거의 임의의 두 날짜(예: 만난 날과 헤어진 날) 사이의 날짜 차이"(SPEC.md
  "주요 사용자")처럼 개인 기념일 용도는 출생일 이전(예: 조부모 결혼기념일, 오래된 문서
  날짜)까지도 다룰 수 있어야 하지만, 그렇다고 무한정 넓힐 근거도 없다. `age-calculator`가
  이미 "만 나이" 산정을 위해 1900년을 하한으로 채택했고 별다른 문제 없이 운영 중이므로
  일관성을 위해 동일 값을 재사용한다.
- 상한 2200-12-31은 두 계산기 모두 채택한 값과 동일하며, "충분히 먼 미래"(약 175년 후)까지
  커버해 결혼기념일·장기 계약·미래 기념일 계획 등 실사용 범위를 넉넉히 포함한다.
- **그레고리력 자체의 소급 적용 가능 범위**: 그레고리력은 실제로는 1582년 10월(가톨릭
  국가) 또는 그 이후(국가별로 다름, 예: 영국·미국은 1752년)부터 시행되었고, 그 이전은
  율리우스력이었다. 1900년은 모든 채택국에서 이미 그레고리력이 시행된 이후이므로, 이
  계산기가 "1900년 이후는 그레고리력 규칙(4/100/400년 윤년 규칙)을 그대로 소급 적용해도
  실제 역사적 달력과 어긋나지 않는다"는 전제가 성립한다. 1900년보다 훨씬 이전(예: 1700년대)
  까지 범위를 넓히면 국가별 그레고리력 전환 시점이 달라 "존재하지 않는 날짜"(전환 시 며칠이
  통째로 건너뛰어짐, 예: 영국은 1752-09-03~13이 존재하지 않음) 문제가 생기므로 다루지
  않는다.
- **JS `Date` 객체의 안전 범위**: JS `Date`는 `±100,000,000일`(약 ±273,790년, 1970-01-01
  기준)까지 표현 가능하므로 1900~2200 범위는 JS `Date`/`Date.UTC` 정수 연산의 안전 범위
  안에 여유 있게 포함된다(`Number.MAX_SAFE_INTEGER` 밀리초 한계와도 무관). 이 범위 자체가
  JS `Date`의 제약 때문에 정해진 것이 아니라, 위 그레고리력 소급 적용 가능 범위와 두 계산기의
  선례가 근거다.
- 결론: 이 계산기도 `age-calculator`/`military-discharge-date`와 동일한 **1900-01-01 ~
  2200-12-31**을 시작일·목표일·기준일 공통 지원 범위로 확정한다. 다르게 할 근거(예: 더 넓은
  과거 범위가 실제로 필요하다는 근거)가 없으므로 SPEC.md의 제안값을 그대로 채택한다.

## N 상한(모드 B 일수) 근거

- 지원 날짜 범위의 전체 폭은 `daySerial(2200-12-31) - daySerial(1900-01-01)
  = 84,370 - (-25,567) = 109,937일`(약 301.05년). 두 값 모두 Howard Hinnant의
  `days_from_civil` 알고리즘으로 별도 손계산해 교차 검증했다(`daySerial`의 `Date.UTC`
  방식과 정확히 일치).
- 제안값 100,000일(약 273.8년)은 전체 범위 폭(109,937일)보다 작다. 범위의 **양 끝단
  기준**으로는 안전함을 확인했다:
  - `daySerial(1900-01-01) + 100,000 = 74,433 < daySerial(2200-12-31) = 84,370` → 범위 안.
  - `daySerial(2200-12-31) - 100,000 = -15,630 > daySerial(1900-01-01) = -25,567` → 범위 안.
    실제 날짜로는 **2200-12-31 − 100,000일 = 1927-03-18**(Hinnant 알고리즘 손계산 검증
    완료, 아래 Golden Test #22).
- 다만 **기준일이 범위 중간에 있으면 100,000일 이동이 범위를 벗어날 수 있다.** 예:
  `2000-01-01 + 100,000일`은 산술적으로 **2273-10-16**이 되어 지원 상한(2200-12-31)을
  넘는다(Hinnant 알고리즘으로 검증, 아래 Golden Test #23). 따라서 100,000은 "입력 필드
  자체의 합리적 상한"일 뿐이며, 계산 결과가 항상 지원 범위 안에 있다는 보장은 이 상한만으로
  성립하지 않는다 — 위 "계산 순서" 모드 B 5단계(결과일 재검증)가 반드시 함께 있어야 하고,
  이는 이 문서의 필수 규칙이다(Builder가 생략하면 계산기 결함으로 반려 대상).
- 100,000이라는 크기의 현실성: 실사용(기념일 카운트, 계약일, 시험일 등)은 대부분 수천 일
  이내이며, 100,000일은 이보다 훨씬 큰 여유 상한이다. 이보다 크게 잡을 이유가 없고(성능·
  현실성 모두 불필요), 이보다 작게 잡으면(예: 30,000일) 지원 범위 안의 두 날짜 사이 최대
  차이(109,937일)를 모드 B의 "며칠 뒤" 형태로는 표현하지 못하는 경우가 지나치게 많아져
  모드 A/B 역함수 불변식(완료 기준)을 실질적으로 검증하기 어려워진다. 따라서 **100,000일**을
  확정값으로 채택한다.

## 요일 계산 검증

`daySerial` 기반(`Date.UTC`/`getUTCDay`) 방식과 **Zeller's Congruence**(그레고리력 버전,
`h = (q + ⌊13(m+1)/5⌋ + K + ⌊K/4⌋ + ⌊J/4⌋ − 2J) mod 7`, 1월·2월은 전년도의 13월·14월로
취급하고 `K`=연도 뒤 2자리, `J`=연도 앞 2자리, `h`: 0=토·1=일·2=월·…·6=금)로 각각 독립
계산해 아래 값이 100% 일치함을 확인했다.

| 날짜 | 요일 | 비고 |
|---|---|---|
| 2000-01-01 | 토요일 | 두 방식 교차검증 앵커(Y2K 기준일) |
| 1900-01-01 | 월요일 | 지원 범위 하한 |
| 2024-02-29 | 목요일 | 윤년 2월 29일 |
| 2028-02-29 | 화요일 | 미래 윤년 2월 29일 |
| 2026-09-12 | 토요일 | 오늘(이 문서 작성일) |
| 2026-12-25 | 금요일 | SPEC.md 예시 문장("…12월 25일까지 104일…")의 목표일 |

## Golden Test (총 26개 — 최소 5개 · 경계값 15개 이상 요건을 모두 상회)

### 모드 A: 날짜 차이

1. 시작일 2026-09-12, 목표일 2026-09-12 → `D-Day`, 차이 0.
2. 시작일 2026-09-12, 목표일 2026-09-13 → `D-1`.
3. 시작일 2026-09-12, 목표일 2026-09-11 → `D+1`.
4. 시작일 2026-09-12, 목표일 2026-12-25 → `D-104`, 목표일 요일 금요일, 주 환산
   `14주 6일 후`.
5. 시작일 2026-09-12, 목표일 2026-01-01 → `D+254`, 목표일 요일 목요일, 주 환산
   `36주 2일 전`.
6. 시작일 2026-12-31, 목표일 2027-01-01 → `D-1`(연말→연초 경계).
7. 시작일 1900-02-28, 목표일 1900-03-01 → `D-1`(1900년은 100년 규칙에 따라 평년).
8. 시작일 2000-02-28, 목표일 2000-03-01 → `D-2`(2000년은 400년 규칙에 따라 윤년).
9. 시작일 2024-02-28, 목표일 2024-03-01 → `D-2`(윤년).
10. 시작일 2028-02-28, 목표일 2028-03-01 → `D-2`(미래 윤년).
11. 시작일 2025-02-28, 목표일 2025-03-01 → `D-1`(평년, 9번·10번과 대조).
12. 시작일 1900-01-01, 목표일 1900-01-01 → `D-Day`(지원 범위 하한 경계 자체가 유효 입력).
13. 시작일 2200-12-31, 목표일 2200-12-31 → `D-Day`(지원 범위 상한 경계 자체가 유효 입력).
14. 목표일 2201-01-01(그 외 값 임의) → 오류(지원 범위 초과, 계산 거부).
15. 목표일 `"2024-02-30"` → 오류(존재하지 않는 날짜).

### 모드 B: 날짜 계산(더하기/빼기)

16. 기준일 2026-09-12, 일수 0, 더하기 → 결과 2026-09-12(요일 토요일), 정상(오류 아님).
17. 기준일 2026-09-12, 일수 104, 더하기 → 결과 2026-12-25(요일 금요일).
18. 기준일 2026-09-12, 일수 254, 빼기 → 결과 2026-01-01(요일 목요일).
19. 기준일 2026-12-31, 일수 1, 더하기 → 결과 2027-01-01(연말→연초 경계).
20. 기준일 2024-02-28, 일수 2, 더하기 → 결과 2024-03-01(윤년 경계).
21. 기준일 2000-01-01, 일수 10,000, 더하기 → 결과 2027-05-19(Hinnant `days_from_civil`/
    `civil_from_days` 손계산 교차검증 완료).
22. 기준일 2200-12-31, 일수 100,000(상한 값), 빼기 → 결과 1927-03-18(지원 범위 안,
    Hinnant 알고리즘 손계산 교차검증 완료).
23. 기준일 2000-01-01, 일수 100,000(상한 값), 더하기 → 산술 결과는 2273-10-16이나 지원
    범위(1900~2200)를 초과 → **계산 결과를 표시하지 않고 범위 초과 오류로 처리해야 한다**
    (상한 통과와 결과 범위 검증은 별개임을 보이는 핵심 케이스, "N 상한 근거" 참고).
24. 일수 100,001(상한 초과, 방향 무관) → 오류.

### 모드 A ↔ 모드 B 역함수 검증

25. 기준일 2026-09-12에 일수 104 더하기 → 2026-12-25. 이 결과를 모드 A에 시작일=
    2026-09-12, 목표일=2026-12-25로 넣으면 정확히 `D-104`가 나와야 한다(#4·#17과 값 일치).
26. 기준일 2026-09-12에서 일수 254 빼기 → 2026-01-01. 이 결과를 모드 A에 시작일=
    2026-09-12, 목표일=2026-01-01로 넣으면 정확히 `D+254`가 나와야 한다(#5·#18과 값 일치).

(#1~#5, #17~#18은 SPEC.md 본문이 직접 제시한 예시값과 일치하는 최우선 Golden Test다.)

## 알려진 제한

- 영업일·공휴일 제외 계산은 제공하지 않는다(SPEC.md "v1 범위 밖", `business-days` 계산기의
  영역).
- 인클루시브 카운트("만난 지 N일째")는 제공하지 않는다 — 날짜 차이 방식으로 통일한다.
- 음력 변환, 달력 기준 "N개월 N일" 환산은 제공하지 않는다(SPEC.md "Could Have"/"v1 범위
  밖").
- 1900-01-01 이전, 2200-12-31 이후 날짜는 지원하지 않는다(위 "지원 범위 확정 근거" 참고).
- 시:분:초 단위 정밀 카운트다운은 제공하지 않는다(달력일 단위까지만).
