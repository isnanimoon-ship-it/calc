## 2. Optimizer 수정 사항 실제 동작 확인

- **`MINIMUM_WAGE_HOURS_HINT` 위치**: 핵심 결과 카드 안, "2026년 최저임금 시간당 10,320원 ·

  텍스트로 렌더링됨을 확인(라이트/다크 모드, 320~1440px 전 구간). → **정상 동작**.
- **info 원형 아이콘 vs warning 삼각형 아이콘**: DOM에서 두 SVG path가 실제로 다름을
  확인(`info`: 원+세로선+점, `warning`: 삼각형+느낌표). 화면 스크린샷(라이트/다크 공통)에서도
  이중 배지 안내 박스(파란/프라이머리 톤)와 미충족 경고 카드(주황/warning 톤)가 색상·아이콘
  모두 명확히 구분됨. → **정상 동작**.
- **법령 조문 제목**: 정책 고지 섹션에 "최저임금법 시행령 제5조(최저임금의 적용을 위한
  임금의 환산)"이 정확히 표시됨을 `Accessibility.getFullAXTree`의 `StaticText` 노드
  텍스트로 직접 확인(과거 오기 "임금의 시간급 환산" 문자열은 페이지 어디에도 없음). →

## 4. 모바일 뷰포트 테스트 (320 / 375 / 390 / 768 / 1440px)

`Emulation.setDeviceMetricsOverride`로 5개 뷰포트 전부 에뮬레이션하고
`document.documentElement.scrollWidth vs clientWidth`로 가로 스크롤 발생 여부를 측정한 뒤
스크린샷으로 육안 확인했다(이중 배지 모순 시나리오 — 카드 수가 가장 많은 복잡한 상태 기준).

| 뷰포트 | 가로 오버플로 | 육안 확인 |
|---|---|---|
| 320px | 없음(`scrollWidth === clientWidth`) | 모드 토글 2열 유지, 입력 필드 잘림 없음, 핵심 카드 숫자(`2,152,442원`) 줄바꿈 없이 표시, 배지가 `flex-wrap`으로 2줄로 자연스럽게 줄바꿈, 이중 배지 안내 박스와 경고 카드가 겹치지 않고 순서대로 스택 |
| 375px | 없음 | 320px와 동일 패턴, 여유 폭 증가 |
| 390px | 없음 | 동일 |
| 768px | 없음 | 폼·카드 폭이 넓어지며 요소 간 여백이 넉넉해짐, 사용안내/소개는 아직 1열(lg 미만) |
| 1440px | 없음 | `max-w-6xl` 중앙 정렬, 사용안내·소개 섹션이 2열(`lg:grid-cols-2`)로 전환, 카드 레이아웃 깨짐 없음 |

전 구간에서 숫자 키패드 속성(`inputMode="numeric"`/`"decimal"`)이 실제 DOM에 존재함을
코드/속성 조회로 확인했고(터치 시 모바일 숫자 키패드가 뜨는 전제 조건 충족), 터치 영역은
버튼·라디오 레이블 모두 `py-3` 이상의 패딩으로 충분히 확보되어 있다.

→ **Mobile Critical Issue 0건. PASS.**

### 다크모드 확인(부가)
`<html>`에 `.dark` 클래스를 직접 주입해 390px에서 재확인 — 핵심 카드 그라디언트, 이중 배지
안내 박스(파란 톤), 경고 카드(주황 톤) 모두 라이트 모드와 동일하게 색상 구분이 유지되고
텍스트 대비도 충분함을 스크린샷으로 확인했다.

## 7. 접근성

- **라벨 연결**: 시급/월급 입력·주 근무시간 입력 모두 `<label htmlFor>`+`id`로 정상 연결됨을
  DOM에서 확인. `Accessibility.getFullAXTree` 조회 결과 `textbox` 노드의 접근 가능한 이름이
  "시급(원)"처럼 라벨+단위가 결합된 형태로 정확히 노출됨.
- **오류 안내**: 모든 필드 오류 시 `role="alert"` + `aria-invalid="true"` +
  `aria-describedby`(오류 id + help id 동시 포함)가 실제 DOM 속성으로 정확히 연결됨을
  확인(3.의 표 참고).
- **모드 토글(라디오 그룹) 구조**: `<fieldset><legend>계산 방향</legend>` 안에 동일한
  `name` 속성을 공유하는 진짜 `<input type="radio">` 2개(`sr-only`로 시각적으로만 숨김,
  `display:none`이 아니므로 포커스 가능)로 구현되어 있음을 확인.
  `Accessibility.getFullAXTree` 결과에서도 `role="radio"`, 정확한 접근 가능한 이름("시급으로
  계산"/"월급으로 계산"), `checked` tristate 값, `focusable=true`가 모두 올바르게 노출됨을
  확인했다. 네이티브 `<input type=radio>`+동일 `name` 조합은 브라우저가 자체적으로 화살표 키
  그룹 탐색을 제공하는 표준 HTML 시맨틱이므로(커스텀 JS 위젯이 아님), 구조적으로 키보드
  접근성이 보장된다.
- **아코디언(FAQ)**: `Accessibility.getFullAXTree`에서 FAQ 질문들이 `button` role +
  `focusable=true`로 노출됨을 확인(코드 리딩 기준 `aria-expanded`/`aria-controls`는
  `FaqAccordion` 공용 컴포넌트가 담당 — 이 계산기가 별도로 구현하지 않음, 기존 계산기와
  동일 컴포넌트 재사용이라 회귀 위험 없음).
- **결과 영역 `aria-live`**: 코드 리딩으로 결과 `<div aria-live="polite">`가 결과 섹션
  전체를 감싸는 것을 확인(DESIGN_SYSTEM.md 요건 충족).

**테스트 환경 한계(정직하게 기록)**: CDP `Input.dispatchKeyEvent`(rawKeyDown/keyDown 양쪽
시도, `Page.bringToFront` 포함)로 실제 하드웨어 키 입력을 시뮬레이션해 라디오 그룹의
ArrowRight/Tab 키보드 조작을 재현하려 했으나, 이 세션(원격/비대화형 데스크톱 환경으로
추정)에서는 CDP로 주입한 키 이벤트가 텍스트 입력 필드에도 문자를 전혀 삽입하지 못하는 등
브라우저에 전달되지 않는 것으로 보였다(OS 레벨 포커스가 필요한 Windows 입력 합성 특성으로
추정). 이 때문에 **라이브 키보드 조작 자체는 이번 세션에서 실행 확인하지 못했다** — 대신
위와 같이 `Accessibility.getFullAXTree`로 네이티브 라디오 시맨틱이 정확함을 구조적으로
검증했고, 이는 커스텀 위젯이 아니라 브라우저 기본 제공 키보드 동작에 의존하는 설계이므로
Critical/High로 분류하지 않는다(Low, 재현 가능한 실제 하드웨어/사용자 테스트 또는 다른 세션
환경에서 재확인 권고).

→ Critical/High 접근성 결함 없음. **PASS**(키보드 라이브 테스트는 환경 제약으로 미완료,
아래 "발견 이슈"에 재기록).
