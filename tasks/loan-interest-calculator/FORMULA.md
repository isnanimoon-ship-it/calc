# FORMULA: 대출 이자 계산기

## 목적
대출 원금·연이율·대출기간(개월)과 상환방식(원리금균등상환 / 원금균등상환 / 만기일시상환)을
입력받아, 상환방식별 회차별(월별) 상환 스케줄(원금 상환액·이자·잔액)과 총 이자·총 상환금액을
계산한다. SPEC.md가 명시한 대로 이 계산기는 **정책형 계산기가 아니다** — 금리는 사용자가
직접 입력하는 값이며 법령·고시 요율을 참조하지 않는다. 따라서 이 문서의 초점은 "기준 연도가
맞는가"가 아니라 **표준 재무수학 공식(연금 산식·균등분할 산식·만기일시 산식)이 정확히
유도·적용되었는가**이다.

## 공식 검증 결과 요약 (Formula Gate)
- 원리금균등상환 공식(연금 현재가치 공식에서 유도): **PASS** — 아래 "공식 ①" 유도 참고, 3개
  독립 출처(사담모아 계산기 설명, 계산기(calculator.net) 공식 예시, 토스피드 실사례)와 대조.
  단, calculator.net 대조(검증 예제 4)는 최초 버전에서 "달러 표시값을 그대로 1,000배
  스케일링"하는 방법론상의 오류로 Expected 값이 4원 틀려 있었던 것을 Builder·Calculation
  Auditor가 발견해 2026-09-06 정정했다 — 공식 유도 자체(이 PASS 판정)에는 영향이 없으며,
  자세한 경위는 아래 "검증 예제 4"를 참고.
- 원금균등상환 공식: **PASS** — 사담모아 계산기 설명과 대조, 자체 산술로 닫힌 형(closed-form)
  검증.
- 만기일시상환 공식: **PASS** — 사담모아 계산기 실제 예시 숫자와 대조.
- 월이율 = 연이율 ÷ 12(단순 나눗셈): **PASS** — 아래 "월이율 산정 방식" 참고, 3개 독립 출처가
  일관되게 이 방식을 확인.
- 반올림 시점·단위(회차마다 원 단위 반올림): **정책 결정(법적 강제 없음, 근거는 아래 "정밀도
  / 반올림 정책" 참고)** — 절사가 아니라 사사오입임은 실사례로 뒷받침되나, "사사오입 vs 올림"
  완전 특정은 **확인 필요**로 남김(아래 참고).

## 입력값
| 변수명 | 설명 | 단위 | 허용 범위 |
|---|---|---|---|
| `principal` (대출 원금) | 대출받는 원금 | 원 | 필수. 정수, 10,000원 이상 10,000,000,000원(100억원) 이하 |
| `annualRatePercent` (연이율) | 사용자가 `5`처럼 %로 입력(내부 계산 시 `/100`으로 소수 변환) | % | 필수. 0 이상 100 이하, 소수점 둘째 자리까지 허용(예: 4.25) |
| `termMonths` (대출기간) | 총 상환 회차 수. UI는 "개월" 직접 입력 또는 "년+개월" 조합 중 Architect/Builder가 결정하되 내부 계산은 항상 이 값(정수 개월)으로 통일 | 개월 | 필수. 정수, 1 이상 480(40년) 이하 |
| `repaymentMethod` (상환방식) | `equalInstallment`(원리금균등) / `equalPrincipal`(원금균등) / `bullet`(만기일시) 중 하나 | enum | 필수 |

### 입력 상한/하한 근거
법령·고시로 강제되는 값이 아니므로(정책형 아님), Formula Analyst가 아래 근거로 v1 기준값을
정한다 — Architect/Builder가 UX상 필요하면 조정할 수 있으나 변경 시 근거를 남길 것을 권장한다.
- **원금 하한(10,000원)**: 계산 자체는 1원 단위로도 성립하지만, "대출"이라는 제품 성격상
  비현실적으로 작은 값(예: 1원)까지 허용할 실익이 없다. 극소액에서도 공식이 깨지지는 않으므로
  법적 제약이 아니라 UX 방어값이다.
- **원금 상한(100억원)**: 은행권 개인신용대출·주택담보대출(SPEC.md가 못박은 v1 범위)을 넉넉히
  포괄하는 값. `Number`(IEEE754 double) 연산에서 원금×월이율×(1+월이율)^n 같은 곱셈이
  `Number.MAX_SAFE_INTEGER`(약 9×10^15)에 전혀 근접하지 않아 부동소수점 안전성에도 문제가
  없다.
- **연이율 상한(100%)**: 대부업법상 법정 최고금리(연 20%, 확인 필요 — 이 계산기는 법정 상한
  준수 여부를 판정하지 않는 순수 시뮬레이터이므로 이 상한을 강제하지 않는다)보다 훨씬 넉넉한
  값으로 잡아, 사용자가 극단적 조건도 시뮬레이션해볼 수 있게 하되 명백한 오타(예: "1000"을
  "10%" 대신 입력)는 차단한다.
- **대출기간 상한(480개월=40년)**: SPEC.md가 예시로 제시한 값을 그대로 채택. 국내 주택담보대출
  최장 만기(40년 상품 존재)를 포괄한다.
- **연이율 0%, 대출기간 1개월**은 하한이 아니라 유효한 경계값이며 아래 "예외"·"검증 예제"에서
  정상 계산 경로로 다룬다.

## 공식

### 월이율 산정 방식 — `monthlyRate = annualRatePercent / 100 / 12`
**단순 연이율 12분할을 채택한다** (복리 환산 `(1+연이율)^(1/12)-1` 방식은 채택하지 않는다).
근거(WebSearch/WebFetch로 3개 독립 출처 확인, 확인일 2026-09-06):
1. **사담모아(sangdammoa.com) 대출 계산기 설명 페이지**: "연 6%, 12개월 → 월이율 0.5%"라는
   예시를 명시적으로 제시 — `6% / 12 = 0.5%`, 단순 나눗셈과 정확히 일치(복리 환산이면
   `(1.06)^(1/12)-1 ≈ 0.4868%`가 되어 불일치).
2. **토스피드(toss.im/tossfeed) "대출 이자 계산 하는 3가지 방법"** 실사례: 원금 1억원, 연
   5%, 20년(240개월) 원리금균등상환 예시에서 1회차 이자를 416,667원으로 제시. 단순 12분할
   `100,000,000 × (0.05/12) = 5,000,000/12 = 416,666.67원 → 반올림 416,667원`과 정확히
   일치한다(복리 환산 방식이었다면 `100,000,000 × 0.4074%(연 5% 복리 월환산) ≈ 407,412원`이
   되어 전혀 다른 값이 나왔을 것 — 실제 값과 불일치).
3. **calculator.net Amortization Calculator**의 표준 예시(원금 $200,000, 연 6%, 15년=180개월
   → 월상환액 $1,687.71)도 `월이율=6%/12=0.5%` 단순 나눗셈으로 계산한 값과 정확히 일치
   (아래 검증 예제 4 — 단, 이 달러 표시값을 원화로 스케일링해 그대로 Expected로 쓰는 것에는
   한계가 있다. 예제 4의 "정정" 내용 참고).

세 출처 모두 국내·국외에서 널리 쓰이는 계산기이며 예외 없이 "연이율/12" 단순 나눗셈을 쓰는
것으로 확인됐다. **복리 월환산 방식을 쓴다는 출처는 발견하지 못했다.** 다만 이는 어디까지나
"월 단위로 미리 스케줄을 보여주는 계산기"의 관행이며, 실제 은행 시스템이 이자를 정산할 때는
계좌 개설일 기준 실제 경과일수(일할계산, 365일 또는 366일 기준)를 쓸 수 있어 실제 청구
금액과는 소액의 차이가 날 수 있다 — 이 한계는 결과 화면에 고지 문구로 반드시 노출한다(SPEC.md
화면 구성 8번 "단리/복리·월이율 산정 기준 등 계산 전제 고지").

### 공식 ① 원리금균등상환(Equal Installment / Annuity)

**유도**: n회 동일 금액 `A`를 매월 말 상환해 원금 `P`를 상환하는 것은, 은행 입장에서
"매월 `A`씩 n회 받는 연금의 현재가치가 대출 시점의 원금 `P`와 같다"는 조건과 동일하다(연금
현재가치 공식).
```
PV(연금) = A × [1 - (1+r)^-n] / r     (r = 월이율, n = 총 회차)
P = A × [1 - (1+r)^-n] / r
⇒ A = P × r / [1 - (1+r)^-n]
      = P × r × (1+r)^n / [(1+r)^n - 1]      … (SPEC.md이 제시한 식과 동일함을 확인)
```
**월이율 0%(r=0) 특수 케이스**: 위 식은 `r→0`일 때 분모·분자가 모두 0으로 가는 부정형이다.
`(1+r)^-n ≈ 1 - nr` (r→0의 1차 근사)이므로 `[1-(1+r)^-n]/r → n`이 되어
```
r = 0 일 때:  A = P / n
```
로 수렴한다(이 극한은 순수 수학적 도출이며 별도 외부 검증이 필요 없다). **Builder는 반드시
`r === 0`을 별도 분기로 처리해야 한다** — 부동소수점 나눗셈 `0/0`은 `NaN`을 반환하므로 그대로
두면 런타임 오류가 아니라 조용히 잘못된 결과(NaN)를 낼 위험이 있다.

**회차별 계산**(`r > 0`, `A`는 위 식으로 한 번만 계산):
```
이자_i        = 직전 잔액_(i-1) × r
원금상환액_i  = A - 이자_i
잔액_i        = 잔액_(i-1) - 원금상환액_i
(마지막 회차 n은 "마지막 회차 단수 처리" 정책에 따라 강제 보정 — 아래 참고)
```

### 공식 ② 원금균등상환(Equal Principal)
```
원금상환액_i(기준값) = P / n                    (매 회차 고정, 마지막 회차 제외)
이자_i               = 직전 잔액_(i-1) × r
상환액_i             = 원금상환액_i + 이자_i
잔액_i               = 잔액_(i-1) - 원금상환액_i
```
`P/n`이 정수 원으로 나누어떨어지지 않으면 반올림 정책에 따라 처리(아래 참고). 총 이자는
`P`가 `n`으로 정확히 나누어떨어지는 이상적인 경우 다음 닫힌 형(closed-form)으로 검증 가능하다
(등차수열 합):
```
totalInterest = r × P × (n+1) / 2     (P가 n으로 나누어떨어질 때 정확히 성립 — 검증 예제 6 참고)
```
나누어떨어지지 않는 경우 이 닫힌 형은 반올림에 따른 근사값이며, 정확한 총 이자는 실제 회차별
스케줄(반올림 포함)을 합산해 산출해야 한다(검증 예제 9에서는 우연히 정확히 일치함을 확인했으나
이는 일반적으로 보장되는 성질은 아니다 — Builder는 닫힌 형이 아니라 실제 스케줄 합계를
`totalInterest`로 채택해야 한다).

### 공식 ③ 만기일시상환(Bullet Repayment)
```
이자_i(1 ≤ i < n) = P × r                        (고정, 잔액이 만기까지 줄지 않으므로)
상환액_i(1 ≤ i < n) = 이자_i                       (원금 상환 없음)
이자_n(마지막 회차)  = P × r                        (직전 회차와 동일)
상환액_n(마지막 회차) = P + 이자_n                   (원금 전액 + 마지막 달 이자)
totalInterest        = P × r × n
```
사담모아(sangdammoa.com) 계산기 설명 페이지가 제시한 실제 예시(원금 1,000만원, 연 6%, 12개월
→ "총이자 = 10,000,000 × 0.005 × 12 = 600,000원")와 정확히 일치(검증 예제 10).

### 세 방식의 총 이자 크기 관계 (완료 기준 불변식)
동일한 `P·r·n`(단, `r>0, n>1`)에서, 실무적 입력 범위(연이율 0~50% 내외 — SPEC.md가 정의한
은행권 개인신용대출·주택담보대출의 현실적 금리 범위를 넉넉히 포괄)에서는 `만기일시상환
총이자 > 원리금균등상환 총이자 > 원금균등상환 총이자`가 **항상 엄격하게(초과, `>`)** 성립한다.
다만 입력 상한의 정확한 극단에서는 반올림으로 인해 동률이 될 수 있음이 확인됐다(각주[^1] 참고).
이를 반영해 이 계산기의 "완료 기준" 불변식은 엄격한 초과가 아니라 **동률을 허용하는 이상
(`≥`)**으로 정의한다: `만기일시상환 총이자 ≥ 원리금균등상환 총이자 ≥ 원금균등상환 총이자`.
- **만기일시가 최대(또는 동률)인 이유**: 잔액이 만기까지 전혀 줄지 않아 매 회차 이자 계산의
  기준(잔액)이 항상 `P`로 최대값이다. 다른 두 방식은 잔액이 매 회차 감소하므로 이자 계산 기준이
  `P`보다 항상 작거나 같다 — 따라서 총 이자가 만기일시보다 클 수 없다.
- **원금균등이 최소(또는 동률)인 이유**: 원금균등은 첫 회차부터 `P/n`을 고정으로 상환해 잔액을
  "선형적으로" 빠르게 줄인다. 원리금균등은 초기 회차의 상환액 중 이자 비중이 커 원금 상환이
  느리게 시작되므로(원금균등 대비 초반 잔액이 더 천천히 줄어듦), 평균 잔액이 원금균등보다
  높고 따라서 누적 이자도 더 크다. 이는 상환액 구성(원금·이자 비율)의 구조적 차이에서 비롯되는
  재무수학의 일반적 성질이며, 검증 예제 13에서 구체적 수치로 재확인한다.
- `r=0` 또는 `n=1`일 때는 세 방식이 수렴한다(검증 예제 1·2·7·8·11·12 참고) — 불변식은
  `n>1, r>0`을 전제로 한다.

[^1]: Calculation Auditor가 `logic.ts`를 참조하지 않는 독립 재구현으로 입력 상한의 정확한
  극단(원금 100억원 · 연이율 100% · 대출기간 480개월 — 세 값 모두 v1 허용 상한)을 재현한
  결과, 원리금균등상환 앵커값(`A`)과 만기일시상환 고정이자(`I = P×r`)의 실제 수학적 차이가
  약 1.7×10⁻⁸원(Decimal 80자리 정밀도로 확인)에 불과해, 원 단위 반올림 시 두 값이 완전히
  동일한 정수(833,333,333원)로 반올림됐다. 그 결과 원리금균등상환의 매 회차 원금상환액이
  479회 연속 0으로 계산돼(만기일시상환과 구분되지 않는 스케줄로 퇴화) 두 방식의
  `totalInterest`가 정확히 동일(399,999,999,840원)해졌다. **이는 계산 오류나 부동소수점
  버그가 아니다** — 고정밀도 재계산으로 실제 수학적 차이가 반올림 단위(1원)보다 작다는 것을
  확인했으며, 반올림 정책(원 단위 사사오입)을 정확히 적용한 결과다. "완료 기준" 불변식 중
  `Σ회차별 원금상환액 = 대출 원금`, `마지막 회차 이후 잔액 = 0`은 이 극단 케이스에서도 여전히
  정상 성립한다(마지막 회차 강제 보정 덕분, 코드로 확인됨). 연이율 20%×480개월, 연이율
  15%×360개월 등 이보다 훨씬 공격적인 조합에서는 재현되지 않으며, 오직 입력 범위의 정확한
  양 극단(100%×480개월)에서만 나타난다 — 현실적 대출 조건(SPEC.md 범위)에서는 실사용 영향이
  없다. 근거: `tasks/loan-interest-calculator/EVALUATION.md` "Calculation Auditor" 절
  "3. 신규 발견" (2026-09-06 확인).

## 계산 순서
1. 입력 검증(원금·연이율·대출기간 범위, 상환방식 선택 여부) — 하나라도 실패하면 계산 중단.
2. `monthlyRate = annualRatePercent / 100 / 12` 계산.
3. 상환방식별 "앵커 값" 계산(전체 정밀도, 부동소수점):
   - 원리금균등: `A = P × r × (1+r)^n / [(1+r)^n - 1]` (r=0이면 `A = P/n`)
   - 원금균등: `base = P / n`
   - 만기일시: `I = P × r`
4. 앵커 값을 원 단위로 **한 번만** 반올림해 정수로 고정(`A_fixed` / `base_fixed` / `I_fixed`) —
   이후 회차 반복 계산은 이 정수값을 그대로 재사용한다(반복마다 다시 반올림하지 않음).
5. 1회차부터 `n-1`회차까지 반복:
   - `이자_i = round(잔액_(i-1) × r)` (원 단위 반올림)
   - 원리금균등: `원금상환액_i = A_fixed - 이자_i`, 상환액_i = `A_fixed`
   - 원금균등: `원금상환액_i = base_fixed`, 상환액_i = `base_fixed + 이자_i`
   - 만기일시: `이자_i = I_fixed`(재계산 불필요, 잔액이 불변이므로 항상 동일), `원금상환액_i = 0`, 상환액_i = `I_fixed`
   - `잔액_i = 잔액_(i-1) - 원금상환액_i`
6. **마지막 회차(n)는 강제 보정**한다(아래 "마지막 회차 단수 처리" 참고) — 잔액이 정확히 0으로
   끝나도록 원금상환액을 "남은 잔액 전액"으로 강제 설정.
7. `totalInterest = Σ schedule[i].이자`, `totalPayment = principal + totalInterest`.
8. 연도별 요약(`yearlySummary`)은 회차별 스케줄을 12개월 단위(마지막 해는 나머지 개월)로
   묶어 원금 합계·이자 합계·연말 잔액을 집계.

## 단위
- 원금·이자·상환액·잔액: 원(KRW), 정수(원 미만 단위 없음 — 근로기준법 평균임금처럼 "전" 단위
  정밀도가 법적으로 요구되는 계산이 아니므로 원 단위 반올림으로 충분하다).
- 연이율: 입력은 `%`(예: `5`), 내부 계산은 소수(`0.05`)로 분리해서 다룬다(`docs/DESIGN_SYSTEM.md`
  "입력 UX" 원칙).
- 월이율(`monthlyRate`): 무차원 소수(예: `0.0041666...`), 반올림하지 않고 계산식에 그대로 사용.
- 대출기간: 입력 UX(개월 단독 vs 년+개월)는 Architect/Builder 결정 사항이나, 내부 계산은 항상
  정수 "개월"(`termMonths`)로 통일한다.

## 정밀도 / 반올림 정책

### 핵심 결정: 회차(행)마다 원 단위로 반올림해 확정하고, 그 확정값을 다음 회차 계산에 재사용한다
`docs/CALCULATOR_RULES.md` "반올림 정책"은 "중간 계산 단계에서 임의로 반올림하지 않는다,
가능하면 최종 표시 단계에서만 formatting한다"는 일반 원칙을 제시하되 "계산기마다 무엇을
쓰는지 FORMULA.md에 명시한다"는 재량도 함께 준다. 이 계산기는 아래 근거로 **회차별 원 단위
확정** 방식을 채택한다(퇴직금 계산기가 채택한 "완전정밀도 유지" 방식과 다른 결론이며, 그
이유는 계산기 성격이 다르기 때문이다 — 아래 설명).
- **이 계산기의 "표시 단계"는 최종 합계 한 줄이 아니라 회차별 스케줄표 자체다.** SPEC.md는
  "연도별 상환 스케줄 요약표"를 Must Have로 요구하고, 사용자는 이 표를 자신이 실제 보유한
  대출의 은행 앱/상환안내서와 대조할 가능성이 높다. 즉 각 회차의 값 자체가 이미 "최종 표시
  값"이므로, 그 값을 다음 회차 계산에 그대로 재사용하는 것은 "표시 단계에서만 반올림한다"는
  원칙과 상충하지 않는다 — 오히려 회차마다 이미 표시되는 값과 실제 계산 근거를 일치시킨다.
- **실사례 근거**: 토스피드가 공개한 실제 계산 예시(원금 1억원, 연5%, 240개월,
  원리금균등상환)에서 1회차 이자가 정확히 `100,000,000 × (0.05/12) = 416,666.666...→
  416,667원`으로 **정수 원 단위로 반올림되어 표시**된다(위 "월이율 산정 방식" 참고). 이는
  최소한 이 값이 "절사(버림)"는 아님을 확인해준다(절사였다면 416,666원이어야 한다).
- **부동소수점 안전성**: 회차마다 원 단위 정수로 확정하면 다음 회차 입력(잔액)도 항상 정수이므로,
  `balance × rate` 한 번의 곱셈에서만 소수가 발생하고 즉시 반올림해 제거된다. 완전정밀도를
  n=480회차까지 유지하는 방식보다 부동소수점 오차 축적 위험이 오히려 낮다.

### 반올림 방법: 사사오입(반올림, round-half-up)
Toss 예시(416,666.666... → 416,667)는 사사오입과 올림(ceiling) 모두와 부합해 두 방식을
구분하지 못한다(둘 다 416,667을 준다). **v1은 사사오입을 기본 정책으로 채택**한다 — 근거는
(1) 이 계산기는 근로기준법 평균임금처럼 "근로자에게 불리하지 않게 올림한다"는 식의 법적·행정
해석이 존재하는 영역이 아니라 순수 시뮬레이션 도구이고, (2) 일반적인 재무 소프트웨어(Excel
`ROUND` 계열, 대다수 국내외 대출 계산기)가 반올림을 기본으로 쓰는 것이 통상적이기 때문이다.
**"절사(은행이 예금 이자 지급 시 원단위 절사를 하는 관행이 대출 상환액 표시에도 동일하게
적용되는지"는 확인하지 못했다 — 확인 필요로 남긴다.** Calculation Auditor가 특정 은행의
실제 절사 관행을 소스코드/약관으로 확인하면 이 정책은 재검토 대상이다.

### 앵커 값(A/base/I)은 "한 번만" 반올림한다
회차마다 `A`(원리금균등 고정 상환액)를 다시 계산·반올림하지 않는다. `A`는 최초 1회 전체
정밀도로 계산한 뒤 정수로 반올림해 고정하고, 그 정수값을 1회차부터 (n-1)회차까지 그대로
반복 사용한다(마지막 회차만 예외 — 아래 참고). 원금균등의 `base = P/n`도 동일하게 최초 1회만
반올림해 고정한다.

### 마지막 회차 단수 처리
원리금균등·원금균등상환 모두 다음 규칙을 적용한다.
```
마지막 회차(n)의 원금상환액 = 직전(n-1) 회차까지의 잔액 전액 (강제, 재계산하지 않음)
마지막 회차의 이자           = round(직전 잔액 × 월이율)   (다른 회차와 동일한 방식으로 계산)
마지막 회차의 상환액         = 마지막 원금상환액 + 마지막 이자
마지막 회차 이후 잔액        = 정확히 0
```
이렇게 강제하는 이유: 매 회차 원 단위 반올림을 적용하면(예: 원금균등에서 `P/n`이 나누어떨어지지
않을 때) 1~(n-1)회차의 반올림 오차가 누적되어, 순수 이론식(반올림 없이 이어감)으로 계산한 마지막
잔액이 정확히 0이 되지 않을 수 있다. 이 오차를 마지막 회차 하나에 몰아 흡수시키는 것은 실제
금융권 상환 스케줄의 통상적 관행이며(예: calculator.net의 amortization schedule도 마지막 회차
상환액이 나머지 회차와 근소하게 달라지는 것으로 확인 — 검증 예제 4 참고), **이 계산기의
"완료 기준" 불변식**("Σ회차별 원금 상환액 = 대출 원금", "마지막 회차 이후 잔액은 0")을 항상
성립시키는 유일하게 안전한 방법이기도 하다.
- **원리금균등상환에서는 마지막 회차 상환액이 다른 회차의 고정 상환액(`A_fixed`)과 1~수 원
  차이 날 수 있다.** 이는 버그가 아니라 정상적인 반올림 잔여 처리이므로, 화면에 "마지막 회차는
  잔액 정산으로 금액이 near 다를 수 있습니다" 같은 안내 문구를 둘 것을 권장한다(UX 결정은
  Architect/Builder 재량).
- **만기일시상환은 이 문제가 없다** — 원금이 만기 전까지 전혀 상환되지 않으므로 반올림 누적
  오차가 발생할 여지가 없다(매 회차 이자 `I_fixed`가 항상 동일).

### 구현 시 숫자 표현 권장(Architect 참고용, 강제 아님)
`docs/CALCULATOR_RULES.md`가 숫자 표현(Number/정수 스케일링/BigInt/decimal.js) 선택을
Architect 재량으로 위임하므로 강제하지는 않되, Formula Analyst 의견을 남긴다: 잔액·원금상환액·
이자·상환액은 항상 정수 원이므로 일반 `Number`로 충분하다(최대값 100억원 규모, 480회 반복에도
`Number.MAX_SAFE_INTEGER` 대비 여유가 크다). `(1+r)^n` 계산(원리금균등 앵커 값 계산 1회)만
부동소수점 지수 연산이 필요하며, 이후 회차 반복은 정수 연산으로 충분하다.

## 예외
- **원금·연이율·대출기간 누락/형식 오류**: 숫자가 아님, 음수, 0 이하(원금·기간의 경우) 등은
  계산하지 않고 해당 필드 오류 표시.
- **원금 0 이하**: 오류(대출이 성립하지 않음).
- **연이율 0%**: 정상 계산 경로(위 "공식 ①" 특수 분기 참고, 세 방식 모두 지원 — 검증 예제
  2·8·12).
- **대출기간 0개월 이하**: 오류(회차가 존재하지 않아 계산 자체가 성립하지 않음).
- **대출기간 1개월**: 정상 계산 경로 — 세 방식이 모두 동일한 결과로 수렴(검증 예제 1·7·11).
- **연이율 음수**: 오류(음리 대출은 v1 범위 밖이며 일반적 대출 상품에 존재하지 않음).
- **상환방식 미선택**: 계산 자체를 수행하지 않고 선택을 요구.
- **원금·연이율·대출기간이 입력 상한을 초과**: 계산하지 않고 오류 표시("입력 상한/하한 근거"
  절 참고).
- **원금균등상환에서 `P/n`이 정수로 나누어떨어지지 않는 경우**: 오류가 아니라 정상 경로 —
  "마지막 회차 단수 처리" 정책에 따라 처리(검증 예제 9).

## 검증 예제 (Golden Test 후보, 13개)

### 예제 1 — 원리금균등상환, 대출기간 1개월(경계값)
- Input: `principal=5,000,000`, `annualRatePercent=12`, `termMonths=1`, `repaymentMethod=equalInstallment`
- 계산: `monthlyRate=0.01`. `n=1`이므로 `A = P×r×(1+r)^1/[(1+r)^1-1] = P×r×(1+r)/r = P×(1+r) = 5,000,000×1.01 = 5,050,000`.
- Expected: 1회차(=마지막 회차) 이자=50,000원, 원금상환액=5,000,000원, 상환액=5,050,000원, 잔액=0. `totalInterest=50,000원`, `totalPayment=5,050,000원`.
- 라벨: 자체 산출(수식 자체가 대수적으로 정확 — 외부 대조 불필요한 항등식). n=1에서 세 방식이 모두 수렴함을 예제 7·11과 함께 확인.

- Input: `principal=200,000,000`(=calculator.net 예시 $200,000을 1,000배 스케일링 — 연금

- 출처: calculator.net Amortization Calculator, 기본 예시 `$200,000 / 15년(180개월) / 연6%
  → 월상환액 $1,687.71, 총이자 $103,788.46, 총상환액 $303,788.86`(WebFetch 확인, 확인일
  2026-09-06). $100,000/15년/6%의 표준 월상환액 $843.86(재무 교재에 흔히 인용되는 값)의
  2배와도 일치해 신뢰도가 높다.
- **[2026-09-06 정정] Expected: `fixedMonthlyPayment = 1,687,714원`.** (이전 버전은
  `1,687,710원`을 "검증 완료"로 잘못 기재했다 — Builder가 구현 중 발견, Calculation
  Auditor가 Python `Decimal`(정밀도 50~60자리) 독립 재계산으로 재확인, 이번 FORMULA.md
  정정 과정에서 수기 근사 검산으로 재차 확인함.)
  - **오류 원인 — "반올림 후 스케일링" ≠ "스케일링 후 반올림"**: calculator.net이 화면에
    표시하는 `$1,687.71`은 `$200,000` 스케일에서 공식을 계산한 원값
    `$1,687.71365609690262...`를 **센트 단위(소수 둘째 자리)로 이미 반올림한 결과**다(세
    번째 소수 자리가 `3`이라 내림 처리됨 — calculator.net 자체의 계산은 정확하다). 이전
    버전 FORMULA.md는 이 **이미 반올림된** `$1,687.71`을 그대로 1,000배 스케일링해
    `1,687,710원`을 Expected 값으로 채택했는데, 이는 반올림 과정에서 이미 소실된 소수
    정보(`$0.0036...`)를 스케일링으로도 복구하지 못한 채 그대로 부풀린 것이다. 실제로는
    원금 200,000,000원이라는 **실제 스케일에서 공식(`A = P×r×(1+r)^n/[(1+r)^n-1]`,
    P=200,000,000, r=0.005, n=180)을 직접 계산**해야 정확한 값이 나온다 — 원값
    `1,687,713.656...원`을 원 단위로 반올림하면 `1,687,714원`이며, `1,687,710원`과는
    4원 차이가 난다.
  - **일반화(향후 유사 실수 방지 주석)**: 외화(또는 다른 통화) 단위로 공개된 공식 계산기의
    "표시값"을 특정 배수로 스케일링해 Golden Test 값으로 삼을 때, 그 표시값 자체가 이미 그
    통화의 최소 단위(예: 센트)로 반올림되어 있다는 점을 놓치기 쉽다. **이런 스케일링 대조는
    "산식의 구조·비율이 맞는지"(예: 월이율 산정 방식이 6%/12=0.5%가 맞는지) 검증하는 데는
    유효하지만, 정수 원 단위 최종값의 정확한 반올림 결과를 검증하는 골든 테스트로는
    부적합하다.** 정수 단위 최종값을 검증하려면 항상 실제로 사용할 스케일(이 계산기라면
    "원")에서 공식을 직접 계산한 값과 대조해야 한다.
  - **`totalInterest`도 이 정정된 값 기준으로 재확인**: 정정된 `fixedMonthlyPayment=
    1,687,714원`을 단순히 `A×n - P`로 계산한 "이론상" 값은
    `1,687,714×180-200,000,000=103,788,520원`이지만, 이 계산기의 정책상 정확한
    `totalInterest`는 단순 곱셈이 아니라 **회차별 스케줄 합산(마지막 회차 강제 보정
    반영)으로 확정**해야 한다(위 "공식 ②" 절의 닫힌 형 vs 실제 합산 논의, "계산 순서" 7단계
    참고). 회차별 스케줄 전체(180행)를 합산해 확정한 정확한 값은
    `totalInterest=103,788,417원`이다(Calculation Auditor가 `logic.ts`를 참조하지 않는
    독립 스크립트로 전체 스케줄을 재현해 확인했으며 Builder의 Golden Test 값과 정확히
    일치 — `tasks/loan-interest-calculator/EVALUATION.md` "Calculation Auditor" 절
    참고). 이에 따라 `totalPayment = 200,000,000 + 103,788,417 = 303,788,417원`이다.
  - **calculator.net 자체 보고값(총이자 $103,788.46, 스케일링 시 103,788,460원)과의
    약 43원 차이는 오차가 아니라 반올림 격자(rounding grid) 단위가 다르기 때문**이다 —
    calculator.net은 `$200,000` 스케일에서 센트(0.01달러, 스케일링 시 10원에 해당) 단위로
    반올림하고, 이 계산기는 `200,000,000원` 스케일에서 원(1원) 단위로 반올림한다. 스케일링을
    거쳐도 두 계산의 반올림 격자 자체가 다르므로(10원 단위 vs 1원 단위) 정수 원 단위까지
    정확히 일치할 이유가 없다 — 이 역시 위와 동일한 "달러 스케일 대조는 정수 최종값 검증에는
    부적합하다"는 교훈의 연장선이며, 더 이상 정정이 필요한 불일치가 아니다.
- 라벨: **공식 계산기 대조**(라벨 유지). 다만 정정 내용대로, 이 예제가 실제로 강하게 검증하는
  것은 "연금 현재가치 공식의 구조와 월이율 산정 방식(6%/12=0.5%)이 옳다"는 점이다.
  `fixedMonthlyPayment`·`totalInterest`의 **정수 원 단위 최종값**은 원 스케일에서 공식을
  직접 계산한 결과(위 정정값, 1,687,714원 / 103,788,417원)를 Golden Test 기준으로 삼으며,
  calculator.net의 달러 표시값을 그대로 1,000배 스케일링한 값은 참고용일 뿐 정수 단위 정밀
  대조 기준으로 쓰지 않는다.

## 확인 필요 목록 (Formula Analyst가 추정하지 않고 남기는 항목)
1. **반올림 방법의 완전한 특정**: 회차별 반올림이 "사사오입"인지 "올림(ceiling)"인지 100%
   확정하지 못했다(Toss 예시 하나만으로는 두 방식을 구분할 수 없음, 위 "반올림 방법" 참고).
   v1은 사사오입을 정책으로 채택했으나, 이후 특정 은행의 실제 계산 스크립트(예: severance-pay가
   moel.go.kr 소스코드를 직접 확인했던 방식)를 확보하면 재검토 대상이다.
2. **은행권 원단위 절사 관행이 대출 상환액 표시에도 적용되는지**: 예금 이자에는 원단위 절사
   관행이 있다고 알려져 있으나(2차 출처 수준), 이것이 "대출 상환액"에도 동일하게 적용되는지는
   확인하지 못했다.
3. **토스피드 16회차 예시의 1원 오차 원인**: 본문 "예제 5" 참고 — 원문 표기상의 반올림 처리
   차이로 추정되나 확정하지 못했다.
4. **실제 은행 상환 스케줄의 일할(day-count) 계산 편차 크기**: 이 계산기는 월 단위 근사
   (연이율/12)만 다루므로, 실제 대출 실행일 기준 일할계산과의 정확한 차이 폭은 산정하지 않았다
   (SPEC.md 범위 밖 — 화면 고지 문구로만 안내).
