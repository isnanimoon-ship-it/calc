# FORMULA: 더치페이 계산기

## 목적

`SPEC.md`가 정의한 세 가지 분배 방식(균등 분배 / 한명 몰아주기 / 인원별 금액설정(사다리타기))의
계산 로직을 정의한다. 이 계산기는 법령·고시를 참조하는 정책형 계산기가 아니다. "계산
정확성"은 다음 두 가지로 재정의된다(SPEC.md "목적" 절):

1. **산술 정확성** — 배분액의 합이 항상 입력 총액과 정확히 일치한다(균등 분배의 나머지 처리).
2. **공정성(편향 없음)** — 무작위 선정(몰아주기)·무작위 매칭(사다리타기)이 실제로 균등한
   확률/분포를 따른다. 이는 법령 대조가 아니라 **알고리즘의 수학적 논증 + 통계적 시뮬레이션
   검증**으로 확인한다.

따라서 이 문서의 "기준/출처"는 법령 조항이 아니라 **표준 알고리즘 출처(Fisher-Yates shuffle
등)와 통계 검정 방법론 출처**를 기록한다(문서 말미 참고).

## 핵심 설계 결정 요약

| 항목 | 결정 | 근거 |
|---|---|---|
| 균등 분배 나머지 처리 | 입력 순서상 **앞쪽 `remainder`명**에게 1원씩 추가 배분(결정적, 무작위 아님) | 아래 "공식 ①" 참고 — 예측 가능하고 사용자에게 설명 가능해야 한다는 SPEC 요건 |
| 몰아주기 RNG | `Math.floor(Math.random() * N)` (N ≤ 20에서 모듈로 편향 무시 가능) | 아래 "공식 ②" 및 "모듈로 편향 검토" 참고 |
| 사다리타기 셔플 | Fisher-Yates(Durstenfeld) shuffle, `Array.sort(() => Math.random()-0.5)` 금지 | 아래 "공식 ③" 및 "왜 Fisher-Yates인가" 참고 |
| 통계 검증 방법 | 카이제곱 적합도 검정, 시행 10,000회 이상, 유의수준 α=0.05 | 아래 "공정성 통계 검증 공통 절차" 참고 |
| 멤버 식별 기준 | 이름 문자열이 아니라 **배열 인덱스(순서)** 를 내부 식별자로 사용 | 이름 중복이 알고리즘 정확성에 영향을 주지 않게 하기 위함 |

## 공통 설계 원칙

- 세 방식 모두 **선정/매칭 로직은 순수 함수**로 구현되어야 한다(입력 → 출력이 결정적으로
  검증 가능해야 하며, 애니메이션·DOM에 접근하지 않는다). 이는 SPEC.md Must Have "계산·선정·
  매칭 로직은 UI와 분리된 순수 함수" 요건과 동일하며, Calculation Auditor가 이 순수 함수를
  독립적으로 수천~수만 회 호출해 통계 검증을 하기 위한 전제조건이다.
- 몰아주기·사다리타기는 **RNG를 함수 인자로 주입 가능**하게 설계할 것을 권장한다(예:
  `pickWinner(members, rng = Math.random)`, `shuffle(amounts, rng = Math.random)`). 이렇게
  하면 (1) 결정적 단위 테스트(고정 시퀀스 주입)와 (2) 실제 `Math.random()`을 사용한 대량
  통계 시뮬레이션 테스트를 같은 함수로 모두 수행할 수 있다. 이 주입 인터페이스의 구체적 타입
  시그니처는 Architect/Builder가 정한다 — FORMULA는 "테스트를 위해 RNG를 교체할 수 있어야
  한다"는 요건만 규정한다.
- **멤버의 내부 식별자는 이름이 아니라 입력 배열의 인덱스(순서)다.** 이름은 표시용이며 중복
  이름이 있어도 선정·매칭 알고리즘은 인덱스로 동작하므로 정확성에 영향이 없다(이름 중복·빈
  이름 처리 정책 자체는 SPEC.md에 따라 Architect/Builder가 UI 레벨에서 결정).
- 애니메이션 유무와 결과가 절대 달라져서는 안 된다 — "먼저 결과를 계산 → 그 결과에 맞춰
  애니메이션 목표 지점을 설정"하는 순서를 모든 방식에서 지킨다(아래 "계산 순서" 참고).

## 입력값

| 변수명 | 설명 | 단위 | 적용 모드 | 허용 범위 |
|---|---|---|---|---|
| `totalAmount` (총 금액) | 나눌 총 비용 | 원(KRW), 정수 | 균등, 몰아주기 | 1 이상 100,000,000(1억) 이하 정수 — **상한은 잠정 제안값, 확인 필요(Architect 확정)** |
| `members[]` (멤버 이름 목록) | 참여자 이름, 입력(추가) 순서가 배열 인덱스를 결정 | 문자열 배열 | 공통 | 길이 2 이상 20 이하(SPEC.md 잠정 상한, 최종 확정은 Architect) — 각 원소 빈 문자열 불가 |
| `amounts[]` (인원별 금액 목록) | 각 멤버가 낼 금액 후보(사다리타기 전용, 매칭 전 목록) | 원(KRW), 정수 배열 | 사다리타기 | 길이 = `members.length` (항상 동일, 불일치 시 계산 차단). 각 원소 1 이상 100,000,000 이하 정수 — 중복 값 허용 |

이름 글자 수 제한은 알고리즘 정확성과 무관한 UI 사안이므로 FORMULA에서 강제하지 않는다(Architect/
PO 재량, 예: 1~20자 권장).

### 입력 상·하한 근거 (확인 필요 포함)

- **총 금액/개별 금액 상한 1억원**: SPEC.md가 구체적 상한을 정하지 않아 Formula Analyst가
  잠정 제안한다. 회식·모임 비용이라는 제품 성격상 1억원을 초과하는 입력은 비현실적이며,
  `Number`(IEEE754 double) 연산에서도 `1억 × 20`(전체 합) 규모는
  `Number.MAX_SAFE_INTEGER`(약 9×10^15) 대비 전혀 문제되지 않는다. **확인 필요**: 이 값은
  법령 근거가 아니라 UX 방어값이므로 Architect가 실제 사용 시나리오를 보고 조정할 수 있다.
- **멤버 수 2~20명**: SPEC.md Must Have가 정한 잠정값을 그대로 채택한다. 최종 확정(애니메이션
  렌더링 성능/가독성 검증)은 Architect 몫이며, FORMULA의 알고리즘(균등 분배 나머지 처리,
  RNG 선정, Fisher-Yates 셔플)은 N이 2~20 범위를 벗어나도(예: N=50) 수학적으로 동일하게
  성립하므로 상한 변경이 있어도 이 문서를 재검토할 필요는 없다 — 단, 아래 "공정성 통계 검증"의
  일부 절차(소규모 N 전수 순열 검증)는 N이 커지면 적용 범위가 달라진다(해당 절 참고).

## 공식

### 공식 ① 균등 분배 — 나머지(잔돈) 처리 규칙

```
n = members.length
baseShare = floor(totalAmount / n)
remainder = totalAmount mod n         // 0 <= remainder < n, JS: totalAmount % n (totalAmount>0이므로 부호 문제 없음)

for i in 0..n-1:
  shares[i].amount = baseShare + (i < remainder ? 1 : 0)
```

**규칙**: 입력 순서(멤버 배열의 인덱스 0부터)상 **앞쪽 `remainder`명**에게 1원씩 추가
배분하고, 나머지 인원은 `baseShare`를 그대로 받는다.

**왜 이 규칙인가(결정적·예측 가능해야 한다는 요건, SPEC.md/작업 지시 참고)**:
- 무작위로 나머지를 배분하면 "균등 분배는 애니메이션 없이 즉시 결과를 보여준다"는 SPEC 요건과
  충돌한다(무작위 요소가 있으면 재계산 시 결과가 달라지고, "왜 이 사람만 1원 더 내는지"를
  설명할 수 없다). 인덱스 기반 결정적 규칙은 같은 입력에 대해 항상 같은 결과를 내고, 화면에
  "입력한 순서상 앞쪽 N명에게 1원씩 추가로 배분되었습니다"라는 근거 문구로 설명 가능하다.
- 대안으로 "뒤쪽 N명에게 배분", "가나다순 정렬 후 배분" 등도 산술적으로는 동등하게 총액과
  일치하지만, "입력 순서 그대로 앞에서부터"가 가장 단순하고 별도 정렬·조작이 필요 없어 구현
  복잡도가 가장 낮다. 이 규칙 자체는 법적 강제가 아니라 Formula Analyst의 설계 선택이다.
- **불변식**: `Σ shares[i].amount === totalAmount`가 모든 입력에서 항상 성립한다. 증명:
  `Σ baseShare = n × baseShare`, 여기에 `remainder`명에게 1원씩 추가하면
  `n×baseShare + remainder = n×floor(totalAmount/n) + (totalAmount mod n) = totalAmount`
  (정수 나눗셈의 정의 자체가 이 항등식을 보장한다).

**경계**: `remainder = 0`이면 전원 `baseShare`로 동일(1번 추가 배분 없음). `remainder = n-1`
이면 마지막 1명만 `baseShare`, 나머지 전원이 `baseShare+1`을 받는다. `totalAmount < n`이면
`baseShare = 0`이 되어 일부 멤버는 0원을 받을 수 있다(수학적으로 정상, 아래 "예외" 참고).

### 공식 ② 한명 몰아주기 — 균등 무작위 선정

```
function pickWinnerIndex(n, rng = Math.random):
  return Math.floor(rng() * n)   // n = members.length, 결과는 0..n-1의 정수
```

`shares[i].amount = (i === selectedIndex) ? totalAmount : 0`

**균등 분포 논증(모듈로 편향 검토)**: 흔히 알려진 "모듈로 편향(modulo bias)"은 정수 난수
생성기의 출력 범위가 목표 범위 `N`으로 나누어떨어지지 않을 때(예: 0~255 범위 난수를 `% 6`
연산으로 6면체 주사위에 매핑) 특정 값이 근소하게 더 자주 나오는 현상이다. `Math.random()`은
정수가 아니라 `[0, 1)` 구간의 부동소수점을 반환하며, 사양상 배정밀도(53비트 가수) 기준
2^53개의 균등 간격 값 중 하나를 반환한다(V8 등 주요 엔진 구현). `Math.floor(rng() * n)`은
이 `[0,1)` 구간을 `n`개의 동일한 폭(`1/n`)의 구간으로 나누는 것과 같다.

- `2^53`이 `n`(2~20)으로 나누어떨어지지 않을 때 이론상 미세한 편향이 존재할 수 있으나, 그
  크기는 최대 `1/2^53`(약 `1.1 × 10^-16`) 수준으로, 10,000~100,000회 시뮬레이션의 카이제곱
  검정 해상도로는 **통계적으로 검출 불가능한 수준**이다. 이는 정수 난수를 작은 범위로 나누는
  전통적 모듈로 편향(수백~수천 개 표본에서도 검출 가능한 수준)과는 크기 차수가 다르다.
- 따라서 v1은 `Math.floor(Math.random() * n)`을 채택하며 `crypto.getRandomValues()`가
  **필요하지 않다** — 이 기능은 암호학적 보안이 요구되는 상황(예: 상금 추첨의 조작 방지)이
  아니라 클라이언트 단에서 각자 확인하는 오락용 공정성이 목적이기 때문이다.
- **확인 필요**: 위 논증은 `Math.random()`이 사양대로 `[0,1)` 구간에서 통계적으로 균등한
  PRNG(예: V8의 xorshift128+)로 구현되어 있다는 전제에 의존한다. 실제 브라우저 엔진의 PRNG
  품질 자체를 이 문서가 보증하지는 않으며, Builder 구현 후 Calculation Auditor가 대량
  시뮬레이션(아래 "공정성 통계 검증 공통 절차")으로 실측해야 최종 확정된다.
- **선택적 대안(더 엄격한 구현을 원할 경우, 필수 아님)**: 거부 샘플링(rejection sampling)을
  적용한 `crypto.getRandomValues()` 기반 구현으로 모듈로 편향을 이론상 완전히 제거할 수 있다.
  ```
  function uniformRandomIndexCrypto(n):
    const MAX = 0xFFFFFFFF
    const limit = MAX - (MAX % n)      // n의 배수인 최대값 — 이 이상 뽑히면 버리고 재추첨
    let x
    do {
      x = crypto.getRandomValues(new Uint32Array(1))[0]
    } while (x >= limit)
    return x % n
  ```
  이 방식은 필수가 아니라 Architect가 원할 경우 채택 가능한 강화 옵션이다.

### 공식 ③ 사다리타기 — 균등 무작위 순열(bijection)

**알고리즘: Fisher-Yates(Durstenfeld 현대판) shuffle** — 끝에서부터 스왑.

```
function fisherYatesShuffle(items, rng = Math.random):
  a = copyOf(items)                       // 원본 배열은 변경하지 않는다
  for i from (a.length - 1) down to 1:
    j = Math.floor(rng() * (i + 1))       // 0..i 범위의 균등 정수 (i+1개 값)
    swap(a[i], a[j])
  return a
```

**적용**: `members`는 입력 순서를 그대로 유지하고(화면상 사다리의 세로줄 위치), `amounts`
배열을 `fisherYatesShuffle(amounts)`로 섞은 뒤 같은 인덱스끼리 짝짓는다.

```
shuffledAmounts = fisherYatesShuffle(amounts)
matches[i] = { memberIndex: i, memberName: members[i], amount: shuffledAmounts[i] }
permutation[i] = 원래 amounts 배열에서 shuffledAmounts[i]가 있던 인덱스 (동일 값이 여러 개면
                 셔플 과정에서 실제로 이동한 원소 하나를 추적해 결정 — 구현 시 값이 아니라
                 "원소(슬롯)"를 인덱스로 추적해야 한다, 아래 "구현 시 유의" 참고)
```

**구현 시 유의**: `amounts`에 중복 값이 있을 수 있으므로(예: 두 사람 모두 5,000원), `permutation`을
값 비교로 역산하면 안 되고, 셔플 함수 내부에서 원소가 아니라 **원래 인덱스 자체를 셔플**해서
`permutation`을 직접 얻는 방식을 권장한다:
```
indices = [0, 1, ..., n-1]
shuffledIndices = fisherYatesShuffle(indices)   // 이것이 그대로 permutation
matches[i] = { memberIndex: i, memberName: members[i], amount: amounts[shuffledIndices[i]] }
```
이렇게 인덱스를 셔플하면 중복 금액이 있어도 `permutation` 배열이 항상 명확하게 정의된다.

**왜 Fisher-Yates가 편향 없는 균등 순열을 만드는가(수학적 논증)**:
- 반복문은 `i = n-1`부터 `i = 1`까지 내려가며, 매 단계에서 `j`를 `0..i` 범위(총 `i+1`개
  값)에서 균등하게 뽑아 `a[i]`와 `a[j]`를 교환한다. 이는 "아직 최종 위치가 확정되지 않은
  `i+1`개 원소 중 하나를 균등 확률 `1/(i+1)`로 뽑아 위치 `i`에 확정 배치"하는 것과 같다.
  이전 단계들은 이미 `i` 초과 위치를 확정했을 뿐 `0..i` 범위 내부의 원소 구성에는 영향을
  주지 않으므로, 각 단계의 선택은 이전 선택과 독립이다.
- 따라서 특정 하나의 순열이 나올 확률은
  `P = 1/n × 1/(n-1) × ... × 1/2 × 1/1 = 1/n!`
  이며, 이는 **모든 `n!`가지 순열에 대해 동일**하다(어떤 목표 순열을 골라도 각 단계에서
  "그 순열이 요구하는 교환"이 나올 확률은 항상 위와 같은 개별 확률의 곱이 되기 때문). 즉
  Fisher-Yates shuffle은 균등 무작위 순열을 만든다(표준 결과, 아래 "기준/출처" 참고).

**금지 안티패턴**: `array.sort(() => Math.random() - 0.5)`는 **채택하지 않는다.** 비교
함수가 무작위 값을 반환하면 정렬 알고리즘(V8 등의 TimSort류)이 "일관성 없는 비교"를 받게
되어 정렬 결과가 안정적인 확률분포를 따르지 않는다 — 엔진의 내부 정렬 전략(원소 수에 따라
비교 횟수·병합 순서가 달라짐)에 따라 특정 순열(흔히 원래 순서에 가까운 배치)이 다른 순열보다
훨씬 자주 나오는 것으로 널리 보고되어 있다(아래 "기준/출처" 참고). 이 방식은 "균등분포"
요건(SPEC.md 완료 기준)을 만족하지 못하므로 Builder는 이 패턴을 사용해서는 안 된다.

**완전한 순열(bijection) 불변식**: 매 실행마다 다음을 만족해야 한다(통계적 검증과 별개로,
매 실행 단위의 결정적 검증).
```
matches.length === members.length === amounts.length
{ matches[i].memberIndex } 의 집합 === { 0, 1, ..., n-1 } (중복/누락 없음)
multiset({ matches[i].amount }) === multiset(amounts) (원래 금액 목록과 값 기준으로 정확히 일치, 중복 금액 포함)
```

## 공정성 통계 검증 공통 절차 (Calculation Auditor 재현용)

몰아주기(선정)와 사다리타기(매칭) 모두 아래 절차를 적용한다. **이 절차는 Formula Analyst가
정의하되, 실제 실행과 판정은 Calculation Auditor의 책임이다** — 아래는 Auditor가 그대로
따라 할 수 있는 재현 가능한 스펙이다.

1. **시행 횟수**: 최소 10,000회(SPEC.md 하한). Bonferroni 보정(아래 4번)을 적용하는 경우
   검정력 확보를 위해 100,000회를 권장한다(특히 N이 클수록, 예: N=20).
2. **검정 방법**: 카이제곱(χ²) 적합도 검정.
   - 몰아주기: 멤버 N명 각각의 당첨 횟수 `O_i`를 집계, 기대값 `E_i = 시행횟수 / N`(모든 i에
     동일), `χ² = Σ (O_i - E_i)² / E_i`, 자유도 `df = N - 1`.
   - 사다리타기(멤버별 marginal 검정, SPEC.md가 요구하는 "특정 멤버-금액 쌍의 배정 빈도"
     검증): 각 멤버 `m`에 대해, 시행마다 그 멤버가 받은 금액이 원래 `amounts` 배열의 몇 번째
     값이었는지(`permutation[m]`)를 집계해 `N`개 범주별 관측 횟수 `O_{m,j}`를 구하고, 기대값
     `E_{m,j} = 시행횟수 / N`로 카이제곱 통계량을 계산(`df = N - 1`). 이는 균등 무작위
     순열에서 각 위치(멤버)가 특정 원소(금액 슬롯)를 받을 한계(marginal) 확률이 정확히
     `1/N`이라는 성질에 근거한다(독립 시행을 반복 집계하므로 이항/다항분포로 근사 가능).
   - 사다리타기(전수 순열 검정, N이 작을 때 보조적으로 권장): N ≤ 5(즉 `N! ≤ 120`)인 경우,
     시행마다 나온 순열 자체를 `N!`개 범주로 집계해 `χ² = Σ (O_k - E_k)² / E_k`,
     `E_k = 시행횟수 / N!`, `df = N! - 1`을 계산할 수 있다. `N ≥ 6`(`N! ≥ 720`)부터는 범주
     수가 급증해(카이제곱 검정의 관례적 최소 조건인 "범주별 기대값 ≥ 5"를 만족하려면
     `시행횟수 ≥ 5×N!`가 필요) 실용적이지 않으므로, 이 경우 멤버별 marginal 검정만 적용한다.
3. **유의수준**: α = 0.05. 판정 기준: `p > 0.05`(귀무가설 "균등분포다"를 기각하지 못함) →
   PASS. `p ≤ 0.05` → FAIL(편향 의심).
   - 임계값 대신 통계량을 직접 비교해도 된다(표준 카이제곱 분포표, 예: `df=1→3.841`,
     `df=4→9.488`, `df=9→16.919`, `df=19→30.144`, 출처는 문서 말미 "기준/출처" 참고).
     `χ² < 임계값` → PASS(귀무가설 기각 못함), `χ² ≥ 임계값` → FAIL.
4. **다중 검정 보정(멤버별 marginal 검정처럼 N개의 독립적 검정을 동시에 수행하는 경우)**:
   Bonferroni 보정을 적용해 개별 검정의 유의수준을 `α_adj = 0.05 / N`으로 낮춘다(예: N=20이면
   `α_adj = 0.0025`). 모든 N개 멤버 검정이 `p > α_adj`를 만족해야 전체 PASS로 판정한다.
5. **재현성/우연한 실패 처리**: 통계 검정은 본질적으로 확률적이므로, 실제로 공정한 구현이라도
   약 α(5%) 확률로 우연히 FAIL이 나올 수 있다. 단일 실행에서 경계선 FAIL(예: p가 0.03~0.05
   사이)이 나오면 **같은 시뮬레이션을 독립적으로 2회 더(총 3회) 반복**하고, 3회 중 2회 이상
   PASS하면 "편향 없음"으로 최종 판정한다. 3회 중 2회 이상 FAIL(또는 매 회 매우 낮은 p값,
   예: p < 0.001)이 반복되면 실제 편향(구현 결함)으로 간주하고 Builder에게 반려한다.
6. **테스트 대상 N 값**: 최소 N=2, 3, 5, 10, 20(SPEC.md 상한)에서 각각 검증한다. 사다리타기의
   전수 순열 검정(위 2번)은 N=2, 3, 4, 5에서만 수행한다.

## 계산 순서

### 공통

1. 입력 검증(멤버 수 2~20, 이름 빈 문자열 없음, 금액 양의 정수, 사다리타기는 `amounts.length
   === members.length`) — 하나라도 실패하면 계산하지 않고 오류 표시.
2. 검증 통과 시에만 아래 방식별 계산을 실행한다.

### 균등 분배

1. `baseShare = floor(totalAmount / n)`, `remainder = totalAmount % n` 계산.
2. 인덱스 `0..remainder-1`에 `baseShare + 1`, 나머지에 `baseShare` 배정.
3. `Σ shares[i].amount === totalAmount` 불변식을 (테스트 단계에서) 확인.
4. **애니메이션 없이** 즉시 결과 표시.

### 한명 몰아주기

1. 먼저 결과를 계산한다: `selectedIndex = pickWinnerIndex(n)` (순수 함수, RNG 1회 호출).
2. `shares[]`를 `selectedIndex`만 `totalAmount`, 나머지 0으로 확정한다.
3. **그 다음** `selectedIndex`를 룰렛 애니메이션 컴포넌트에 "목표 지점"으로 전달한다 —
   애니메이션은 이미 정해진 `selectedIndex`가 멈출 위치를 계산해 회전·감속 애니메이션을
   재생할 뿐, 애니메이션 로직이 결과를 다시 정하지 않는다.
4. `prefers-reduced-motion` 등으로 애니메이션을 생략해도 2번에서 이미 확정된 결과를 그대로
   표시한다(애니메이션 유무가 결과에 영향을 주지 않음).
5. 애니메이션 종료(또는 생략) 후 결과 카드 표시.

### 사다리타기

1. 먼저 결과를 계산한다: `shuffledIndices = fisherYatesShuffle([0..n-1])`(인덱스 순열),
   `matches[i] = { memberIndex: i, memberName: members[i], amount: amounts[shuffledIndices[i]] }`.
2. 완전한 순열 불변식(위 "공식 ③" 참고)을 확인한다.
3. **그 다음** 확정된 `matches`(또는 `shuffledIndices`)를 사다리타기 애니메이션 컴포넌트에
   전달한다 — 애니메이션(세로줄+가로줄 경로 시뮬레이션이든, 매칭 결과를 먼저 정하고 사다리
   형태로 시각화하는 방식이든, 선택은 Architect/Builder 몫)은 이미 정해진 `matches`를
   "보여주는" 연출만 담당한다.
4. `prefers-reduced-motion`이면 애니메이션 생략, 1번에서 확정된 `matches`를 즉시 표시.
5. 애니메이션 종료(또는 생략) 후 결과 카드(멤버-금액 매칭 목록) 표시.

## 단위

- 금액(총 금액, 개별 배분액, 개별 금액 목록): 원(KRW), 정수. "전"(원 미만) 단위 정밀도는
  요구되지 않는다(SPEC.md "금액은 양의 정수(원 단위)").
- 인원수: 명, 정수(2~20).
- 확률: 무차원 소수(0~1) 또는 `1/N` 분수 표현.
- 카이제곱 통계량: 무차원.

## 정밀도 / 반올림 정책

- **내부 계산**: 모든 금액은 정수 원 단위로만 다룬다. 균등 분배의 `floor(totalAmount / n)`은
  정수 나눗셈이며 부동소수점 반올림이 개입할 여지가 없다(입력 자체가 정수, `n`도 정수이므로
  JS에서 `Math.floor(totalAmount / n)`이 정확한 정수를 반환함 — `totalAmount`, `n` 모두
  `Number.MAX_SAFE_INTEGER` 대비 매우 작은 값이라 정밀도 손실 없음).
- **표시 결과**: `Intl.NumberFormat('ko-KR')` 등으로 천단위 구분 표시(`docs/CALCULATOR_RULES.md`
  공통 규칙).
- **근거**: 법적으로 강제되는 절사/반올림 규정 없음(정책형 계산기 아님) — 이 계산기의
  반올림 정책은 순수히 "정수 나눗셈의 나머지를 결정적으로 배분"하는 설계 문제다(위 "공식 ①"
  참고).
- 카이제곱 통계량·p-value 계산 자체는 검증 스크립트(Auditor 측)에서 수행하며 이 계산기의
  프로덕션 코드에는 포함되지 않는다.

## 예외

- **총 금액 0 이하 / 숫자가 아님**: 계산하지 않고 오류 표시(균등, 몰아주기).
- **개별 금액 0 이하 / 숫자가 아님**(사다리타기): 계산하지 않고 오류 표시.
- **멤버 수 1명 이하**: 오류(SPEC.md 최소 2명 요건 위반) — "나눌 대상이 없음"으로 계산 자체가
  성립하지 않는다.
- **멤버 수 21명 이상**(또는 Architect가 확정한 상한 초과): 오류.
- **사다리타기에서 `amounts.length !== members.length`**: 계산 실행 전 차단(SPEC.md "오류와
  예외 처리").
- **빈 이름**: 계산 실행 차단(SPEC.md Must Have).
- **총 금액 < 멤버 수(균등 분배 경계)**: 오류가 아니라 정상 계산 경로다. `baseShare = 0`이
  되어 일부 멤버(정확히 `n - remainder`명)는 0원을 받는다 — 수학적으로 총액과 정확히
  일치하므로 유효한 결과다(검증 예제 5 참고). UI에서 0원을 명확히 표시할 것을 권장(UX는
  Architect/Builder 재량).
- **사다리타기에서 `amounts`에 중복 값**: 오류가 아니다. 중복 금액이 있어도 인덱스 기반
  셔플(위 "공식 ③" "구현 시 유의")로 permutation이 항상 명확히 정의되고 bijection 불변식이
  그대로 성립한다.
- **멤버 수 2명(최소)**: 균등은 나머지 0 또는 1만 가능(정상). 몰아주기는 N=2 이항 검정(카이제곱
  df=1)으로 검증. 사다리타기는 N=2, 즉 2!=2가지 경우의 수만 존재(검증 예제 10 참고).
- **멤버 수 20명(최대, SPEC 잠정)**: 균등은 나머지 0~19 전 구간 가능. 몰아주기·사다리타기
  통계 검증은 "공정성 통계 검증 공통 절차" 6번의 N=20 케이스로 수행.

## 검증 예제 (Golden Test 후보, 13개)

### 예제 1 — 균등 분배, 나누어떨어지는 경우
- Input: `totalAmount=10,000`, `members=[A,B]`(n=2)
- 계산: `baseShare=5,000`, `remainder=0`.
- Expected: `shares=[5,000, 5,000]`. 합계 10,000원과 일치.

### 예제 2 — 균등 분배, 나머지 1(3명)
- Input: `totalAmount=10,000`, `members=[A,B,C]`(n=3)
- 계산: `baseShare=floor(10,000/3)=3,333`, `remainder=1`.
- Expected: `shares=[3,334(A), 3,333(B), 3,333(C)]`. 합계 `3,334+3,333+3,333=10,000`.

### 예제 3 — 균등 분배, 나머지 = N-1(7명 중 6명 추가 배분)
- Input: `totalAmount=10,002`, `members=[A,B,C,D,E,F,G]`(n=7)
- 계산: `baseShare=floor(10,002/7)=1,428`, `remainder=10,002-1,428×7=10,002-9,996=6`.
- Expected: 앞 6명(A~F) 각 1,429원, 마지막 1명(G) 1,428원. 합계
  `1,429×6+1,428=8,574+1,428=10,002`.

### 예제 4 — 균등 분배, 작은 총액(100원/3명)
- Input: `totalAmount=100`, `members=[A,B,C]`(n=3)
- 계산: `baseShare=floor(100/3)=33`, `remainder=1`.
- Expected: `shares=[34(A), 33(B), 33(C)]`. 합계 100.

### 예제 5 — 균등 분배, 총액 < 인원수 경계(0원 발생)
- Input: `totalAmount=1`, `members=[A,B]`(n=2)
- 계산: `baseShare=floor(1/2)=0`, `remainder=1`.
- Expected: `shares=[1(A), 0(B)]`. 합계 1원과 정확히 일치 — 0원 배분은 오류가 아니라 정상
  경로(위 "예외" 참고).

### 예제 6 — 균등 분배, 최대 인원(20명), 나머지 1
- Input: `totalAmount=10,001`, `members=20명(M1..M20)`(n=20)
- 계산: `baseShare=floor(10,001/20)=500`, `remainder=1`.
- Expected: M1만 501원, M2~M20은 각 500원. 합계 `501+500×19=501+9,500=10,001`.

### 예제 7 — 균등 분배, 최대 인원(20명), 나누어떨어지는 경우
- Input: `totalAmount=1,000,000`, `members=20명`(n=20)
- 계산: `baseShare=50,000`, `remainder=0`.
- Expected: 전원 50,000원. 합계 1,000,000원.

### 예제 8 — 몰아주기, 모듈로 편향 부재 논증(수학적 검증, 시뮬레이션 아님)
- 명제: N=2~20에서 `Math.floor(Math.random() * N)`의 각 결과값이 나올 이론적 확률은
  `[0,1)` 구간을 `N`등분한 각 구간의 폭(`1/N`)에 정확히 비례하며, `Math.random()`의 표현
  가능한 값 개수(`2^53`)가 `N`으로 나누어떨어지지 않을 때의 편향 크기는 최대 `1/2^53 ≈
  1.11×10^-16`이다.
- Expected: 이 편향은 10,000~100,000회 규모의 카이제곱 검정으로 통계적으로 검출 불가능한
  수준(검정의 최소 검출 가능 편차보다 약 12자리 이상 작음) — "공정성 통계 검증 공통 절차"
  전제조건으로 채택.
- 출처: 위 "공식 ②" 논증 참고. **확인 필요**: 실제 브라우저 엔진의 `Math.random()` PRNG
  구현이 이론적 균등성에 부합하는지는 Auditor의 실측 시뮬레이션으로 최종 확인.

### 예제 9 — 몰아주기, 통계 검증 절차 시연(가상 데이터, 방법론 예시)
- **주의: 아래 수치는 방법론을 보여주기 위한 가상(hypothetical) 예시이며, 실제 구현 결과가
  아니다. Calculation Auditor가 실제 구현으로 재현해 진짜 값을 산출해야 한다.**
- 가정: N=5, 시행 10,000회, 가상 관측값 `O = [2010, 1985, 2040, 1975, 1990]`(합계 10,000).
- 계산: `E_i=2,000`(각각). `χ² = (10²+15²+40²+25²+10²)/2,000 = (100+225+1,600+625+100)/2,000
  = 2,650/2,000 = 1.325`. `df=4`, 임계값(α=0.05) `9.488`.
- Expected(가상 데이터 기준): `χ²=1.325 < 9.488` → `p>0.05` → PASS(귀무가설 "균등분포" 기각
  못함, 편향 없음과 일치하는 결과). **Auditor는 이 예제와 동일한 절차로 실제 시뮬레이션
  데이터를 넣어 재계산해야 한다.**

### 예제 10 — 사다리타기, 완전한 순열 손 추적(N=2)
- Input: `members=[A,B]`, `amounts=[1000,2000]`
- Fisher-Yates 진행: `i=1`(마지막 인덱스), `j=randomInt(0,1)`.
  - `j=0`(확률 1/2): `swap(indices[1], indices[0])` → `shuffledIndices=[1,0]` →
    매칭 `A-2000, B-1000`.
  - `j=1`(확률 1/2): 스왑 없음 → `shuffledIndices=[0,1]` → 매칭 `A-1000, B-2000`.
- Expected: 2가지 결과(`2!=2`)가 각각 정확히 1/2 확률로 나온다. 두 경우 모두
  `{matches[i].memberIndex}={0,1}`(누락/중복 없음), `multiset(amounts 배정값)={1000,2000}`
  (원본과 일치) — bijection 불변식 성립.
- **재검산 확인(2026-09-07)**: 예제 11의 오류 발견을 계기로 Formula Analyst가 이 예제도
  같은 방식(`i=1`에서 `swap(a[1],a[j])`, 시작 배열 `[0,1]`)으로 재추적했다. N=2는 경우의
  수가 2개뿐이라 오기 여지가 적었고, 실제로 위 두 행 모두 알고리즘과 정확히 일치함을
  재확인했다 — 수정 사항 없음.

### 예제 11 — 사다리타기, 완전한 순열 손 추적(N=3, 전체 6가지 조합)
- Input: `members=[A,B,C]`, `amounts=[100,200,300]`
- Fisher-Yates 진행(`i=2`에서 `j2∈{0,1,2}`, 이후 `i=1`에서 `j1∈{0,1}`, 각 독립 균등):
  `j2, j1` 조합 6가지(각 확률 `1/3 × 1/2 = 1/6`)와 그 결과 순열:

  | j2 | j1 | 최종 `shuffledIndices` | 매칭 |
  |---|---|---|---|
  | 0 | 0 | [1,2,0] | A-200,B-300,C-100 |
  | 0 | 1 | [2,1,0] | A-300,B-200,C-100 |
  | 1 | 0 | [2,0,1] | A-300,B-100,C-200 |
  | 1 | 1 | [0,2,1] | A-100,B-300,C-200 |
  | 2 | 0 | [1,0,2] | A-200,B-100,C-300 |
  | 2 | 1 | [0,1,2] | A-100,B-200,C-300 |

  > **정정 이력(2026-09-07)**: 이 표는 최초 작성 시 `(j2,j1)` 조합과 결과 순열의 대응
  > 관계에 오기가 있었다(6행 중 `(j2,j1)=(0,0)→[1,2,0]` 한 행만 정확했고, 나머지 5행은
  > `(j2,j1)`과 최종 `shuffledIndices`/매칭의 대응이 잘못 기재되어 있었다). Builder가
  > 구현 검증(Golden Test 작성) 중 실제 알고리즘(공식 ③: 시작 배열 `[0,1,2]`에서 `i=2`
  > 단계 `swap(a[2],a[j2])`, 이어서 `i=1` 단계 `swap(a[1],a[j1])`)을 직접 손으로 추적해
  > 발견했고, Formula Analyst가 동일한 방식으로 독립 재추적해 위 표로 정정했다(2026-09-07).
  > 6가지 결과 순열의 집합(`{[1,2,0],[2,1,0],[2,0,1],[0,2,1],[1,0,2],[0,1,2]}`, 중복 없이
  > `3!=6`가지 전부)과 각 확률(`1/6`)이라는 예제의 결론 자체는 최초 작성 시부터 정확했으며,
  > 이번 정정으로 바뀌지 않는다 — 바뀐 것은 어떤 `(j2,j1)` 조합이 어떤 특정 순열에
  > 대응하는지의 표기뿐이다.

- Expected: 6가지(`3!=6`) 조합이 각각 정확히 `1/6`(=`1/3×1/2`) 확률로 나오며, 서로 다른
  6개의 순열과 1:1로 대응한다(중복 순열 없음) — 이는 Fisher-Yates가 각 단계의 독립 균등
  선택을 곱해 `1/n!` 균등분포를 만든다는 "공식 ③" 논증의 구체적 재현이다. 6가지 모두에서
  `{memberIndex 집합}={0,1,2}`, `multiset(배정값)={100,200,300}`이 성립(bijection 확인).

### 예제 12 — 사다리타기, 완전한 순열 불변식 검증 절차(결정적, 매 실행 단위)
- 절차: 임의의 유효 입력(N=2~20)에 대해 `fisherYatesShuffle` 실행 결과 `matches`에 대해
  다음을 assert한다.
  1. `matches.length === N`
  2. `sort(matches.map(m => m.memberIndex)) === [0,1,...,N-1]`
  3. `sort(matches.map(m => m.amount)) === sort(원본 amounts)` (multiset 비교, 중복 값 포함)
- Expected: 위 3개 assertion이 **모든** 실행에서 100% 성립(통계적 검증이 아니라 결정적
  불변식 — 단 1회라도 실패하면 Critical 결함).

### 예제 13 — 사다리타기, 통계적 균등분포 검증 절차(marginal + 전수 순열)
- 절차 A(marginal, 모든 N에서 적용): N=5, 시행 10,000회, 멤버 A(인덱스 0)가 원래 `amounts`의
  몇 번째 값을 받았는지(`permutation[0]`) 집계 → 5개 범주 기대값 각 2,000, `df=4`, 임계값
  9.488. `χ² < 9.488`이면 PASS. 이를 멤버 5명 전원에 대해 반복하고, Bonferroni 보정
  `α_adj=0.05/5=0.01`(임계값은 `df=4, α=0.01` 기준 `13.277`, 표준 카이제곱표 참고)을
  적용해 5개 검정 전부 PASS해야 종합 PASS.
- 절차 B(전수 순열, N≤5에서만): N=4(`4!=24`), 시행 100,000회 이상(범주별 기대값
  `100,000/24≈4,167 ≥ 5` 조건 충분히 만족), 24개 순열 각각의 관측 빈도로 `χ²` 계산,
  `df=23`, 임계값(α=0.05) `35.172`(표준 카이제곱표). `χ² < 35.172`이면 PASS.
- Expected: 실제 수치는 Calculation Auditor가 구현 완료 후 시뮬레이션을 실행해 산출·기록한다.
  이 예제는 절차 자체가 재현 가능하도록 구체적 시행 횟수·자유도·임계값을 명시하는 것이
  목적이다.

> Golden Test 후보 총 13개. 균등 분배 7개(나누어떨어짐/나머지 1/나머지=N-1/소액/총액<인원수/
> 최대인원 2종 포함), 몰아주기 2개(수학적 논증 1 + 통계 검증 방법론 시연 1), 사다리타기 4개
> (손 추적 2 + 불변식 검증 절차 1 + 통계 검증 절차 1).

## 사다리타기 시각화 경로 재구성 알고리즘 (2026-09-07 추가)

### 배경 — 무엇을 고치는가

`src/calculators/bill-split-calculator/LadderAnimation.tsx`는 현재 (1) `permutation`이
가리키는 목표 열까지 멤버별 베지어 곡선을 직접 그리고, (2) 화면의 회색 가로줄(rung)은
`generateDecorativeRungs`가 열·개수·높이를 완전히 무작위로 생성해 그 곡선과 아무 관계 없이
얹는 방식으로 동작한다. 이는 `tasks/bill-split-calculator/ARCHITECTURE.md` "5."가 명시적으로
채택한 "매칭 결과를 먼저 정하고 사다리 형태로만 시각화하는 방식"(가로줄은 순수 장식, 결과에
영향 없음)을 그대로 구현한 것이며, 이 문서의 기존 "확인 필요 목록" 3번도 그 결정으로 답이
난 것으로 기록돼 있었다.

그런데 실제 브라우저 테스트에서 사용자가 "그려진 선을 따라 이동하는 게 아니라 마음대로
꽂히는 것처럼 보인다"고 지적했다 — 좌표상 도착 지점(`permutation`)은 정확하지만, 화면에 보이는
가로줄과 곡선이 무관하므로 "사다리를 타고 내려간다"는 시각적 설득력이 없다는 문제다. 이
절은 그 문제를 고치기 위한 **새로운 가로줄(rung) 배치 알고리즘**을 정의한다 — **가로줄
자체가 실제 경로가 되도록**, 즉 "그려진 세로줄+가로줄만 보고 위에서 아래로 순서대로 교차를
따라가면 정확히 `permutation`이 나오는" 배치를 만든다.

**범위**: 이 절은 공식①·②·③(균등 분배 나머지 처리, 몰아주기 RNG, Fisher-Yates 셔플)과
"공정성 통계 검증 공통 절차"를 전혀 수정하지 않는다. `permutation`은 이미 확정된 값으로
**읽기 전용 입력**을 받을 뿐이며, 이 알고리즘은 그 값에 어떤 영향도 주지 않는다(요구사항
5번). 이 절이 채택되면 `ARCHITECTURE.md` "5."의 "가로줄은 순수 장식"이라는 전제 자체가
바뀌므로, 실제 코드 반영 여부·`ARCHITECTURE.md` 갱신은 Architect의 권한이다 — 이 문서는
그 개정에 쓸 수 있는 **수학적으로 검증된 알고리즘**을 제공하는 역할만 한다.

### 용어 정의

- **열(column)**: 멤버 `i`가 서 있는 세로줄 위치, `0..n-1`. `permutation[i]`는 멤버 `i`가
  최종적으로 도착해야 하는 열이다(기존 "출력값" 절 정의 그대로).
- **행(row)**: 시간축(위→아래) 순서를 나타내는 정수, `0`부터 시작. 화면상 Y좌표로의 변환은
  구현 재량이며 이 절은 순서(row 오름차순)만 규정한다.
- **가로줄(rung)**: `{ row: number, column: number }` — 열 `column`과 `column+1` 사이를
  잇는 가로줄이 시간축상 `row`번째에 있음을 뜻한다(`column`은 `0..n-2` 범위).
- **역함수 `target[]`**: `target[c] = i`(단, `permutation[i] === c`) — "열 `c`에 최종적으로
  도착해야 하는 멤버가 누구인가"를 나타낸다. `permutation`이 bijection이므로 `target`도
  항상 명확히 정의되는 bijection이다(공식③ "완전한 순열 불변식" 참고).

### 알고리즘 개요

2단계로 구성된다.

1. **1단계 — 인접 전치(스왑) 생성**: "선택정렬 스타일 버블링"으로, `current` 배열(열별 현재
   점유 멤버)을 `target` 배열과 일치할 때까지 인접한 두 열끼리의 스왑만으로 바꿔나간다.
   결과는 시간순으로 정렬된 스왑 목록(각 스왑은 "열 `c`와 `c+1` 사이"라는 정보만 가짐)이다.
2. **2단계 — 그리디 행 스케줄링**: 1단계가 만든 시간순 스왑 목록을, "같은 열을 건드리지
   않는 스왑은 같은 행에 함께 배치"하는 그리디 규칙으로 압축해 `{row, column}` 목록(=최종
   rung 배치)으로 변환한다.

이 문서의 "권장 접근법"(작업 지시)이 제안한 방식을 그대로 검토·채택했다 — 아래 "정확성
증명"에서 보듯 항상 올바르게 동작하며, N=20 최악 케이스에서도 행 수가 합리적 범위(37행,
아래 "행 수 상한 분석" 참고)에 들어와 대안(홀짝 전치 정렬망(odd-even transposition sort)
등 더 복잡한 표준 병렬 정렬망)으로 바꿀 필요가 없다고 판단했다.

### 1단계 — 인접 전치(스왑) 생성 (선택정렬 스타일 버블링)

```
function generateAdjacentSwaps(permutation):
  n = permutation.length
  target = new Array(n)
  for i in 0..n-1:
    target[permutation[i]] = i          // target = permutation의 역함수

  current = [0, 1, ..., n-1]
  swapsInTimeOrder = []                  // 시간순 스왑 목록, 원소는 열 번호(c, c와 c+1 사이)

  for c from 0 to n-1:
    p = c
    while current[p] !== target[c]:      // c 이상 범위에서 target[c] 탐색(항상 존재, 아래 증명 참고)
      p = p + 1
    while p > c:
      swapsInTimeOrder.push(p - 1)       // 열 (p-1, p) 사이 스왑
      swap(current[p - 1], current[p])
      p = p - 1
    // 루프 종료 시 current[c] === target[c]

  return swapsInTimeOrder
```

RNG를 전혀 쓰지 않는 **완전 결정적 순수 함수**다(공식③ "RNG를 함수 인자로 주입 가능하게
설계" 원칙과 달리, 이 함수는 애초에 RNG가 필요 없다 — 무작위성은 이미 `permutation`을 만든
Fisher-Yates 단계에서 전부 소비되었다).

### 2단계 — 그리디 행 스케줄링

```
function scheduleSwapsIntoRows(swapsInTimeOrder, n):
  lastUsedRow = new Array(n).fill(-1)    // 열 경계선(0..n-1) 각각이 마지막으로 쓰인 row
  rungs = []
  for c of swapsInTimeOrder:             // 1단계가 만든 시간순 그대로 순회(순서 변경 금지)
    row = max(lastUsedRow[c], lastUsedRow[c + 1]) + 1
    rungs.push({ row: row, column: c })
    lastUsedRow[c] = row
    lastUsedRow[c + 1] = row
  return rungs

function buildLadderRungs(permutation):
  swaps = generateAdjacentSwaps(permutation)
  rungs = scheduleSwapsIntoRows(swaps, permutation.length)
  rowCount = rungs.length === 0 ? 0 : max(rungs.map(r => r.row)) + 1
  return { rungs, rowCount }
```

`lastUsedRow[ℓ]`는 "열 경계선 `ℓ`(즉 열 `ℓ-1`과 `ℓ` 사이, 또는 `ℓ`과 `ℓ+1` 사이 — 정확히는
"열 `ℓ`을 양 끝 중 하나로 갖는 가로줄이 마지막으로 배정된 행")을 추적하는 배열이다. 한
스왑(열 `c`)을 스케줄링할 때, 그 스왑이 건드리는 두 열(`c`, `c+1`) 중 더 늦게 쓰인 행보다
하나 큰 행에 배정한다 — 이렇게 하면 같은 열을 공유하는 스왑끼리는 항상 서로 다른 행에,
공유하지 않는 스왑끼리는 같은 행에 모일 수 있다(아래 "정확성 증명 — 불변식 4" 참고).

### 시뮬레이션(검증) 규칙 정의

Builder/Auditor가 "핵심 불변식"을 검증할 때 그대로 구현해야 하는 시뮬레이션 함수:

```
function simulateFinalColumn(rungs, startColumn):
  sorted = rungs를 row 오름차순으로 정렬(같은 row끼리는 서로 순서 무관, 아래 증명 참고)
  col = startColumn
  for rung of sorted:
    if rung.column === col:
      col = col + 1
    else if rung.column + 1 === col:
      col = col - 1
    // 그 외(rung이 현재 열을 건드리지 않음)에는 그대로 둔다
  return col
```

**핵심 불변식(요구사항 3번)**: 모든 유효한 `permutation`과 모든 `i`(`0 <= i < n`)에 대해
`simulateFinalColumn(buildLadderRungs(permutation).rungs, i) === permutation[i]`가 항상
성립해야 한다. 아래 "정확성 증명"에서 이를 증명한다.

### 정확성 증명

#### 불변식 3 증명 — `current`가 결국 `target`과 일치함

**존재성 보조정리**: `for c` 루프의 각 단계 진입 시, `current[0..c-1] = target[0..c-1]`이
이미 성립한다(귀납 가정, `c=0`일 때는 공집합이라 자명). `target`은 `permutation`의 역함수라
`0..n-1`의 순열이므로 `target[c]`는 `target[0..c-1]`의 어떤 값과도 다르다. 한편 `current`는
항상 `0..n-1`의 순열(스왑은 두 원소를 교환할 뿐 값 자체를 바꾸지 않음)이므로,
`current[0..c-1] = target[0..c-1]`이라는 조건 아래 `target[c]`는 `current[0..c-1]` 안에
있을 수 없다 — 따라서 반드시 `current[c..n-1]`의 어딘가에 있다. 즉 `while` 탐색은 항상
`p <= n-1`에서 종료하며 배열 범위를 벗어나지 않는다.

**버블링 보조정리**: `p`(`> c`)에서 `target[c]`를 찾았다면, `(p-1,p), (p-2,p-1), ...,
(c,c+1)` 순서로 인접 스왑을 적용하면 그 값이 정확히 위치 `c`로 이동하고(매 스왑이 그 값을
한 칸씩 왼쪽으로 옮기는 것과 동치), 이 과정에서 위치 `0..c-1`은 전혀 건드리지 않는다(모든
스왑이 `p-1 >= c` 범위에서만 일어남). 따라서 루프가 끝나면 `current[c] = target[c]`이고
`current[0..c-1]`은 그대로 보존된다.

**귀납 결론**: 위 두 보조정리로 `c = 0, 1, ..., n-1`을 차례로 처리하면 매 단계 후
`current[0..c] = target[0..c]`가 성립하고, `c=n-1`까지 마치면 `current = target`이
정확히 성립한다. ∎

#### `current`의 진화와 `simulateFinalColumn`의 대응

`pos_t`를 "시간순으로 처음 `t`개 스왑을 순서대로 적용한 뒤의 `current` 배열"이라 하자
(`pos_0 = [0,...,n-1]`, 위 증명의 최종 `current = pos_T`, `T`=전체 스왑 수). `pos_t[c] = m`은
"열 `c`에 원래 열 `m`에서 출발한 토큰이 와 있다"는 뜻이므로, `loc_t[m] := pos_t^{-1}[m]`은
"원래 열 `m`에서 출발한 토큰이 `t`번째 스왑까지 적용한 시점에 있는 열"이다.

위 증명으로 `pos_T[c] = target[c]`이며, `target[c] = m`은 정의상 `permutation[m] = c`를
뜻한다. 따라서 모든 멤버 `m`에 대해 `loc_T[m] = pos_T^{-1}[m] = c = permutation[m]`이
성립한다 — **즉 "원래 열 `m`에서 출발해 전체 스왑을 시간순으로 다 적용하면 도착하는 열"이
정확히 `permutation[m]`이다.**

이제 `simulateFinalColumn`이 이 `pos_0 -> pos_T`와 같은 결과를 내는지만 보이면 된다(다음
"불변식 4 증명"에서 이어서 증명).

#### 불변식 4 증명 — 같은 행끼리 열 비공유 + 시간순 보존

`scheduleSwapsIntoRows`가 시간순으로 스왑을 하나씩 처리하며 `row = max(lastUsedRow[c],
lastUsedRow[c+1]) + 1`로 배정하고, 그 즉시 `lastUsedRow[c] = lastUsedRow[c+1] = row`로
갱신한다는 점에서 다음 두 가지가 따라온다.

**(a) 같은 행에 배정된 두 스왑은 열을 공유하지 않는다.** 스왑 A(열 `a`)가 행 `R`에
배정된 직후 `lastUsedRow[a] = lastUsedRow[a+1] = R`이 된다. 만약 나중에(시간순으로 A
이후) 처리되는 스왑 B가 A와 열을 공유한다면(즉 `b ∈ {a-1, a, a+1}`이어서 `{b,b+1} ∩
{a,a+1} ≠ ∅`), B를 스케줄링할 때 `lastUsedRow`의 해당 항목이 이미 `R`(또는 그 이후 갱신된
더 큰 값)이므로 `row(B) = max(...) + 1 >= R + 1 > R`이다. 따라서 열을 공유하는 두 스왑은
**절대 같은 행에 배정되지 않는다** — 대우로, 같은 행에 배정된 두 스왑은 열을 공유하지
않는다(요구사항 4번).

**(b) 열을 공유하는 두 스왑은 시간순과 행 순서가 일치한다.** 위 논증에서 이미 보였듯,
시간순으로 나중에 처리되는 스왑이 항상 더 큰(또는 최소한 이전 것보다 엄격히 큰) 행을
받는다 — 즉 어떤 열 `ℓ`을 공유하는 스왑들을 시간순으로 나열하면 그 행 번호도 반드시
오름차순이다.

**따라서 "행 오름차순으로 그룹 적용"은 "시간순 적용"과 동일한 결과를 낸다.** 임의의 열
경계선 `ℓ`을 하나 고르면, `ℓ`을 건드리는 스왑들은 (b)에 의해 시간순과 행 순서가 정확히
일치하므로, 행 오름차순으로 처리해도 `ℓ`의 값은 시간순으로 처리했을 때와 똑같은 순서로
갱신된다. 같은 행 안의 서로 다른 스왑들은 (a)에 의해 서로 다른 열 경계선만 건드리므로,
그들 사이의 처리 순서는 결과에 영향을 주지 않는다(서로 독립적인 위치를 건드리므로
교환 가능/commute). 어떤 위치(열)의 최종 값이든 그 위치에 실제로 영향을 준 스왑들의
상대적 순서만이 결과를 결정하는데, 그 상대 순서가 항상 보존되므로, 전체 배열 관점에서
"행 오름차순 그룹 적용" = "시간순 순차 적용" = `pos_T`. ∎

`simulateFinalColumn`은 정확히 "행 오름차순으로, 자신에게 해당하는 교차만 반영"하는
절차이므로 위 등식에 의해 `simulateFinalColumn(rungs, m) = loc_T[m] = permutation[m]`이
**모든 멤버 `m`에 대해 항상** 성립한다. 이것으로 요구사항 3번(핵심 불변식)이 완전히
증명되었다.

### 무작위성 삽입 지점 (선택, 필수 아님)

요구사항 5번대로, 위 알고리즘은 이미 완전히 결정적이며 별도 무작위성 없이도 요구사항을
모두 만족한다. 매 렌더마다 사다리 모양에 장식적 다양성을 주고 싶다면 다음 한 가지 지점만
안전하게 검토할 수 있다.

- **`for c` 루프 방향 뒤집기**: 본문은 `c`를 `0`부터 오름차순으로 처리하며 필요한 값을
  "왼쪽으로 버블링"한다. 대칭적으로 `c`를 `n-1`부터 내림차순으로 처리하며 필요한 값을
  "오른쪽으로 버블링"하는 변형도 독립적으로 같은 방식(귀납법)으로 정확성을 증명할 수 있다.
  두 변형 중 어느 쪽을 쓸지 매 렌더마다 무작위로 고르면 같은 `permutation`에 대해 시각적으로
  다른 사다리 모양을 낼 수 있다.
- **이 외의 변형(예: `c` 처리 순서를 임의로 섞기, 스케줄링 결과를 임의로 재배치)은 위
  증명의 전제(귀납 순서, 시간순 보존)를 깨뜨릴 수 있으므로 채택하지 않는다.** 새로운
  변형을 추가하려면 이 절과 동일한 수준의 증명을 다시 작성해 Formula Analyst 검토를 거쳐야
  한다 — Builder/Architect가 "장식적 다양성"을 이유로 임의 변형을 만드는 것은 금지한다.
- 두 변형 모두 채택하지 않고 오름차순 버블링 하나만 쓰는 것으로 충분하다(요구사항 자체가
  무작위성을 요구하지 않음) — 아래 Golden Test는 오름차순 버블링 기준으로만 작성했다.

### 행 수 상한 분석 (N=20 역순 케이스)

**총 스왑 수(1단계)**: 역순 순열(`permutation[i] = n-1-i`, 전치 횟수가 최대인 경우)에서
`generateAdjacentSwaps`가 만드는 스왑 수는 정확히 `n(n-1)/2`다(선택정렬 스타일 버블링의
스왑 횟수는 `current`와 `target` 사이의 "역전(inversion)" 개수와 같고, 역순 순열은 가능한
최대 역전 수 `n(n-1)/2`를 갖는다). N=20이면 `20×19/2 = 190`회 — 이를 그대로(스왑 하나당
행 하나) 표시하면 작업 지시가 우려한 대로 190행이 되어 화면에 표시하기엔 과도하다.

**2단계 그리디 스케줄링 적용 후 실제 행 수**: N=2..6에 대해 알고리즘을 직접 손으로
추적한 결과, 다음과 같은 정확히 `2n-3`행의 패턴이 나타난다(아래 "검증 예제 L2, L3, L5, L6"
및 추가 확인한 N=6 케이스).

| n | 총 스왑 수 `n(n-1)/2` | 실제 행 수 | `2n-3` |
|---|---|---|---|
| 2 | 1 | 1 | 1 |
| 3 | 3 | 3 | 3 |
| 4 | 6 | 5 | 5 |
| 5 | 10 | 7 | 7 |
| 6 | 15 | 9 | 9 |

**패턴이 생기는 이유(자기유사 재귀 구조)**: 역순 순열에서 `c=0` 처리 블록은 항상 열
`n-2, n-3, ..., 0` 순서로 `n-1`번 스왑하며, 그 결과 `current`는 `[n-1, 0, 1, ..., n-2]`
(오른쪽으로 1칸 회전)가 된다. 이는 **정확히 열 `1..n-1`에 대한 (n-1)명짜리 역순 순열
부분문제와 동일한 형태**이며, 실제로 그 부분문제의 첫 스왑(열 `n-2`)이 배정받는 행은
`c=0` 블록의 첫 스왑(같은 열 `n-2`, 행 `0`)과 그다음 스왑(열 `n-3`, 행 `1`, 열 `n-2`도
같이 갱신)의 영향으로 항상 행 `2`부터 시작한다(n=3,4,5,6 모두에서 직접 확인). 부분문제
크기가 하나 줄 때마다 시작 행이 정확히 2씩 밀리고 부분문제 자체의 행 수도 그대로
재귀되므로, `f(n) = f(n-1) + 2`, `f(2) = 1` → `f(n) = 2n - 3`이 성립한다(n=2..6 직접
검증으로 재귀의 처음 5단계를 전부 확인했으므로, 이 재귀가 일반 n에도 그대로 이어진다는
결론에 높은 확신을 갖는다).

**N=20 결과**: `f(20) = 2×20 - 3 = 37`행. 190회의 스왑이 37행으로 압축되어(약 5.1배
압축), 작업 지시가 제시한 "몇~수십 행 이내" 기준을 충분히 만족한다.

**확인 필요**: 위 `2n-3` 공식은 "역순 순열이 만들어내는 특정 스왑 시퀀스 + 이 문서가 정의한
그리디 스케줄링"의 조합에서 나온 결과이며, n=2..6을 직접 손으로 추적해 확인했고 그 이상의
n에 대해서는 재귀 구조(자기유사성)에 근거해 일반화했다(엄밀한 전체 귀납 증명은 아니다).
또한 역순 순열이 이 알고리즘 기준으로도 항상 "모든 순열 중 최대 행 수"를 낸다는 것은
별도로 증명하지 않았다(전체 스왑 수가 항상 행 수의 자연스러운 상한이므로, 역순이 아닌
다른 순열은 최대 `190`보다 적은 스왑을 만들고, 경험적으로 스왑이 적을수록 행 수도 적거나
같다). Architect/Calculation Auditor가 필요하면 N=7~20 구간을 스크립트로 전수 실행해
`2n-3` 공식과 "역순이 최댓값" 가정을 재확인할 것을 권장한다 — 다만 37이라는 구체적 수치
자체는 "수십 행" 기준을 이미 넉넉히 만족하므로, 이 재확인이 지연되어도 화면 표시 설계를
막을 필요는 없다.

### 검증 예제 (Golden Test, 최소 6개)

아래 예제는 기존 "검증 예제(Golden Test 후보, 13개)"와 번호 체계가 겹치지 않도록 `L`
접두사를 쓴다(Ladder). 모두 `buildLadderRungs`(1+2단계)와 `simulateFinalColumn`을 손으로
직접 추적해 확인했다.

#### 예제 L1 — N=2, 항등순열(교차 없음)
- Input: `permutation=[0,1]`
- `target=[0,1]`. `current=[0,1]`: `c=0`에서 `p=0=c`(스왑 없음), `c=1`에서 `p=1=c`(스왑 없음).
- `swaps=[]` → `rungs=[]`, `rowCount=0`.
- 시뮬레이션: `simulateFinalColumn([], 0)=0=permutation[0]`,
  `simulateFinalColumn([], 1)=1=permutation[1]`. 두 멤버 모두 일치.
- 의미: 가로줄이 하나도 없는(교차 없이 그대로 내려가는) 경우도 유효한 정상 케이스임을
  확인한다 — Fisher-Yates가 항등순열을 만들 수도 있으므로 이 경로는 반드시 지원해야 한다.

#### 예제 L2 — N=2, 역순(교차 1회)
- Input: `permutation=[1,0]`
- `target=[1,0]`. `c=0`: `target[0]=1`, `current=[0,1]`에서 위치1 → `p=1`; `p>0`이므로
  `swaps.push(0)`, `swap(current[0],current[1])` → `current=[1,0]`, `p=0`. `c=1`: 이미
  `current[1]=0=target[1]`, 스왑 없음.
- `swaps=[0]`. 스케줄링: `lastUsedRow=[-1,-1]` → 열0 스왑: `row=max(-1,-1)+1=0`.
  `rungs=[{row:0,column:0}]`, `rowCount=1`.
- 시뮬레이션: 멤버0(열0) → row0에서 `rung.column(0)===col(0)` → 열1로 교차, 최종열1
  `=permutation[0]=1` ✓. 멤버1(열1) → row0에서 `rung.column+1(1)===col(1)` → 열0으로 교차,
  최종열0 `=permutation[1]=0` ✓.

#### 예제 L3 — N=3, 역순(`permutation=[2,1,0]`)
- `target=[2,1,0]`(자기 자신의 역함수). `current=[0,1,2]`.
  - `c=0`: `target[0]=2`는 위치2에 있음(`p=2`). `p>0`: `swaps.push(1)`,
    `current=[0,2,1]`, `p=1`; 계속 `p>0`: `swaps.push(0)`, `current=[2,0,1]`, `p=0`.
  - `c=1`: `target[1]=1`은 `current=[2,0,1]`의 위치2에 있음(`p=2`). `p>1`:
    `swaps.push(1)`, `current=[2,1,0]`, `p=1`. 종료.
  - `c=2`: `current[2]=0=target[2]`, 스왑 없음.
- `swaps=[1,0,1]`(시간순, 총 3회=`3×2/2`).
- 스케줄링(`lastUsedRow=[-1,-1,-1]`):
  1. 열1(선1,2) → `row=max(-1,-1)+1=0`. 갱신 선1=0,선2=0.
  2. 열0(선0,1) → `row=max(-1,0)+1=1`. 갱신 선0=1,선1=1.
  3. 열1(선1,2) → `row=max(1,0)+1=2`. 갱신 선1=2,선2=2.
  - `rungs=[{row0,col1},{row1,col0},{row2,col1}]`, `rowCount=3(=2×3-3)`.
- 전체 멤버 시뮬레이션(행 오름차순):
  - 멤버0(열0): row0(col1, 선1,2 — 무관, 유지0) → row1(col0, 선0,1 — 열0 일치 → 열1) →
    row2(col1, 선1,2 — 열1 일치 → 열2). 최종열2 `=permutation[0]=2` ✓
  - 멤버1(열1): row0(col1 — 열1 일치 → 열2) → row1(col0 — 무관, 유지2) → row2(col1 — 열2가
    `col+1`과 일치 → 열1). 최종열1 `=permutation[1]=1` ✓
  - 멤버2(열2): row0(col1 — 열2가 `col+1`과 일치 → 열1) → row1(col0 — 열1이 `col+1`과 일치
    → 열0) → row2(col1 — 무관, 유지0). 최종열0 `=permutation[2]=0` ✓
- 모든 멤버 일치 — 불변식 3, 4 모두 확인.

#### 예제 L4 — N=3, 비-역순 순환(`permutation=[1,2,0]`)
- `target`: `permutation[0]=1→target[1]=0`, `permutation[1]=2→target[2]=1`,
  `permutation[2]=0→target[0]=2`. `target=[2,0,1]`.
- `current=[0,1,2]`.
  - `c=0`: `target[0]=2`, 위치2(`p=2`). `swaps.push(1)`, `current=[0,2,1]`, `p=1`;
    `swaps.push(0)`, `current=[2,0,1]`, `p=0`.
  - `c=1`: `target[1]=0`, `current=[2,0,1]`의 위치1에 이미 있음(`p=1=c`) — 스왑 없음.
  - `c=2`: `target[2]=1`, `current[2]=1` 이미 일치 — 스왑 없음.
- `swaps=[1,0]`(총 2회, 역순 케이스보다 적음 — 순열마다 필요한 스왑 수가 다름을 보여준다).
- 스케줄링: 열1(선1,2)→`row=0`; 열0(선0,1)→`row=max(-1,0)+1=1`.
  `rungs=[{row0,col1},{row1,col0}]`, `rowCount=2`.
- 전체 멤버 시뮬레이션:
  - 멤버0(열0): row0(col1 — 무관, 유지0) → row1(col0 — 열0 일치 → 열1). 최종1
    `=permutation[0]=1` ✓
  - 멤버1(열1): row0(col1 — 열1 일치 → 열2) → row1(col0 — 무관, 유지2). 최종2
    `=permutation[1]=2` ✓
  - 멤버2(열2): row0(col1 — 열2가 `col+1` 일치 → 열1) → row1(col0 — 열1이 `col+1` 일치
    → 열0). 최종0 `=permutation[2]=0` ✓
- 모든 멤버 일치. 총 스왑 2회·행 2개로 역순(3회·3행)보다 적게 필요함을 확인 — 즉 필요한
  행 수는 순열마다 달라지고 역순이 상한에 가까운 경우임을 뒷받침한다.

#### 예제 L5 — N=4, 역순(`permutation=[3,2,1,0]`), 4명 전원 시뮬레이션
- `target=[3,2,1,0]`. `generateAdjacentSwaps` 진행 결과(직접 추적):
  `swaps = [2,1,0, 2,1, 2]`(시간순 6회 `=4×3/2`).
- 스케줄링(`lastUsedRow` 초기 `[-1,-1,-1,-1]`, 선0..3):
  1. 열2(선2,3)→`row0`. 2. 열1(선1,2)→`row=max(-1,0)+1=1`. 3. 열0(선0,1)→`row=max(-1,1)+1=2`.
  4. 열2(선2,3)→`row=max(1,0)+1=2`. 5. 열1(선1,2)→`row=max(2,2)+1=3`. 6. 열2(선2,3)→
     `row=max(3,2)+1=4`.
  - `rungs = [{0,col2},{1,col1},{2,col0},{2,col2},{3,col1},{4,col2}]`, `rowCount=5(=2×4-3)`.
  - `row2`에 열0(선0,1)과 열2(선2,3) 두 rung이 공존 — 선을 공유하지 않으므로 요구사항 4번
    충족(동시에 표시해도 모호하지 않음).
- 전체 멤버 시뮬레이션(행0→4 순서):
  - 멤버0(열0): row0 무관(0) → row1 무관(0) → row2: col0(열0 일치→열1), col2(무관) → row3
    col1(열1 일치→열2) → row4 col2(열2 일치→열3). 최종3 `=permutation[0]=3` ✓
  - 멤버1(열1): row0 무관(1) → row1 col1(열1 일치→열2) → row2 col0(무관), col2(열2 일치
    →열3) → row3 col1(무관, 열3 유지) → row4 col2(열3이 `col+1` 일치→열2). 최종2
    `=permutation[1]=2` ✓
  - 멤버2(열2): row0 col2(열2 일치→열3) → row1 무관(열3 유지) → row2 col0(무관), col2(열3이
    `col+1` 일치→열2) → row3 col1(열2가 `col+1` 일치→열1) → row4 col2(무관, 열1 유지).
    최종1 `=permutation[2]=1` ✓
  - 멤버3(열3): row0 col2(열3이 `col+1` 일치→열2) → row1 col1(열2가 `col+1` 일치→열1) →
    row2 col0(열1이 `col+1` 일치→열0), col2(무관) → row3 col1(무관, 열0 유지) → row4
    col2(무관, 열0 유지). 최종0 `=permutation[3]=0` ✓
- 4명 전원 일치 — N=4 역순 케이스를 rung 배치까지 포함해 완전히 검증했다.

#### 예제 L6 — N=5, 역순(`permutation=[4,3,2,1,0]`), 5명 전원 시뮬레이션
- `target=[4,3,2,1,0]`. `generateAdjacentSwaps` 진행 결과: `swaps =
  [3,2,1,0, 3,2,1, 3,2, 3]`(시간순 10회 `=5×4/2`).
- 스케줄링(선0..4 초기 `-1`):
  1.열3→row0 2.열2→row1 3.열1→row2 4.열0→row3 5.열3→`max(1,0)+1=2` 6.열2→`max(2,2)+1=3`
  7.열1→`max(3,3)+1=4` 8.열3→`max(3,2)+1=4` 9.열2→`max(4,4)+1=5` 10.열3→`max(5,4)+1=6`
  - `rungs` 행별: row0:{col3}, row1:{col2}, row2:{col1,col3}, row3:{col0,col2},
    row4:{col1,col3}, row5:{col2}, row6:{col3}. `rowCount=7(=2×5-3)`.
  - row2(col1 선1,2 / col3 선3,4), row3(col0 선0,1 / col2 선2,3), row4(col1 선1,2 / col3
    선3,4) 모두 각 행 내 두 rung이 선을 공유하지 않음(요구사항 4 충족).
- 전체 멤버 시뮬레이션(행0→6 순서, 열 표기만 추적):
  - 멤버0: 0→0→0→0→[row3 col0 일치]1→[row4 col1 일치]2→[row5 col2 일치]3→[row6 col3 일치]4.
    최종4 `=permutation[0]=4` ✓
  - 멤버1: 1→1→[row2 col1 일치]2→[row3 col2 일치]3→[row4 col3 일치]4→4→[row6 col3의
    `col+1` 일치]3. 최종3 `=permutation[1]=3` ✓
  - 멤버2: 2→[row1 col2 일치]3→[row2 col3 일치]4→4→[row4 col3의 `col+1` 일치]3→
    [row5 col2의 `col+1` 일치]2→2. 최종2 `=permutation[2]=2` ✓
  - 멤버3: [row0 col3 일치]4→4→[row2 col3의 `col+1` 일치]3→[row3 col2의 `col+1` 일치]2→
    [row4 col1의 `col+1` 일치]1→1→1. 최종1 `=permutation[3]=1` ✓
  - 멤버4: [row0 col3의 `col+1` 일치]3→[row1 col2의 `col+1` 일치]2→[row2 col1의 `col+1`
    일치]1→[row3 col0의 `col+1` 일치]0→0→0→0. 최종0 `=permutation[4]=0` ✓
- 5명 전원 일치 — N=5 역순 케이스도 rung 배치까지 포함해 완전히 검증했다. 교차 검산으로,
  최종열별 점유 멤버(열0←멤버4, 열1←멤버3, 열2←멤버2, 열3←멤버1, 열4←멤버0)가 `target=
  [4,3,2,1,0]`과 정확히 일치함도 확인했다(자기 자신의 역함수라는 역순 순열의 특성과 부합).

#### 예제 L7 — N=20, 역순 순열, 행 수 상한 확인
- Input: `permutation[i] = 19 - i` (`i=0..19`), 즉 가장 많은 스왑을 요구하는 최악 케이스.
- 총 스왑 수: `n(n-1)/2 = 20×19/2 = 190`회(위 "행 수 상한 분석"의 일반 공식).
- 실제 행 수(그리디 스케줄링 후): `2n - 3 = 2×20 - 3 = 37`행(위 "행 수 상한 분석"의 재귀
  패턴, N=2..6 직접검증 + 자기유사 재귀로 일반화).
- Expected: `37`행은 작업 지시가 제시한 "합리적인 행 수(대략 몇~수십 행 이내)" 기준을
  충분히 만족한다(190행 대비 약 5.1배 압축). 전체 190회의 개별 스왑을 손으로 다 추적하지는
  않았으나(N=4, N=5에서 검증한 것과 같은 재귀 구조가 반복되므로), 이 예제는 "행 수 상한이
  실제로 지켜지는가"라는 요구사항(작업 지시 "Golden Test" 절 마지막 문장)에 대한 답으로
  작성했다. Architect/Auditor가 필요하면 스크립트로 N=20 전체를 실행해 37행이 실측값과
  일치하는지, 그리고 시뮬레이션 결과가 `permutation`과 100% 일치하는지 재확인할 것을
  권장한다(위 "행 수 상한 분석"의 "확인 필요" 참고).

> Golden Test 총 7개(L1~L7). N=2 2개(항등/역순), N=3 2개(역순/비역순), N=4 1개(역순, 4명
> 전원 rung 기반 시뮬레이션), N=5 1개(역순, 5명 전원 rung 기반 시뮬레이션), N=20 1개(역순,

### 구현 시 유의사항 (Architect/Builder 참고, 강제 아님)

- 이 절의 출력(`rungs`, `rowCount`)은 현재 `generateDecorativeRungs`가 만드는 "장식용
  가로줄"을 대체해야 한다 — 더 이상 가로줄을 독립적인 무작위값으로 생성해서는 안 되고, 이
  알고리즘의 출력을 그대로 렌더링해야 "그려진 사다리를 실제로 타고 내려간다"는 사용자 인지와
  일치한다.
- 현재 컴포넌트가 멤버별로 직접 그리는 베지어 곡선(`paths`)도, 이 절의 `rungs`를 따라가는
  꺾은선(세로 구간 + 가로 교차 구간의 반복)으로 다시 그려야 시각적으로 "가로줄을 타고
  내려가는" 모양이 된다 — 구체적 SVG 경로 문자열 생성 방식(예: 각 rung 위치에서 수평
  이동을 넣은 절선(polyline) 또는 짧은 S자 곡선)은 Architect/Builder 재량이다. 다만 렌더링
  결과가 "row 오름차순으로 rung을 지날 때만 열이 바뀐다"는 이 절의 시뮬레이션 규칙과
  어긋나서는 안 된다.
- `rowCount`를 화면 Y좌표로 매핑할 때(예: 기존 `TOP_Y=26`, `BOTTOM_Y=220` 사이를 `rowCount+1`
  등분), `rowCount=0`(항등순열, 예제 L1)인 경우를 0으로 나누지 않도록 분기 처리가 필요하다.
- `tasks/bill-split-calculator/ARCHITECTURE.md` "5."가 "가로줄 배치는 순수 장식(결과에
  영향 없음)"이라고 기록한 부분은 이 절 채택 시 더 이상 정확하지 않다 — 가로줄이 이제
  `permutation`으로부터 결정적으로 유도되는 값이 된다(다만 여전히 `permutation` 자체를
  바꾸지는 않으므로, "RNG 주입/통계 검증 대상이 아니다"라는 결론 자체는 그대로 유지된다).
  이 문서(FORMULA.md)는 Edit 권한이 없어 ARCHITECTURE.md를 직접 고칠 수 없으므로, 실제
  문서 갱신은 Architect가 이어서 진행해야 한다.

### 확인 필요 (이 절 국소)

- 일반 `n`(7~20)에 대한 `2n-3` 공식과 "역순 순열이 항상 최대 행 수"라는 가정은 n=2..6
  직접 검증 + 재귀 구조 논증으로 뒷받침했으나, 전체 n에 대한 완전한 수학적 귀납 증명은
  이 문서에 싣지 않았다(위 "행 수 상한 분석" 참고). 필요하면 Architect/Calculation
  Auditor가 스크립트로 N=7~20 전수 실행해 재확인할 수 있다 — 다만 N=20 결과(37행)가
  요구 기준을 이미 넉넉히 만족하므로 이 재확인은 필수 선행 조건은 아니다.
- 화면에 표시 가능한 "행 수 상한"을 Architect가 이 알고리즘과 별개로(예: 모바일 320px
  화면 가독성 기준) 더 낮게 못박고 싶다면, 이 알고리즘 자체는 그 상한을 보장하지 않는다
  (N=20 역순에서 37행이 나오는 것은 이 알고리즘의 자연스러운 결과이지, 조정 가능한
  파라미터가 아니다) — 그런 요구가 있다면 이 절을 다시 열어 압축 전략(예: 여러 행을 시각
  간격만 줄여 겹쳐 배치)을 추가로 설계해야 한다.
