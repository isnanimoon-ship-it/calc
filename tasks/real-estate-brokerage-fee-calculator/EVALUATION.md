### 판단이 필요했던 애매한 지점 (다음 역할이 참고할 것)

1. **`convertedDeposit` 상한 검증 실패 시 오류를 붙이는 필드 — `monthlyRent`로 고정**.
   ARCHITECTURE.md "6.2"는 "계산된 값을 재검증해야 한다"는 규칙만 정하고 어느 필드에
   오류를 표시할지는 명시하지 않았다. `deposit`만으로는 상한을 넘을 수 없고(그 경우
   `deposit` 자체의 상한 검사에서 먼저 걸린다) 항상 `monthlyRent`가 원인이므로
   `monthlyRent` 필드에 오류를 붙이도록 구현했다. UX/UI Critic이 이 오류 메시지의
   위치·문구가 사용자에게 원인을 명확히 전달하는지 검토할 수 있다.
2. **"요율 적용 금액(참고)" 표시 위치 — 계산 근거 dl 목록의 4번째 항목으로 배치**.
   ARCHITECTURE.md "8.1"은 "거래금액 × 요율 = 참고 금액"을 보여줄 것만 요구했고 정확한
   레이아웃은 위임했다. 다른 3개 항목(거래금액·적용 구간·적용 상한요율)과 같은 grid
   안에 넣어 "거래금액 × 요율 = 참고 금액" 한 줄로 표시했다 — 한도액 비교 줄(있는 경우만)
   과는 별도 단락으로 분리해, "이 참고 금액이 최종 확정값이 아니라 한도액과 비교되기
   전 단계"라는 순서가 시각적으로도 드러나게 했다.
3. **부동산 종류 확인 라디오의 표시 조건 — `transactionType`을 선택한 뒤에만 노출**.
   SPEC.md는 "입력 단계에서부터 명시"라고만 했고 거래 유형 선택 전에도 보여줄지는
   명시하지 않았다. 거래 유형 미선택 상태에서는 이 라디오가 어느 모드에도 속하지 않아
   보여줄 맥락이 없다고 판단해, 매매/임대차 중 하나를 선택한 뒤에만 렌더링했다(두 모드
   모두에서 동일한 내용). UX/UI Critic이 이 순서가 "입력 단계에서부터 명시"라는 요구를
   충분히 만족하는지 검토할 수 있다.
4. **표시 전용 "요율 적용 금액"과 최종 `maxBrokerageFee`가 항상 일치하는 경우(한도액이
   없는 구간)에도 두 값을 모두 노출** — 중복처럼 보일 수 있으나, 사용자가 "왜 이 금액이
   나왔는지" 계산 과정을 한도액 유무와 무관하게 일관된 형식으로 볼 수 있게 하려는 의도로
   그대로 두었다. UX/UI Critic이 불필요한 중복으로 판단하면 한도액이 없는 구간에서는 이
   줄을 생략하는 것도 검토할 수 있다.

### Calculation Auditor 인수인계 — 최우선 체크리스트

FORMULA.md가 이미 "확인 필요 목록"으로 남긴 6개 항목(그대로 미해결 상태이며, Builder

있고 결과 화면 "꼭 확인하세요" 섹션에도 노출된다):

1. **「공인중개사법 시행규칙」제20조의 정확한 항·호 번호 — 부분확인**. law.go.kr 원문을

   별표2", "제5항제1호=환산보증금"이라는 서술은 2차 출처(nepla.ai·bigcase.ai·WebSearch AI
   합성)의 일관된 교차 확인에 근거한다. 요율·금액 수치 자체의 신뢰도와는 별개 사안이지만,
   Calculation Auditor가 law.go.kr을 브라우저로 직접 열어 항·호 번호를 재확인할 것을
   권고한다.
2. **「서울특별시 주택 중개보수 등에 관한 조례」의 정확한 조·별표 번호 미확인**. 명칭과

   확인하지 못했다.
3. **17개 광역자치단체 전수조사 미완료**. 서울·경기 2곳만 직접 확인했다(완전히 일치). 이

   필요하다.
4. **중개보수 금액의 절사·반올림에 대한 명시적 법적 근거 부재**. 취득세의 국고금 관리법
   준용 규정 같은 조항을 찾지 못해, 이 계산기는 사이트 공통 원칙(원 단위 사사오입, 최종
   표시 단계 1회)을 잠정 채택했다.
5. **부가가치세 관련 「부가가치세법」의 정확한 조항 미확인**. v1 계산에는 반영하지
   않으며 고지 문구만 노출한다.
6. **오피스텔 외 준주택(도시형생활주택 등)이 이 계산기의 "주택" 범위에 포함되는지
   미검토**.

Builder가 구현 과정에서 추가로 확인을 요청하는 항목:

7. **부동소수점 정밀도 재검증** — ARCHITECTURE.md "7."이 이미 최악 조합(1조원 × 0.7%)과
   실제 부동소수점 곱셈 오차(최대 약 3×10⁻¹⁰)를 직접 계산해 "어떤 실제 입력에서도
   `isCapApplied` 판정이나 최종 반올림 방향이 뒤집힐 수 없다"고 결론 냈다. Builder는 이
   결론을 그대로 신뢰해 별도 epsilon 보정 없이 `Math.round`만 사용했다(예: 899,999,999 ×
   0.004 = 3,599,999.996 → 반올림 3,600,000이 Golden Test에서 정확히 재현됨을 확인했다).
   Calculation Auditor가 실제 구현(`calculateFeeFromTier`)에 대해 동일한 경계값으로
   독립적으로 재확인할 것을 권고한다(ARCHITECTURE.md "14."가 이미 동일하게 권고).
8. **환산보증금 상한 재검증 로직(`validation.ts`)의 필드 귀속 판단** — 위 "판단이 필요했던
   애매한 지점" 1번 참고. 로직 자체(하한은 `deposit`, 상한은 `convertedDeposit`)는
   ARCHITECTURE.md "6.2"를 그대로 따랐으나, 오류를 표시하는 필드 선택은 Builder 재량으로
   결정했다.
