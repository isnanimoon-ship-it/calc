## 1. 기능 테스트 (모드 전환 + Golden Test 대표 사례)

### 1.1 모드 토글 동작
"적금 계산" 클릭 → `aria-pressed` true/false가 정확히 뒤바뀜, 예금 전용 필드(`예치 원금`
입력·`이자 계산 방식` 라디오 2개)가 DOM에서 완전히 사라지고 `월 납입액` 필드로 교체됨을
확인. 이전에 계산해 둔 예금 결과(656자 텍스트)가 모드 전환 즉시 `0`자로 초기화됨(체이닝
방지)도 확인. 반대 방향(적금→예금) 전환도 대칭적으로 정상 동작.

### 1.2 예금 단리 — 원금 10,000,000원·연3%·12개월(샘플 값 채우기)
"샘플 값 채우기" → 원금 `10,000,000`/연이율 `3`/기간 `12`/단리 라디오 체크 자동 입력 확인 →
제출.

화면 표시값(정확히 일치):
- 세후 만기수령액 **10,253,800원**
- 원금 10,000,000원 / 세전 이자 **300,000원** / **이자소득세(15.4%) 46,200원** / 세후 이자
  **253,800원**
- 계산 근거: `10,000,000원 × 연 3% × (12개월 ÷ 12) = 300,000원` → 소득세
  `300,000×14%=42,000원(사사오입)` → 지방소득세 `42,000×10%=4,200원` → `300,000−42,000−4,200
  =253,800원` → `10,000,000+253,800=10,253,800원`

→ **PASS**. 지시받은 기대값(세전이자 300,000원, 세후이자 253,800원)과 정확히 일치.

### 1.3 예금 월복리 — 같은 조건, 계산방식만 복리로
compound 라디오 클릭(같은 화면에서 방식만 전환) → 재제출.

- 세후 만기수령액 **10,257,319원**
- 세전 이자 **304,159원**(ARCHITECTURE.md "11." 정밀 재계산 확정값과 원 단위까지 일치),
  이자소득세(15.4%) 46,840원, 세후 이자 257,319원, 월이율 **0.25%**
- 계산 근거: `10,000,000원 × [(1+0.0025)^12 − 1] = 304,159원` 등 단계별 표시 정상

→ **PASS**. 지시받은 정확한 BigInt 확정값(304,159원)과 화면 표시값이 완전히 일치.

### 1.4 적금 — 월 500,000원·연3.5%·12개월(1pic.kr 대조값)
적금 모드에서 월 납입액 `500000`/연이율 `3.5`/기간 `12` 직접 입력 → 제출.

- 세후 만기수령액 **6,096,232원**
- 납입원금 합계 6,000,000원 / 세전 이자 **113,750원** / 이자소득세(15.4%) 17,518원 / 세후 이자
  **96,232원**
- 회차별 표 12행 정상(1회차 잔여12개월·17,500원 ~ 12회차 잔여1개월·1,458원), 합계 검증 문구
  "이번 계산은 표의 합계와 세전 이자가 원 단위까지 일치합니다."

→ **PASS**. 지시받은 1pic.kr 대조값(세전이자 113,750원, 세후이자 96,232원)과 정확히 일치.
(참고: 적금 모드의 내장 "샘플 값 채우기" 버튼은 FORMULA.md 예제 7(연 3%, 세전이자 97,500원/
세후이자 82,485원)을 쓴다 — 별도로 재확인해 화면 값이 `logic.test.ts` 예제7과도 정확히
일치함을 확인했다.)

### 1.5 Calculation Auditor 대형 원금 경계 케이스 — 원금 9,000,000,000원·연6.27%·113개월
예금 단리 모드로 전환 후 위 값 직접 입력 → 제출.

- 세후 만기수령액 **13,495,495,950원**
- 세전 이자 **5,313,825,000원**, 이자소득세(15.4%) 818,329,050원, 세후 이자
  **4,495,495,950원**

→ **PASS**. `logic.test.ts` "Calculation Auditor 재검증 반례(High)" 골든 테스트 기댓값

`afterTaxMaturityAmount: 13,495,495,950`)과 원 단위까지 완전히 일치 — 4라운드에 걸쳐 수정된

### 1.6 이자소득세(15.4%) vs 이자소득세(국세분) 구분 육안 확인
위 1.2/1.3/1.4/1.5 모든 사례에서 **핵심 결과 카드**의 "이자소득세(15.4%)"는 항상 `totalTax`
(소득세+지방소득세 합계, 예: 46,200원/46,840원/17,518원/818,329,050원)를 가리키고, 그 아래
**계산 방법** 섹션의 "이자소득세(국세분) 계산" 단계는 항상 소득세만(`incomeTax`, 예:
42,000원/42,582원/15,925원/743,935,500원)을 가리키는 **서로 다른 숫자**임을 화면에서 직접
확인했다. 두 라벨이 화면상 위치도 뚜렷이 분리돼 있고(강조 카드 vs 아래 SectionCard), 괄호
수식어("(15.4%)" vs "(국세분)") 자체가 시각적 구분 신호를 주어 혼동 소지가 낮다 — UX/UI
Critic 재검증 판정과 일치.

### 1.7 회차별 표 합계 불일치 고지 — 실제 불일치 케이스로 재현
지시받은 대로 "표시가 실제로 나타나는지"를 확인하기 위해, 위 1.2~1.5 사례(모두 우연히
합계와 세전 이자가 일치하는 케이스)와 별도로 **불일치가 실제로 발생하는 케이스**를 찾아
검증했다: 월 납입액 10,000원(하한)·연이율 0.5%·4개월 →

> "회차별 이자는 각 회차마다 독립적으로 반올림해 표시하기 때문에, 이 표의 합계(42원)가
> 세전 이자(41원)보다 1원 더 많습니다. 계산 오류가 아니라 반올림 정책에 따른 자연스러운
> 차이입니다."

→ **PASS**. 고지 문구가 조건에 따라 "일치" 문구와 "불일치(방향·차액 명시)" 문구 두 가지로
정확히 분기해 실제로 렌더링됨을 확인 — SPEC.md/ARCHITECTURE.md "4."가 의도한 동적 고지가
정상 동작한다.

### 1.8 결과 계산 후 입력 변경 시 재초기화(체이닝 방지)
결과가 표시된 상태에서 (a) 계산방식 라디오만 변경, (b) 연이율 필드만 변경 — 두 경우 모두
결과 영역이 즉시 빈 문자열로 초기화됨을 확인(재계산 전까지 이전 결과와 새 입력이 섞여
보이지 않음).

### 1.9 공유 링크(state) 왕복 — URL 상태 복원
compound 결과(1.3) 상태에서 X 공유 인텐트 링크의 `url` 파라미터(base64 인코딩된

## 2. 모바일 뷰포트 테스트 (320 / 375 / 390 / 768 / 1440px)

`Emulation.setDeviceMetricsOverride`로 5개 뷰포트 전부 에뮬레이션하고
`document.documentElement.scrollWidth vs clientWidth`로 가로 스크롤 발생 여부를 측정한 뒤
적금 12행 결과 상태에서 확인했다.

| 뷰포트 | 가로 오버플로 | 회차별 표 표시 방식 | 비고 |
|---|---|---|---|
| 320px | 없음(320=320) | `sm:hidden` 카드 리스트(12개 모두 렌더링, 스크롤 컨테이너) | 카드마다 회차·잔여개월·납입액·세전 이자 4개 정보 모두 노출 확인(스크린샷) |
| 375px | 없음 | 카드 리스트 | 동일 패턴 |
| 390px | 없음 | 카드 리스트 | 동일 패턴 |
| 768px | 없음(753=753, 스크롤바 제외 실측) | `hidden sm:block` 표(테이블) | 카드 리스트는 숨김 처리 확인 |
| 1440px | 없음(1425=1425) | 표(테이블) | 동일 |

`sm:hidden`/`hidden sm:block` 두 버전이 정확히 상호 배타적으로 노출되고(한쪽이 보이면
다른 쪽은 `display:none`), 둘 다 같은 `scheduleRows` 데이터를 렌더링해 표시 숫자가
100% 동일함을 확인했다 — UX/UI Critic 재검증이 QA에 위임한 항목을 실기기(에뮬레이션)로
직접 재현·통과시켰다.

### 320px 스크린샷 육안 확인
- 입력 폼(모드 토글·연이율·기간·월 납입액 등) 잘림 없음, 다크모드 대비 양호.

  15,000원" 두 줄 — 4개 정보 전부 한 화면에서 가로 스크롤 없이 확인됨.
- 핵심 결과 카드의 "이자소득세(15.4%)" 라벨은 320px 2열 그리드에서 **한 줄로 정상
  표시**됨(UX/UI Critic 재검증이 Low로 남긴 "두 줄로 꺾일 가능성" 우려는 실측 결과

→ **Mobile Critical Issue 0건. PASS.**

## 5. Copy / Reset 동작

- **초기화(Reset)**: 값 입력 후 클릭 시 모든 필드·오류·결과가 정확히 초기값으로 복원됨을
  확인. **다만 적금 모드에서 초기화를 누르면 모드 자체가 예금 모드로 되돌아간다**
  (`EMPTY_FORM.mode`가 `"deposit"`로 하드코딩되어 있어, "초기화"가 필드값뿐 아니라 모드
  선택까지 초기 상태로 되돌리는 것이 의도된 동작으로 보인다) — 아래 "발견 이슈" Low 참고.
- **샘플 값 채우기**: 예금 모드에서는 FORMULA.md 예제 1(원금 10,000,000/연3%/12개월/단리),
  적금 모드에서는 예제 7(월 500,000/연3%/12개월)이 각각 정확히 채워짐을 확인. 두 클릭을
  하나의 동기 실행 컨텍스트에서 딜레이 없이 곧바로 제출하면 React 상태 갱신 타이밍상
  구버전 값으로 제출되는 현상을 테스트 스크립트에서 관찰했으나(React 배칭 특성상 실제
  사용자의 개별 클릭 사이에는 항상 렌더링 시간차가 있으므로), 클릭 사이에 자연스러운
  시간차(150ms 이상)를 두면 항상 최신 샘플 값으로 정상 제출됨을 재확인했다 — 실사용
  시나리오에서 발생하지 않는 테스트 아티팩트이며 제품 결함이 아니다.
- **결과 링크 복사(공유, `ShareActions` 공용 컴포넌트)**: "링크 복사" 버튼 클릭 시 피드백
  텍스트 영역(`<p aria-live="polite">`)이 존재하고 정상 동작 경로에서는 "링크를
  복사했습니다."를 표시하도록 구현돼 있음을 코드로 확인했다. 실제 클립보드 쓰기
  (`navigator.clipboard.writeText`)는 이번 세션(격리된 CDP 자동화 창)에서
  "Document is not focused" 오류로 완전히 검증하지 못했다(테스트 환경 한계 — 아래 "발견
  이슈" 참고, 다른 계산기 QA에서도 보고된 적 있는 동일 계열의 환경 제약). 대신 이 컴포넌트가
  생성하는 공유 URL 자체(base64 상태 인코딩)가 올바른지, 그리고 그 URL로 재방문했을 때
  상태 복원이 실제로 동작하는지는 위 "1.9"에서 완전히 검증했다 — 링크 생성·복원 로직은
  정상, 클립보드 API 호출 자체만 이 환경에서 미검증.

→ 계산 관련 핵심 로직(Reset/Sample 필드 값)은 **PASS**. 클립보드 복사는 환경 제약으로

## 7. 접근성

- **모드 토글**: `aria-pressed="true"/"false"`가 실제로 정확히 전환됨을 클릭 전후 DOM
  속성으로 직접 확인.
- **단리/복리 라디오**: `input[type=radio]` 2개 모두 `aria-required="true"`. 같은
  `name` 속성을 공유하는 진짜 라디오 그룹(`sr-only`로 시각적으로만 숨김, `display:none`
  아님)으로 구현되어 키보드 포커스 가능한 네이티브 시맨틱을 유지한다.
- **오류 필드**: 상한 초과 등 오류 상태에서 해당 input에 `aria-invalid="true"` +
  `aria-describedby`가 실제 `<p role="alert">` 오류 메시지 요소의 id를 정확히 가리키고,
  그 요소가 DOM에 실재하며 텍스트가 일치함을 확인(4절 표 마지막 행).
- **결과 영역 `aria-live`**: 페이지에 `aria-live="polite"` 요소가 **정확히 2개** 존재함을
  확인했다 — (1) `ShareActions`의 복사/공유 피드백 텍스트(`<p>`, 항상 존재하나 평소
  비어 있음), (2) 계산 결과 전체를 감싸는 `<div>`(핵심 결과 카드+회차별 표+계산 근거).
  두 요소를 혼동해 선택자를 잘못 짜면(`querySelector('[aria-live="polite"]')`가 첫 번째
  요소를 먼저 잡음) 테스트가 거짓 실패할 수 있다는 점을 이번 QA에서 직접 겪었다 — 향후
  이 계산기를 다시 테스트할 때 참고할 실무 팁으로 남긴다.
- **FAQ 아코디언**(SPEC.md 정의 7문항 전부 정확히 렌더링 확인): 첫 번째 항목 클릭 시
  `aria-expanded`가 `"false"→"true"`로 전환되고, `aria-controls`가 가리키는 패널이 DOM에
  나타나며 `role="region"` + `aria-labelledby`가 버튼 id와 정확히 일치함을 확인. 다시
  클릭하면 `aria-expanded`가 `"false"`로 돌아가고 패널이 DOM에서 완전히 제거됨(펼치기
  전에는 `aria-controls`가 가리키는 id가 DOM에 아직 존재하지 않는 지연 마운트 패턴 —
  `FaqAccordion` 공용 컴포넌트의 기존 구현이며 이 계산기가 새로 만든 것이 아니다).
- **문서 메타**: `document.documentElement.lang === "ko"`, `<h1>`이 정확히 1개
  ("예금·적금 이자 계산기").

→ Critical/High 접근성 결함 없음. **PASS**.
